2. Identifiers and naming rules

L1 L2

L1 Fundamental

An identifier is a programmatic token used to name a variable, function, class, module, or package in Python source code.

Rule DimensionPermitted Syntactic PatternProhibited Pattern (Raises SyntaxError)
Allowed Characters Alphabet letters (a-z, A-Z), decimal digits (0-9), underscore (_). Punctuation and symbols: @, $, -, %, #, !, &, space.
Leading Character Must start with an alphabet letter or an underscore (_). Cannot start with a digit: e.g. 123total is invalid.
Case Sensitivity Python is strictly case-sensitive: total, Total, TOTAL are 3 distinct identifiers. Do not assume case-folding.
Reserved Collision Identifiers must not match any of the 35 reserved hard keywords. Cannot use words like def, class, return as variable names.
Identifier Length Python imposes no arbitrary character limit on identifier length. Bounded only by system memory (PEP 8 recommends keeping lines under 79–88 characters for readability).

2.1. PEP 8 Naming Conventions

Construct TypeNaming StyleExampleRationale
Variables & Functionssnake_caseuser_account, calculate_tax()Clear readability with lowercase words separated by underscores.
ClassesPascalCase (CapWords)HttpConnection, ThreadPoolDistinguishes type constructors from callable function instances.
ConstantsUPPER_SNAKE_CASEMAX_BUFFER_SIZE, API_TIMEOUTSignals immutable configuration intent to other engineers.

L2 Intermediate

2.2. The 5 Underscore (_) Patterns in Python

In Python, the underscore character conveys critical semantic instructions to the compiler, runtime, and fellow developers:

PatternSyntaxCompiler & Runtime BehaviorEngineering Use Case
Single Leading Underscore _internal_var Weak internal indicator: Python does not restrict access (obj._internal_var still succeeds), but it prevents export when using wildcard imports: from module import * ignores identifiers with a leading _. Protected module/class internals by convention.
Double Leading Underscore __private_var Name Mangling: The CPython compiler internally rewrites the attribute name to _ClassName__private_var. This prevents subclasses from accidentally overriding parent private state. Encapsulation and avoiding subclass collision.
Leading & Trailing Double Underscore __init__, __str__ Magic / Dunder Methods: Reserved by the core language for operator overloading and protocol hooks. Application code must never invent custom dunder names. Python data model protocols.
Single Trailing Underscore class_, def_, in_ Keyword Disambiguation: A standard Python convention used when a domain model name collides with a Python reserved keyword. Naming a variable or parameter without raising SyntaxError (e.g. filter(class_="primary")).
Standalone Underscore _ 1. Dummy / Throwaway Variable: Used in loops and tuple unpacking to signal an unneeded value.
2. REPL Cache: In interactive REPL shells, _ stores the evaluation result of the last executed statement.		 for _ in range(5): do_work()
host, _, port = text.partition(":")

# 1. Single Leading Underscore (_var): Conventional indicator for internal variables
_internal_db_port = 5432
print("Internal config port:", _internal_db_port)

# 2. Double Leading Underscore (__var): Triggers Name Mangling in OOP classes
# Note: Name mangling is a class feature covered in Module 19 (OOP Fundamentals).
# In a class, Python internally rewrites __balance to _ClassName__balance.
# For regular script variables, stick to standard names or single leading underscore!

# 3. Trailing Underscore (var_): Prevents collisions with reserved keywords
class_ = "Physics 101"   # 'class' is a reserved keyword, so we append '_'
def_ = "Definition of terms"
print(f"Course: {class_}, Topic: {def_}")

# 4. System-defined / Dunder (__var__): Reserved by Python runtime
print("Current module name (__name__):", __name__)  # Prints '__main__'

# 5. Single Underscore (_): In Python's interactive REPL shell,
# '_' automatically stores the result of the last evaluated expression:
# >>> 25 * 4
# 100
# >>> _ + 50
# 150

3. Reserved words

L1

L1 Fundamental

  • Reserved keywords have fixed grammatical meanings in Python — they cannot be used as identifiers (variable names, function names, or class names).
  • In Python 3, there are 35 reserved keywords.
  • Capitalization rule: Exactly 3 keywords start with an uppercase letter (True, False, None). The remaining 32 keywords are all strictly lowercase.

3.1. Complete List of all 35 Reserved Words (Categorized)

Category Keywords Description / Use Case
Values / Literals (3) False, None, True Boolean truth values and singleton absence of value (Capitalized).
Logical Operators (3) and, or, not Short-circuiting boolean operations.
Conditionals (3) if, elif, else Conditional branching statements.
Loops & Flow (4) for, while, break, continue Definite/indefinite iteration, loop termination, and next iteration jump.
Functions & Generators (4) def, return, lambda, yield Function definition, exit value, anonymous functions, generator iteration.
Classes & Deletion (2) class, del Object-oriented class definition and explicit variable/item deletion.
Exception Handling (5) try, except, finally, raise, assert Error catching, cleanup guarantee, manual raising, and diagnostic testing.
Namespaces & Scope (2) global, nonlocal Binding identifiers to module global scope or outer closure scope.
Modules & Imports (3) import, from, as Loading libraries, importing specific symbols, and creating aliases.
Context & Identity (4) with, pass, in, is Context managers, no-op placeholder, membership test, and memory identity.
Asynchronous (2) async, await Coroutines and asynchronous task suspension (asyncio).

3.2. Inspecting Keywords in Code

import keyword

# 1. Total keyword count in current Python environment:
print("Keyword count:", len(keyword.kwlist))  # 35

# 2. Print all keywords sorted:
print(keyword.kwlist)

# 3. Check programmatically if a name is reserved:
print(keyword.iskeyword("class"))   # True  -> Cannot use as variable
print(keyword.iskeyword("total"))   # False -> Safe to use

# 4. Attempting to assign to a reserved word:
# class = 100    # SyntaxError: invalid syntax
# def = "func"   # SyntaxError: invalid syntax

3.3. Soft Keywords (Python 3.10+ & 3.12+)

A soft keyword is a keyword that is reserved only in specific syntactic contexts, but remains a completely valid identifier (variable name, function name, parameter, or attribute) everywhere else. This preserves backward compatibility with existing codebases.

Soft Keyword Introduced In Contextual Role Allowed as Variable / Identifier?
match Python 3.10 (PEP 634) Starts a structural pattern matching block: match subject: Yes — e.g. match = re.search(...)
case Python 3.10 (PEP 634) Specifies a pattern clause inside a match block: case 404: Yes — e.g. case = "uppercase"
_ Python 3.10 (PEP 634) Wildcard pattern inside a match statement: case _: Yes — e.g. for _ in range(5): or REPL last result
type Python 3.12 (PEP 695) Defines type aliases: type Point = tuple[float, float] Yes — e.g. type = "admin" (also the built-in function type())

Hard Keywords vs. Soft Keywords Comparison

Aspect Hard Keywords (kwlist) Soft Keywords (softkwlist)
Total Count 35 reserved words 4 contextual words ('_', 'case', 'match', 'type')
Identifier Usage Strictly prohibited (raises SyntaxError) Allowed anywhere outside its specific statement context
Detection Function keyword.iskeyword(name) keyword.issoftkeyword(name)
Primary Purpose Core language syntax & grammar New language features without breaking existing variable names

Soft Keywords Demonstration in Python

import keyword

# 1. Inspect soft keywords list:
print("Soft keywords count:", len(keyword.softkwlist))  # 4
print("keyword.softkwlist:", keyword.softkwlist)        # ['_', 'case', 'match', 'type']

# 2. Testing keyword membership:
print(keyword.issoftkeyword("match"))  # True
print(keyword.issoftkeyword("class"))  # False (class is a HARD keyword)
print(keyword.iskeyword("match"))      # False (not a hard keyword!)

# 3. Soft keywords work seamlessly as variables outside match/type blocks:
match = "regex_result"      # Completely valid variable name!
case = 100                  # Completely valid variable name!
type = "regular_user"       # Completely valid variable name!

# 4. Pattern matching context (Python 3.10+):
http_status = 404
match http_status:          # 'match' acts as keyword here
    case 200:               # 'case' acts as keyword here
        status_msg = "OK"
    case 404:
        status_msg = "Not Found"
    case _:                 # '_' acts as wildcard pattern here
        status_msg = "Unknown Status"

print(f"Status for {http_status}: {status_msg}")
print(f"Variables outside match: match='{match}', case={case}, type='{type}'")

4.3. Line Continuation Rules (Explicit vs Implicit)

In Python, the newline character (\n) normally signals the termination of a logical statement. Long statements can be broken across multiple physical lines in two ways:

MethodMechanism & SyntaxPEP 8 Recommendation
Implicit Continuation (Recommended) Expressions enclosed inside parentheses (), square brackets [], or curly braces {} automatically continue across newlines without extra punctuation. Strongly preferred. Safe, visually clean, and immune to trailing whitespace bugs.
Explicit Continuation (Backslash \) Ending a line with a single backslash (\) escapes the newline character, telling the lexer that the statement continues on the next physical line. Discouraged except when parentheses are syntactically impossible (e.g. complex with statements in older Python). If any invisible whitespace follows \, Python raises a fatal SyntaxError! 
# 1. Implicit line continuation inside parentheses (Pythonic):
total = (
    100 + 200 + 300
    + 400 + 500
)

# 2. Implicit continuation in collections:
allowed_roles = [
    "administrator",
    "developer",
    "auditor",
]

# 3. Explicit line continuation with backslash (\):
flag = 10 > 5 and \
       20 > 15 and \
       30 > 25
# Caution: An invisible space after \ causes 'SyntaxError: unexpected character after line continuation character'

# 4. Multiple statements on a single line using semicolon (;):
x = 10; y = 20; z = x + y  # Syntactically valid, but strongly discouraged by PEP 8

C. Common questions

L1 L2

L1 Fundamental

C.1. Can an identifier start with an underscore, and what does it mean? ▾ Answer

Yes. Underscores are valid identifier characters. Their placement signals specific conventions and compiler behaviors:

  • _var: Indicates a private or internal API by convention. Excluded from wildcard imports (from module import *).
  • __var: Triggers Name Mangling by CPython compiler (_ClassName__var) to prevent subclass attribute collisions.
  • __var__: Reserved for language-defined dunder/magic methods.
  • var_: Trailing underscore to avoid collision with reserved keywords (e.g. class_).
  • _: Standalone throwaway dummy variable or REPL last evaluated expression cache.
C.2. Why does Python enforce indentation instead of curly braces {}? ▾ Answer

In languages with braces (C, Java, JavaScript), visual indentation and actual compiler block scoping can drift apart, leading to famous security bugs like Apple's *“goto fail”*. By making indentation the formal grammar for block scoping:

  • Code visual structure is guaranteed to match compiler execution logic.
  • Eliminates visual clutter from redundant braces and semicolons.
  • Enforces uniform readability across teams and codebases.
C.3. Can an identifier in Python have an unlimited length? ▾ Answer

Yes. Python places no arbitrary maximum character length limit on identifier names. The compiler will parse an identifier of any length bounded only by available system RAM. However, PEP 8 recommends keeping identifier names concise, descriptive, and adhering to the maximum line length limit (79 to 88 characters).

L2 Intermediate

C.4. What is Name Mangling, and how does CPython rewrite double-underscore identifiers? ▾ Answer

Any identifier inside a class definition with at least two leading underscores and at most one trailing underscore (e.g. __balance) is textually replaced by the bytecode compiler with _ClassName__attributeName.

Purpose: It is designed to prevent accidental attribute overrides in subclasses. If a subclass defines __balance, it will be mangled to _SubClass__balance, leaving the parent class's _BaseClass__balance completely intact in the object's instance dictionary.

C.5. Why is implicit line continuation inside parentheses preferred over backslash (\)? ▾ Answer

Explicit line continuation using a trailing backslash (\) is notoriously fragile. If an invisible space or tab character is accidentally inserted after the backslash, Python raises a fatal SyntaxError: unexpected character after line continuation character. In contrast, enclosing expressions in parentheses () allows arbitrary whitespace, comments, and linebreaks safely.

C.6. Are Unicode characters allowed in Python identifiers? ▾ Answer

Yes. Under PEP 3131, Python 3 allows non-ASCII Unicode letters and digits in identifiers (e.g. π = 3.14159 or prix_en_€ = 50). However, PEP 8 mandates using standard ASCII characters exclusively in all production and open-source repositories to avoid editor rendering, typing, and international collaboration issues.
