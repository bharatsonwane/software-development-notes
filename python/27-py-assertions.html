27. Assertions

Internal invariants, sanity checking during development, production caveats, and the -O optimization flag.

1. Introduction

L1 Fundamental

1.1. Overview: What is an Assertion?

An assertion is a debugging aid that tests a boolean condition that developer assumptions dictate must always be true at that specific point in code. If the condition evaluates to True, program execution continues unimpeded.

If the condition evaluates to False, the Python runtime immediately raises an AssertionError, halting execution and pointing directly to the invalid internal state.

Key Mental Model: Assertions are internal guard rails for the developer, not error-handling mechanisms for end users. An assertion failure represents a bug in the software itself, indicating that an internal invariant or assumption was violated.

2. Debugging with assertions

L1 L2

L1 Fundamental

2.1. The Two Forms of the assert Statement

Python provides two syntactic forms for assertions:

  • Simple Form: assert <condition>
  • Augmented Form (with descriptive message): assert <condition>, <error_message>
# Form 1: Simple assertion without message
total_count = 15
assert total_count > 0

# Form 2: Augmented assertion with descriptive diagnostic message (BEST PRACTICE)
def apply_discount(price, discount_percent):
    assert 0 <= discount_percent <= 100, f"Discount must be between 0 and 100%, got {discount_percent}"
    assert price >= 0, f"Price cannot be negative, got {price}"
    discounted_price = price * (1 - discount_percent / 100)
    assert 0 <= discounted_price <= price, "Postcondition failure: discounted price out of bounds!"
    return discounted_price

print("Discounted price:", apply_discount(200, 20))  # 160.0

try:
    apply_discount(200, 150)  # Invalid discount
except AssertionError as err:
    print("Assertion caught:", err)

L2 Intermediate

2.2. Assertions for Internal Invariants

Invariants are conditions that must hold true at specific points in program execution (e.g. loop invariants, state machine transitions, unreachable default cases).

def process_transaction_state(state):
    if state == "PENDING":
        return "Waiting for payment"
    elif state == "CONFIRMED":
        return "Order in fulfillment"
    elif state == "SHIPPED":
        return "Package in transit"
    else:
        # If code reaches here, an illegal unhandled state was introduced!
        raise AssertionError(f"Unreachable branch reached: unknown state '{state}'")

3. assert forms and when to use

L1 L2

L1 Fundamental

3.1. When to Use vs When NOT to Use Assertions

Good Uses for assert Dangerous / Bad Uses for assert
Internal function postconditions and sanity checks. User input validation (form fields, query params, CLI args).
Validating private helper function arguments. Security & authentication checks (checking user roles/permissions).
Defensive programming against impossible states. Checking conditions that depend on external resources (files, network).
Unit testing (e.g., test case assertions in pytest). Operations with side effects inside the condition (e.g., assert pop_item()).

L2 Intermediate

3.2. The -O (Optimize) Production Caveat

When Python is run with the -O (optimize) or -OO flag (e.g., python -O script.py), the bytecode compiler sets the built-in constant __debug__ to False and completely removes and strips all assert statements from the compiled .pyc bytecode files!

CRITICAL SECURITY HAZARD: If you use assert is_admin(user) to guard sensitive operations, running your application with python -O will strip the check completely, allowing ANY unauthorized user full administrative access! Always use standard if not is_admin(user): raise PermissionError() for runtime logic and security checks.

3.3. The Parentheses Tuple Gotcha

In Python, assert is a statement, not a function. If you write parentheses around the condition and message like a function call (assert (condition, "message")), Python parses it as asserting the truthiness of a 2-element tuple!

Because any non-empty tuple evaluates to True in Python boolean logic, the assertion will NEVER fail, even if the condition is False!

# THE FATAL BUG:
x = -5

# This creates a 2-tuple: (False, "x must be positive")
# A non-empty tuple is ALWAYS truthy in Python!
assert (x > 0, "x must be positive")  # NEVER FAILS! (Silent bug)

# THE CORRECT SYNTAX (No wrapping parentheses):
try:
    assert x > 0, "x must be positive"  # Properly raises AssertionError!
except AssertionError as e:
    print("Caught proper assertion:", e)

C. Common questions

L1 L2

L1 Fundamental

C.1. What is an assertion in Python and what does it do when evaluated? ▾ Answer

An assertion is an internal sanity-check statement that verifies a boolean condition expected to always hold true during normal execution. If the condition evaluates to False, an AssertionError is raised, signaling that a programming bug or invalid internal state has occurred.

C.2. What is the difference between an assertion and an exception check? ▾ Answer
  • Assertions (assert): Test internal invariants and developer assumptions that should never happen if the software has no bugs. They can be disabled globally at compile time via the -O flag.
  • Exceptions (if ... raise): Handle expected, recoverable, or external runtime conditions (e.g. bad user input, missing configuration files, network timeouts). They can never be disabled by optimization flags.
C.3. Why must assertions never be used for user input validation or security? ▾ Answer

Running Python with optimization flags (python -O or python -OO) completely ignores and strips all assert statements from the compiled bytecode. If validation or authorization relies on assertions, running in optimized production mode completely disables security guards.

C.4. What is the syntax trap when using parentheses with assert? ▾ Answer

Because assert is a keyword statement and not a function, writing assert(x > 0, "Error") evaluates the expression as a non-empty 2-element tuple (x > 0, "Error"). In Python, all non-empty tuples evaluate to boolean True, meaning the assertion will always pass and never raise an error.

L2 Intermediate

C.5. What does the built-in constant __debug__ represent? ▾ Answer

__debug__ is a built-in boolean constant. Under normal Python execution, __debug__ is True. When Python is executed with the -O flag, __debug__ is set to False. The statement assert cond, msg is compiled under the hood as:

if __debug__:
    if not cond:
        raise AssertionError(msg)

When __debug__ is False, the entire block is omitted from bytecode generation.

C.6. Should you catch AssertionError in production try-except blocks? ▾ Answer

Generally, no. An AssertionError signals a developer logic bug rather than a recoverable runtime event. Catching and swallowing it hides bugs and allows the program to continue running with corrupted internal state. The only common exception is within automated testing frameworks (like pytest or unittest) which catch AssertionError to report test failures.

C.7. What are preconditions, postconditions, and class invariants? ▾ Answer
  • Precondition: A condition that must be true before a function executes (e.g. arguments meet internal requirements).
  • Postcondition: A condition that must be true after a function completes (e.g. output is within calculated bounds).
  • Class Invariant: A condition that an object must satisfy throughout its entire lifetime (e.g. an account balance must never be negative).
C.8. Why should assertion conditions avoid expressions with side effects? ▾ Answer

If an assertion condition executes a function that mutates state (e.g., assert items.pop() == "target"), the program will behave differently in normal mode (where the item is popped) versus optimized -O mode (where the assert is stripped and the item is NOT popped). Assertion conditions must always be pure, side-effect-free evaluations.

P.3. Challenge

  1. Mini project — Build a 2D Vector or Matrix math helper using internal assertions to verify dimension invariants. ▾ Solution 
    # Mini Project: Matrix Dimension Invariant Validator
class Matrix:
    def __init__(self, data):
        assert isinstance(data, list) and len(data) > 0, "Matrix data must be a non-empty list"
        self.rows = len(data)
        self.cols = len(data[0])
        # Invariant: all rows must have identical column count
        for row in data:
            assert len(row) == self.cols, f"Row length mismatch: expected {self.cols}, got {len(row)}"
        self.data = data

    def add(self, other):
        # Invariant: matrices must have identical dimensions for addition
        assert self.rows == other.rows and self.cols == other.cols, \
            f"Dimension mismatch: ({self.rows}x{self.cols}) vs ({other.rows}x{other.cols})"
        result = [
            [self.data[r][c] + other.data[r][c] for c in range(self.cols)]
            for r in range(self.rows)
        ]
        return Matrix(result)

m1 = Matrix([[1, 2], [3, 4]])
m2 = Matrix([[5, 6], [7, 8]])
m3 = m1.add(m2)
print("Matrix addition result:", m3.data)
  2. Edge cases — Demonstrate state-altering expressions in assertions (why they should be avoided). ▾ Solution 
    # Edge Case: Side-effects in assertions

# BAD: Mutating state inside assert:
# In normal mode, queue.pop(0) runs. Under python -O, it is skipped entirely!

# GOOD: Mutate explicitly outside assert, then assert invariant:

assert item == "job2"
