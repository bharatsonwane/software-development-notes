1. Introduction

L1

L1 Fundamental

1.1. Concurrency vs Parallelism

  • Concurrency: The ability of a system to manage multiple tasks by interleaving their execution over overlapping time periods. Even on a single-core CPU, concurrency creates the illusion of simultaneous execution via rapid context switching.
  • Parallelism: The ability of a system to execute multiple computational tasks literally at the exact same physical instant across multiple CPU cores.

1.2. The Global Interpreter Lock (GIL)

In standard CPython (the reference implementation of Python), multithreading is governed by the Global Interpreter Lock (GIL). The GIL is a mutual exclusion lock that prevents multiple native threads from executing Python bytecodes at once.

  • CPU-Bound Tasks (Math, Image Processing, Compression): Threads spend their time executing Python bytecode. Due to the GIL, multithreading does NOT achieve true multi-core speedup for CPU-bound tasks in CPython (and can even run slower due to lock contention). Use the multiprocessing module instead!
  • I/O-Bound Tasks (Network Requests, File I/O, Database Queries): When a thread waits for disk I/O or network responses, Python releases the GIL. Another thread can immediately execute. Multithreading provides massive throughput and responsiveness gains for I/O-bound tasks.

2. Introduction to multithreading

L1 L2

L1 Fundamental

2.1. Processes vs Threads

Property Process Thread
Memory Space Isolated, independent memory address space. Shared memory space within the parent process.
Creation Overhead Heavy; requires duplicating or allocating full OS resources. Lightweight; shares process heap and descriptors.
Communication Inter-Process Communication (IPC: pipes, sockets, shared memory). Direct variable access (requires synchronization to avoid race conditions).
Crash Impact One process crash does not affect other processes. An unhandled crash in one thread can terminate the entire process.

2.2. The Main Thread

When any Python program starts, the Python runtime creates a single execution thread known as the MainThread. Any additional threads spawned by the code are child threads.

import threading

# Inspecting the main thread:
current = threading.current_thread()
print("Current thread name:", current.name)       # MainThread
print("Thread identifier:  ", current.ident)      # Integer thread ID
print("Is thread alive?    ", current.is_alive())  # True

3. Creating and starting threads

L1 L2

L1 Fundamental

3.1. Approach 1: Passing a Target Function

The simplest way to create a thread is by instantiating threading.Thread with a target callable and a tuple of positional arguments via args (or a dictionary via kwargs).

import threading
import time

def worker_task(task_name, duration):
    print(f"[{threading.current_thread().name}] Starting {task_name}...")
    time.sleep(duration)  # Simulating I/O wait
    print(f"[{threading.current_thread().name}] Finished {task_name}!")

# 1. Instantiate threads
t1 = threading.Thread(target=worker_task, args=("Download File A", 1), name="Worker-A")
t2 = threading.Thread(target=worker_task, args=("Download File B", 2), name="Worker-B")

# 2. Start threads (spawns OS-level native thread)
t1.start()
t2.start()

# 3. Wait for threads to finish using join()
t1.join()
t2.join()

print("Both worker threads have completed. Main continues.")
CRITICAL: start() vs run(): Always call t.start() to initiate a new thread of execution. If you call t.run() directly, it simply executes the target function sequentially inside the current calling thread without spawning any new thread!

L2 Intermediate

3.2. Approach 2: Subclassing threading.Thread

For complex thread workers requiring internal state, subclass threading.Thread, call super().__init__() in __init__, and override the run() method.

import threading
import time

class CustomWorkerThread(threading.Thread):
    def __init__(self, worker_id, items):
        super().__init__(name=f"CustomWorker-{worker_id}")
        self.worker_id = worker_id
        self.items = items
        self.processed_count = 0

    def run(self):
        print(f"[{self.name}] Beginning batch processing...")
        for item in self.items:
            # Process each item
            time.sleep(0.05)
            self.processed_count += 1
        print(f"[{self.name}] Completed batch of {self.processed_count} items.")

# Spawning custom worker threads:
worker1 = CustomWorkerThread(1, ["apple", "banana", "cherry"])
worker2 = CustomWorkerThread(2, ["dog", "elephant"])

worker1.start()
worker2.start()

worker1.join()
worker2.join()

print("Worker 1 processed:", worker1.processed_count)
print("Worker 2 processed:", worker2.processed_count)

4. Thread names and related methods

L1 L2

L1 Fundamental

4.1. Thread Inspection Utilities

  • threading.current_thread(): Returns the Thread object corresponding to the caller's thread of control.
  • threading.active_count(): Returns the number of currently alive Thread objects.
  • threading.enumerate(): Returns a list of all currently alive Thread objects.
  • thread.is_alive(): Returns True if the thread has started and has not yet terminated.
  • thread.ident / thread.native_id: Unique system thread identifiers assigned by the OS.
import threading
import time

def background_pulse():
    time.sleep(0.5)

threads = [threading.Thread(target=background_pulse, name=f"Pulse-{i}") for i in range(3)]
for t in threads:
    t.start()

print(f"Active thread count: {threading.active_count()}")
print("Currently running threads:")
for t in threading.enumerate():
    print(f"  - {t.name} (alive={t.is_alive()}, id={t.ident})")

for t in threads:
    t.join()

5. Daemon threads

L1 L2

L1 Fundamental

5.1. Daemon vs Non-Daemon Threads

By default, threads created in Python are non-daemon threads. The Python interpreter process will remain alive and running until every non-daemon thread has finished executing its code.

A daemon thread is a low-priority background support thread (e.g., garbage collectors, periodic healthcheck pingers, telemetry senders). When only daemon threads remain alive, the Python runtime exits immediately, abruptly killing all daemon threads.

import threading
import time

def daemon_heartbeat():
    while True:
        print("[HEARTBEAT] Ping sent from daemon thread...")
        time.sleep(0.5)

# Marking a thread as daemon:
daemon_t = threading.Thread(target=daemon_heartbeat, daemon=True, name="HeartbeatDaemon")
daemon_t.start()

print("Main thread running important 2-second job...")
time.sleep(2.0)
print("Main thread exiting now.")
# When main thread exits here, daemon_t is killed instantly!
CAUTION: Daemon Threads Skip Cleanups! Because daemon threads are abruptly killed upon interpreter exit, their finally blocks are NOT guaranteed to execute, and context managers (like open file handles or database transactions) may NOT be properly closed or committed! Never perform state-critical operations in daemon threads without graceful shutdown signals.

6. Synchronization (Lock, RLock, Semaphore)

L1 L2

L1 Fundamental

6.1. Race Conditions & threading.Lock

A race condition occurs when multiple threads concurrently read and modify shared mutable state without proper coordination, leading to data corruption. In Python, an operation like counter += 1 translates to multiple underlying bytecode instructions (read, increment, write). If context switches happen between these bytecodes, updates are lost.

import threading

counter = 0
lock = threading.Lock()

def safe_increment(n):
    global counter
    for _ in range(n):
        # Mutual exclusion using with lock context manager:
        with lock:
            counter += 1

threads = [threading.Thread(target=safe_increment, args=(100_000,)) for _ in range(5)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print("Expected: 500,000 | Actual counter:", counter)  # 500,000 (Guaranteed!)

L2 Intermediate

6.2. threading.RLock (Reentrant Lock)

A standard Lock cannot be acquired twice by the same thread; attempting to do so causes a self-deadlock. An RLock (Reentrant Lock) keeps track of the owning thread and recursion depth, allowing the owner to acquire it multiple times. It is released only when the release count equals the acquire count.

import threading

class Account:
    def __init__(self, balance):
        self.balance = balance
        self.rlock = threading.RLock()

    def deposit(self, amount):
        with self.rlock:
            self.balance += amount

    def transfer(self, target_account, amount):
        with self.rlock:  # First acquire
            self.balance -= amount
            # deposit also acquires self.rlock - with standard Lock, this deadlocks!
            target_account.deposit(amount)

acc1 = Account(1000)
acc2 = Account(500)
acc1.transfer(acc2, 200)
print("Acc 1 balance:", acc1.balance)  # 800
print("Acc 2 balance:", acc2.balance)  # 700

6.3. threading.Semaphore

A Semaphore manages an internal counter that decreases on acquire() and increases on release(). It allows up to $N$ concurrent threads to access a shared pool of resources (e.g., maximum 3 simultaneous database connections).

import threading
import time

# Permit at most 2 simultaneous connections
connection_pool = threading.Semaphore(2)

def access_database(thread_id):
    print(f"Thread {thread_id} waiting for connection slot...")
    with connection_pool:
        print(f"--> Thread {thread_id} ACQUIRED database slot! Working...")
        time.sleep(0.5)
        print(f"<-- Thread {thread_id} RELEASING slot.")

threads = [threading.Thread(target=access_database, args=(i,)) for i in range(5)]
for t in threads:
    t.start()
for t in threads:
    t.join()

7. Inter-thread communication (Event, Condition, Queue)

L1 L2

L1 Fundamental

7.1. threading.Event

An Event is one of the simplest communication mechanisms between threads: one thread signals an event, and other threads wait for it. It manages an internal boolean flag initialized to False.

  • event.set(): Sets flag to True, awakening all waiting threads.
  • event.clear(): Resets flag to False.
  • event.wait([timeout]): Blocks until the flag becomes True.
import threading
import time

ready_event = threading.Event()

def server_initialization():
    print("[INIT] Loading configurations and database pools...")
    time.sleep(1.0)
    print("[INIT] Server ready to receive traffic!")
    ready_event.set()  # Broadcast signal to waiting workers

def client_worker(client_id):
    print(f"Client {client_id} waiting for server to become ready...")
    ready_event.wait()  # Blocks until ready_event.set() is called
    print(f"Client {client_id} connected and processing requests!")

t_server = threading.Thread(target=server_initialization)
t_clients = [threading.Thread(target=client_worker, args=(i,)) for i in range(3)]

for c in t_clients: c.start()
t_server.start()

t_server.join()
for c in t_clients: c.join()

L2 Intermediate

7.2. queue.Queue: The Gold Standard for Thread Communication

Instead of manually coordinating locks and events, idiomatic Python multithreading uses queue.Queue. A Queue is internally thread-safe; all locking, notification, and bounds-checking are handled automatically.

import threading
import queue
import time

task_queue = queue.Queue(maxsize=5)

def producer(items_count):
    for i in range(items_count):
        item = f"TASK-{i}"
        task_queue.put(item)  # Blocks if queue is full
        print(f"[PRODUCED] {item}")
        time.sleep(0.1)

def consumer(consumer_id):
    while True:
        try:
            item = task_queue.get(timeout=0.5)  # Blocks until item available
            print(f"  [CONSUMER {consumer_id}] Processed {item}")
            task_queue.task_done()  # Signals task completion
        except queue.Empty:
            print(f"  [CONSUMER {consumer_id}] Queue empty, worker shutting down.")
            break

prod = threading.Thread(target=producer, args=(6,))
cons1 = threading.Thread(target=consumer, args=(1,))
cons2 = threading.Thread(target=consumer, args=(2,))

prod.start()
cons1.start()
cons2.start()

prod.join()
task_queue.join()  # Blocks until all items have been task_done()
cons1.join()
cons2.join()
print("All tasks processed safely!")

8. Good practices and summary

L1 L2

L1 Fundamental

8.1. Summary Checklist

  • Prefer Queues: Avoid shared mutable variables protected by manual locks wherever possible; pass messages through queue.Queue.
  • Always Use Context Managers: Use with lock: instead of manual lock.acquire() and lock.release() to prevent deadlocks caused by unhandled exceptions.
  • Watch for GIL Bottlenecks: Use threading for I/O-bound tasks; use multiprocessing or concurrent.futures.ProcessPoolExecutor for CPU-heavy calculations.
  • Clean Daemon Lifecycles: Never rely on daemon threads to flush files or commit database transactions on shutdown.

C. Common questions

L1 L2

L1 Fundamental

C.1. What is the Python GIL and how does it affect multithreading? ▾ Answer

The Global Interpreter Lock (GIL) is a mutex in CPython that ensures only one thread executes Python bytecode at any given moment, protecting CPython's internal memory management and reference counting from race conditions.

As a result, multithreading in CPython cannot utilize multiple CPU cores for CPU-bound computations (such as number crunching). However, the GIL is released during I/O operations (network requests, disk access, sleeps), making multithreading highly effective for concurrent I/O-bound applications.

C.2. What is the difference between t.start() and t.run()? ▾ Answer

t.start(): Invokes the operating system API to create and launch a new native thread of execution, which then internally calls the thread's run() method in parallel.

t.run(): Simply calls the target function directly inside the current calling thread. No new thread is spawned, and the code runs synchronously and sequentially.

C.3. What is a daemon thread, and what happens when the main thread finishes? ▾ Answer

A daemon thread is a background thread that does not prevent the Python process from terminating. When all non-daemon threads have finished executing, the Python interpreter immediately exits, terminating all remaining daemon threads abruptly without executing their finally clauses.

C.4. What is the difference between Lock and RLock? ▾ Answer

Lock (Standard Mutex): Can be acquired only once. If the thread currently holding the lock attempts to acquire it again, it deadlocks itself.

RLock (Reentrant Lock): Can be acquired multiple times by the same owning thread. It tracks the acquiring thread and an internal counter. The lock is only released when the owner has called release() an equal number of times as acquire().

L2 Intermediate

C.5. How does a Semaphore differ from a Lock? ▾ Answer

A Lock allows mutually exclusive access to exactly one thread at a time (binary state: locked or unlocked).

A Semaphore manages an internal integer counter representing available resource tokens. It allows up to $N$ threads to acquire tokens simultaneously, making it ideal for limiting concurrency (e.g., maximum 5 simultaneous database connections or rate-limiting HTTP requests).

C.6. How do threading.Event and threading.Condition differ? ▾ Answer

Event: Provides a simple binary signal (flag True or False). Any number of threads can wait for the flag to be set via wait(). Once set via set(), all waiting threads wake up simultaneously.

Condition: Always associated with an underlying lock. It allows threads to wait until a complex state condition is satisfied (via wait()), releasing the lock while waiting and re-acquiring it when notified by another thread via notify() or notify_all().

C.7. Why is queue.Queue preferred over manual locks for inter-thread communication? ▾ Answer

queue.Queue encapsulates all necessary locks, condition variables, and boundary checks internally. It eliminates common concurrency bugs:

  • No manual acquire() and release() calls, eliminating lock leaks and deadlocks.
  • Built-in blocking and timeouts on put() and get().
  • Clean task tracking with task_done() and join().
C.8. When should you choose threading vs multiprocessing vs asyncio? ▾ Answer
  • multiprocessing: For CPU-intensive tasks (machine learning, data encryption, video encoding). Spawns separate processes with separate Python runtimes, bypassing the GIL to use all CPU cores.
  • threading: For I/O-bound tasks with legacy synchronous libraries or blocking OS calls where threads can share memory easily.
  • asyncio: For high-concurrency network servers (thousands of simultaneous web socket connections) using cooperative single-threaded event loops.

P.3. Challenge

  1. Mini project — Build a multi-worker Producer-Consumer task pipeline with graceful shutdown using queue.Queue. ▾ Solution 
    # Mini Project: Thread-safe Producer-Consumer Pipeline
import threading
import queue
import time

task_queue = queue.Queue(maxsize=10)
stop_event = threading.Event()

def producer(count):
    for i in range(count):
        task_queue.put(f"Job-{i}")
        print(f"[Producer] Queued Job-{i}")
        time.sleep(0.05)

def worker(worker_id):
    while not stop_event.is_set() or not task_queue.empty():
        try:
            job = task_queue.get(timeout=0.1)
            print(f"  [Worker {worker_id}] Processing {job}")
            time.sleep(0.08)
            task_queue.task_done()
        except queue.Empty:
            continue

p = threading.Thread(target=producer, args=(6,))
workers = [threading.Thread(target=worker, args=(i,)) for i in range(2)]

p.start()
for w in workers: w.start()

p.join()
task_queue.join()
stop_event.set()
for w in workers: w.join()
print("All tasks processed and workers gracefully stopped.")
