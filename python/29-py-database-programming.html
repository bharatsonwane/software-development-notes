1. Introduction

L1

L1 Fundamental

1.1. Overview: What is PDBC & PEP 249?

Python Database Connectivity (PDBC) refers to interacting with relational database management systems (RDBMS) directly from Python code. To ensure that developers do not have to learn a completely different API for every vendor (PostgreSQL, SQLite, MySQL, Oracle), Python defined PEP 249 (Python Database API Specification v2.0).

PEP 249 establishes standard interfaces, method signatures, parameter formatting rules, and exception hierarchies across all compliant Python database drivers. Whether using sqlite3, psycopg2 / psycopg (for PostgreSQL), or other drivers, the fundamental workflow is identical:

The Standard PEP 249 DB-API Workflow:
  1. Connect: Open a connection object via driver.connect(...).
  2. Cursor: Create a cursor via connection.cursor() to manage query context and result sets.
  3. Execute: Run parameterized SQL queries with cursor.execute(sql, params) or cursor.executemany(sql, seq_of_params).
  4. Retrieve / Persist: Fetch rows using cursor.fetchone(), cursor.fetchall(), or cursor.fetchmany(). For DML (INSERT/UPDATE/DELETE), commit changes via connection.commit().
  5. Release: Close the cursor and connection via cursor.close() and connection.close() (or using with context managers).

1.2. The Cardinal Rule: Prevent SQL Injection

Never format or concatenate user input into SQL query strings using Python f-strings or string concatenation. Doing so leaves your application vulnerable to SQL Injection (SQLi) attacks, where malicious actors can bypass authentication, exfiltrate private data, or wipe database tables.

import sqlite3

# DANGEROUS VULNERABILITY (SQL Injection):
user_id: str = "1 OR 1=1; DROP TABLE users; --"
# BAD: f-string inserts raw string directly into the SQL parser!
# cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")

# SAFE: Parameterized Query (PEP 249 parameter binding)
# The database engine treats the parameter strictly as literal data, never executable SQL:
conn: sqlite3.Connection = sqlite3.connect(":memory:")
cursor: sqlite3.Cursor = conn.cursor()
cursor.execute("CREATE TABLE IF NOT EXISTS users (id TEXT, name TEXT)")
cursor.execute("SELECT * FROM users WHERE id = ?", (user_id,))

1.3. Database Programming Typing (Connection & Cursor)

In modern typed Python, annotate connection handles, cursors, and query return types to prevent interface mistakes:

import sqlite3
from typing import Any

conn: sqlite3.Connection = sqlite3.connect(":memory:")
cur: sqlite3.Cursor = conn.cursor()

cur.execute("CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT, price REAL)")
cur.execute("INSERT INTO products (name, price) VALUES (?, ?)", ("Widget", 19.99))
conn.commit()

cur.execute("SELECT id, name, price FROM products WHERE price < ?", (50.0,))
single_record: tuple[Any, ...] | None = cur.fetchone()
all_records: list[tuple[Any, ...]] = cur.fetchall()

cur.close()
conn.close()

2.1. Built-in sqlite3: The Zero-Configuration Database

Python includes the sqlite3 module in the standard library. SQLite runs embedded in-process without requiring a separate database server process, making it ideal for testing, local data storage, and prototyping.

Special database target: passing ":memory:" to sqlite3.connect() creates a lightning-fast, volatile in-RAM database that disappears when the process exits.

import sqlite3

# Connect to a transient in-memory database:
conn: sqlite3.Connection = sqlite3.connect(":memory:")
cursor: sqlite3.Cursor = conn.cursor()

# Verify SQLite engine version:
cursor.execute("SELECT sqlite_version()")
row: tuple[str] | None = cursor.fetchone()
version: str = row[0] if row else "unknown"
print(f"Connected to SQLite engine version: {version}")

# Clean up resources:
cursor.close()
conn.close()

3.1. DDL: Creating and Dropping Tables

Data Definition Language (DDL) statements like CREATE TABLE and DROP TABLE define the schema structure. Always use IF NOT EXISTS and IF EXISTS to prevent fatal runtime errors on repeat runs.

import sqlite3

conn: sqlite3.Connection = sqlite3.connect(":memory:")
cur: sqlite3.Cursor = conn.cursor()

# 1. Clean previous state if needed:
cur.execute("DROP TABLE IF EXISTS employees")

# 2. Define schema with constraints:
cur.execute("""
    CREATE TABLE employees (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        name TEXT NOT NULL,
        department TEXT NOT NULL,
        salary REAL CHECK(salary >= 0),
        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    )
""")
print("Table 'employees' created successfully.")

L2 Intermediate

3.2. Single Inserts vs Bulk executemany()

Executing individual INSERT statements inside a Python loop causes heavy round-trip overhead. PEP 249 provides cursor.executemany(), which executes a prepared statement against an iterable sequence of tuples efficiently.

# Single insert:
cur.execute(
    "INSERT INTO employees (name, department, salary) VALUES (?, ?, ?)",
    ("Alice", "Engineering", 95000.0)
)
alice_id: int | None = cur.lastrowid
print(f"Inserted Alice with ID: {alice_id}")

# Bulk insert using executemany():
new_hires: list[tuple[str, str, float]] = [
    ("Bob", "Marketing", 72000.0),
    ("Charlie", "Engineering", 110000.0),
    ("Diana", "Finance", 88000.0)
]

cur.executemany(
    "INSERT INTO employees (name, department, salary) VALUES (?, ?, ?)",
    new_hires
)

# CRUCIAL: Always commit DML operations to persist them!
conn.commit()
print(f"Bulk insert complete. Rows affected: {cur.rowcount}")

4.1. Reading Data: fetchone(), fetchall(), and Direct Iteration

After running a SELECT query, several methods exist to retrieve the results:

  • cursor.fetchone(): Returns the next single row as a tuple (or None if no more rows).
  • cursor.fetchall(): Fetches all remaining rows at once into a list of tuples.
  • cursor.fetchmany(size): Fetches the next batch of $N$ rows (ideal for pagination).
  • Direct Cursor Iteration: for row in cursor: ... — streams rows lazily without loading the entire result set into RAM at once!
from typing import Any

# 1. Fetch all rows:
cur.execute("SELECT id, name, department, salary FROM employees ORDER BY salary DESC")
all_rows: list[tuple[Any, ...]] = cur.fetchall()
print("All employees (ordered by salary):")
for r in all_rows:
    print(f"  ID {r[0]}: {r[1]} ({r[2]}) - ${r[3]:,.2f}")

# 2. Fetch single row:
cur.execute("SELECT name, salary FROM employees WHERE id = ?", (1,))
single_emp: tuple[Any, ...] | None = cur.fetchone()
if single_emp:
    print(f"\nEmployee 1: {single_emp[0]}, Salary: ${single_emp[1]}")

# 3. Memory-friendly cursor stream:
cur.execute("SELECT name FROM employees WHERE department = ?", ("Engineering",))
for (emp_name,) in cur:
    print(f"Engineer: {emp_name}")

L2 Intermediate

4.2. Updating and Deleting Records with Transactions

Transactions satisfy the ACID guarantees (Atomicity, Consistency, Isolation, Durability). In PEP 249, transactions are managed at the connection level. If an error occurs during an update or delete, call conn.rollback() to revert the database to its pre-transaction state.

import sqlite3

def update_employee_salary(conn: sqlite3.Connection, emp_id: int, new_salary: float) -> None:
    cur: sqlite3.Cursor = conn.cursor()
    try:
        cur.execute("UPDATE employees SET salary = ? WHERE id = ?", (new_salary, emp_id))
        if cur.rowcount == 0:
            print(f"[WARN] No employee found with ID: {emp_id}")
        else:
            conn.commit()
            print(f"[SUCCESS] Updated employee {emp_id} salary to ${new_salary}")
    except Exception as err:
        conn.rollback()
        print(f"[ERROR] Update failed, transaction rolled back: {err}")

update_employee_salary(conn, 1, 98000.0)

def delete_employee(conn: sqlite3.Connection, emp_id: int) -> None:
    cur: sqlite3.Cursor = conn.cursor()
    try:
        cur.execute("DELETE FROM employees WHERE id = ?", (emp_id,))
        conn.commit()
        print(f"[DELETED] Successfully removed employee {emp_id}")
    except Exception as err:
        conn.rollback()
        print(f"[ERROR] Delete failed, transaction rolled back: {err}")

delete_employee(conn, 2)

4.3. Row Factories (Returning Dictionaries Instead of Tuples)

By default, DB-API returns rows as plain numeric tuples (e.g. row[0], row[1]). Using sqlite3.Row allows accessing columns by name (row["name"]) or index, making code cleaner and resilient against column reordering.

import sqlite3

conn.row_factory = sqlite3.Row  # Configure row factory
cur: sqlite3.Cursor = conn.cursor()

cur.execute("SELECT id, name, salary FROM employees WHERE id = ?", (1,))
row: sqlite3.Row | None = cur.fetchone()

if row is not None:
    print("Access by column name:", row["name"])
    print("Access by index:      ", row[1])
    print("Convert to dict:      ", dict(row))

5. Working with PostgreSQL (psycopg & DB-API)

L1 L2

L1 Fundamental

5.1. Why PostgreSQL in Enterprise Python?

PostgreSQL is widely regarded as the world's most advanced open-source object-relational database. Unlike SQLite, PostgreSQL is a client-server RDBMS designed for multi-user concurrency, high write throughput, enterprise ACID compliance, complex window functions, and rich native data types (such as JSONB, UUID, and geometric arrays).

5.2. PostgreSQL Python Drivers: psycopg2 vs psycopg (v3)

The standard, battle-tested Python driver for PostgreSQL is psycopg2 (or the pure-C binary distribution psycopg2-binary). The next-generation driver is psycopg (version 3), which adds full native Python asyncio support and faster binary copying.

# Installing PostgreSQL drivers via pip:
# pip install psycopg2-binary
# or modern psycopg 3:
# pip install "psycopg[binary]"

import psycopg2
from psycopg2.extras import RealDictCursor
from typing import Any

# Standard PostgreSQL connection parameters:
DB_CONFIG: dict[str, Any] = {
    "host": "localhost",
    "port": 5432,
    "dbname": "production_db",
    "user": "postgres_user",
    "password": "secure_password_123"
}

try:
    # 1. Establish connection:
    conn = psycopg2.connect(**DB_CONFIG)
    
    # 2. Use context managers for automatic cursor closing:
    with conn.cursor(cursor_factory=RealDictCursor) as cur:
        # Note: PostgreSQL uses %s for parameter substitution (NEVER '?'!):
        cur.execute("""
            SELECT id, username, email, is_active
            FROM users
            WHERE is_active = %s
            ORDER BY id ASC
            LIMIT %s;
        """, (True, 5))

        rows: list[dict[str, Any]] = cur.fetchall()
        for user in rows:
            print(f"User: {user['username']} | Email: {user['email']}")

    conn.close()
except psycopg2.Error as err:
    print(f"PostgreSQL database error: {err}")

L2 Intermediate

5.3. PostgreSQL Connection Pooling

In PostgreSQL, each client connection spawns a new server-side process on the database host. Repeatedly opening and closing TCP connections on every HTTP request introduces severe latency and can overwhelm server resources. Production applications use a Connection Pool to reuse pre-warmed connection instances.

from psycopg2 import pool
from typing import Any

# Initialize a thread-safe connection pool (min 1, max 10 connections):
db_pool: pool.ThreadedConnectionPool = pool.ThreadedConnectionPool(
    minconn=1,
    maxconn=10,
    host="localhost",
    port=5432,
    dbname="production_db",
    user="postgres_user",
    password="secure_password_123"
)

def fetch_user_by_id(user_id: int) -> tuple[Any, ...] | None:
    # Acquire a connection from the pool:
    conn = db_pool.getconn()
    try:
        with conn.cursor() as cur:
            cur.execute("SELECT id, username FROM users WHERE id = %s", (user_id,))
            return cur.fetchone()
    finally:
        # ALWAYS return connection to the pool when finished:
        db_pool.putconn(conn)

# Graceful application shutdown:
# db_pool.closeall()

5.4. Working with PostgreSQL JSONB and Transactions

PostgreSQL allows storing and querying structured JSON data with indexable JSONB columns. psycopg2 automatically serializes Python dictionaries into JSONB and deserializes them back into Python dictionaries.

import psycopg2
from psycopg2.extras import Json
from typing import Any

def insert_user_settings(conn: Any, user_id: int, settings_dict: dict[str, Any]) -> int:
    with conn.cursor() as cur:
        cur.execute("""
            INSERT INTO user_profiles (user_id, preferences)
            VALUES (%s, %s)
            ON CONFLICT (user_id) DO UPDATE
            SET preferences = EXCLUDED.preferences
            RETURNING id;
        """, (user_id, Json(settings_dict)))
        
        row = cur.fetchone()
        record_id: int = row[0]
        conn.commit()
        return record_id

C. Common questions

L1 L2

L1 Fundamental

C.1. What is PEP 249 (Python DB-API 2.0) and why is it important? ▾ Answer

PEP 249 is the Python Database API Specification v2.0. It defines a standardized programming interface for connecting to and interacting with relational databases from Python. It specifies standard connection functions (connect()), connection methods (cursor(), commit(), rollback(), close()), cursor methods (execute(), fetchall(), fetchone()), and standard exception classes (DatabaseError, IntegrityError, OperationalError).

This allows Python code to be database-agnostic: switching between SQLite, PostgreSQL, and MySQL requires changing only the connection initialization and minor dialect syntax, while the core application logic remains identical.

C.2. Why is SQL Injection dangerous and how does parameterization prevent it? ▾ Answer

SQL Injection occurs when untrusted input is concatenated directly into a SQL command string, altering the SQL parser's syntax tree and allowing attackers to run arbitrary database commands (such as dumping passwords or dropping tables).

Parameterized queries separate the query structure from the input parameters. The SQL statement is compiled by the database engine first, and parameters are sent separately over the protocol as literal values. Even if a parameter contains ' OR 1=1; DROP TABLE users;, the database treats it as literal string content, completely neutralizing the attack.

C.3. What are the differences between fetchone(), fetchall(), and fetchmany()? ▾ Answer
  • fetchone(): Retrieves the single next row of a query result set, returning a tuple or None when exhausted. Minimal memory overhead.
  • fetchall(): Fetches all remaining rows at once into a Python list. Can cause memory exhaustion (MemoryError) if the result set contains hundreds of thousands of rows.
  • fetchmany(size=N): Fetches a specific batch of $N$ rows. Ideal for pagination, chunked processing, and streaming pipelines.
C.4. Why is conn.commit() necessary, and what does conn.rollback() do? ▾ Answer

In PEP 249 compliant drivers, connections start transactions automatically when DML statements (INSERT, UPDATE, DELETE) are executed.

conn.commit() writes and permanently applies all pending transactional changes to persistent disk storage. If you close the connection without calling commit(), all changes are automatically discarded. conn.rollback() explicitly aborts the current transaction, reverting the database state to the beginning of the transaction block.

L2 Intermediate

C.5. What parameter placeholders are used by SQLite vs PostgreSQL? ▾ Answer

PEP 249 defines multiple parameter styles (paramstyle):

  • SQLite (qmark style): Uses question marks: WHERE id = ? AND name = ?.
  • PostgreSQL / psycopg2 (pyformat or format style): Uses percent-s: WHERE id = %s AND name = %s. (Note: even for integers and dates, use %s; the driver casts the types automatically based on the Python objects).
C.6. What is a Connection Pool and why is it critical for PostgreSQL? ▾ Answer

A connection pool maintains a cache of pre-opened, active database connections that can be borrowed and returned by worker threads or web requests.

Unlike SQLite or multi-threaded servers, PostgreSQL uses a process-per-connection architecture. Spawning a new PostgreSQL connection involves a full OS process fork, TCP three-way handshake, TLS negotiation, and authentication handshake (taking 20–100ms per connection). A connection pool reduces connection acquisition latency to sub-millisecond speeds and protects the database from connection exhaustion.

C.7. How do you retrieve query results as dictionaries instead of tuples? ▾ Answer
  • In SQLite: Set the connection's row factory: conn.row_factory = sqlite3.Row. Each row can then be accessed by column name (row["email"]) or converted to a dict via dict(row).
  • In PostgreSQL (psycopg2): Use cursor_factory=RealDictCursor from psycopg2.extras: with conn.cursor(cursor_factory=RealDictCursor) as cur: .... Rows are returned directly as standard Python dictionaries.
C.8. How do with context managers work with database connections and cursors? ▾ Answer
  • with conn.cursor() as cur: guarantees that the cursor is automatically closed when exiting the block, even if an exception is raised.
  • In sqlite3 and psycopg2, with conn: manages transaction boundaries: if the block completes without errors, it automatically calls conn.commit(); if an exception occurs, it automatically calls conn.rollback()! Note: with conn: does NOT close the connection itself.

  1. Mini project — Build an atomic bank funds transfer function with complete transaction rollback on failure. ▾ Solution 
    # Mini Project: Atomic Banking Transfer with ACID Rollback
import sqlite3

conn: sqlite3.Connection = sqlite3.connect(":memory:")
cur: sqlite3.Cursor = conn.cursor()

cur.execute("""
    CREATE TABLE accounts (
        id INTEGER PRIMARY KEY,
        holder TEXT NOT NULL,
        balance REAL CHECK(balance >= 0)
    )
""")

cur.execute("INSERT INTO accounts VALUES (1, 'Alice', 1000.0), (2, 'Bob', 500.0)")
conn.commit()

def transfer(conn: sqlite3.Connection, from_acc: int, to_acc: int, amount: float) -> None:
    cur: sqlite3.Cursor = conn.cursor()
    try:
        # Atomic Transaction Begin
        cur.execute("UPDATE accounts SET balance = balance - ? WHERE id = ?", (amount, from_acc))
        cur.execute("UPDATE accounts SET balance = balance + ? WHERE id = ?", (amount, to_acc))
        conn.commit()
        print(f"[SUCCESS] Transferred ${amount:.2f} from Account #{from_acc} to #{to_acc}")
    except sqlite3.IntegrityError as err:
        conn.rollback()  # Rollback on CHECK(balance >= 0) violation
        print(f"[ROLLBACK] Transfer of ${amount:.2f} aborted: Insufficient funds or constraint error ({err})")

# Valid transfer:
transfer(conn, 1, 2, 200.0)

# Invalid transfer (attempting to overdraft Alice's remaining $800):
transfer(conn, 1, 2, 950.0)

for row in cur.execute("SELECT id, holder, balance FROM accounts"):
    print(f"  Account {row[0]} ({row[1]}): ${row[2]:.2f}")
conn.close()
