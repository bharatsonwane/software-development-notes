1.1. Why Automated Testing?

A unit test is an automated script that exercises an isolated, individual component (unit) of source code—such as a single function, method, or class—and verifies that it returns the expected outcome given specific inputs.

Key benefits of unit testing:

  • Prevents Regressions: Ensures that adding new features or fixing bugs does not silently break existing functionality.
  • Enables Confident Refactoring: Allows developers to clean up architecture, improve performance, or upgrade Python versions knowing tests will catch anomalies immediately.
  • Acts as Living Documentation: Clear tests demonstrate exactly how classes and functions are intended to be invoked.
  • Enables CI/CD: Automated test suites run on every commit or pull request before code reaches production servers.

2. unittest introduction

L1 L2

L1 Fundamental

2.1. Python's Built-in unittest Framework

The unittest module (historically inspired by JUnit) is Python's built-in testing framework. Key conventions:

  • Test classes inherit from unittest.TestCase.
  • Individual test methods must start with the prefix test_ (e.g. test_addition). Methods without this prefix are ignored by the test runner.
  • Tests use specialized assertion methods provided by TestCase.
import unittest

def add(x, y):
    return x + y

def divide(x, y):
    if y == 0:
        raise ValueError("Cannot divide by zero!")
    return x / y

class TestMathOperations(unittest.TestCase):
    def test_add_positive_integers(self):
        self.assertEqual(add(10, 5), 15)

    def test_add_negative_integers(self):
        self.assertEqual(add(-10, -5), -15)

    def test_divide_valid(self):
        self.assertAlmostEqual(divide(10, 3), 3.3333333, places=5)

    def test_divide_by_zero_raises_value_error(self):
        with self.assertRaises(ValueError):
            divide(10, 0)

if __name__ == "__main__":
    unittest.main()

4. Limitations of unittest; intro to pytest

L1 L2

L1 Fundamental

4.1. Why the Python Community Migrated to pytest

While unittest is built into Python, it suffers from several legacy Java-style design constraints:

  • Boilerplate Overhead: Every test requires class declarations and inheriting from unittest.TestCase.
  • Cumbersome Assertions: You must memorize dozens of specialized camelCase methods (assertEqual, assertIn, assertDictEqual).
  • No Native Parametrization: Running the same test logic over 20 different inputs requires messy subtests or loops.

pytest is the modern industry standard framework for Python testing. In pytest, tests are simple standalone functions, assertions use standard Python assert statements, and failure outputs provide rich value introspection.

# Clean pytest test function:
def test_string_formatting():
    name = "Bharat"
    greeting = f"Hello, {name}!"
    # Plain Python assert: pytest rewrites the bytecode to show exact failed diffs!
    assert greeting == "Hello, Bharat!"
    assert len(greeting) > 0

L2 Intermediate

4.2. Parametrized Tests with @pytest.mark.parametrize

Instead of writing separate test functions or loops, @pytest.mark.parametrize runs a test function multiple times across a matrix of input arguments and expected results.

import pytest

def is_palindrome(text):
    clean = "".join(c.lower() for c in text if c.isalnum())
    return clean == clean[::-1]

@pytest.mark.parametrize("test_input, expected", [
    ("radar", True),
    ("Racecar", True),
    ("hello", False),
    ("A man, a plan, a canal: Panama", True),
    ("12321", True),
    ("12345", False)
])
def test_palindrome_detection(test_input, expected):
    assert is_palindrome(test_input) == expected

5. setUp / tearDown / class-level fixtures in pytest

L1 L2

L1 Fundamental

5.1. setUp and tearDown in unittest

In unittest, test setup and cleanup are implemented by overriding lifecycle methods:

  • setUp(self): Runs before every single test method in the class.
  • tearDown(self): Runs after every single test method in the class.
  • @classmethod setUpClass(cls): Runs once before any tests in the class start.
  • @classmethod tearDownClass(cls): Runs once after all tests in the class complete.
import unittest

class TestDatabaseWorker(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        print("\n[DB SETUP] Connecting to shared database...")

    @classmethod
    def tearDownClass(cls):
        print("\n[DB TEARDOWN] Dropping shared database connection...")

    def setUp(self):
        # Fresh isolated state before each test
        self.session_data = {"user": "Alice", "cart": []}

    def tearDown(self):
        # Cleanup state after each test
        self.session_data.clear()

    def test_add_item(self):
        self.session_data["cart"].append("Item-1")
        self.assertEqual(len(self.session_data["cart"]), 1)

    def test_empty_cart(self):
        self.assertEqual(len(self.session_data["cart"]), 0)

L2 Intermediate

5.2. Modern Fixtures in pytest

pytest replaces rigid class lifecycles with fixtures via @pytest.fixture. Fixtures use dependency injection: test functions request fixtures simply by declaring them as parameters.

Teardown logic is implemented using the yield keyword: code before yield runs as setup; code after yield runs as teardown!

import pytest

@pytest.fixture(scope="function")
def sample_user():
    # Setup:
    print("\n[SETUP] Creating test user object...")
    user = {"id": 101, "name": "Bharat", "role": "admin"}
    yield user  # Provide value to test function
    # Teardown:
    print("\n[TEARDOWN] Purging user session...")

def test_user_role(sample_user):
    assert sample_user["role"] == "admin"

def test_user_id(sample_user):
    assert sample_user["id"] > 0

6.1. Mocking External Dependencies with unittest.mock

Real-world unit tests should not make actual external network calls, charge real credit cards, or send real emails. The standard library provides unittest.mock.patch to replace external functions with controllable mock objects.

from unittest.mock import patch, MagicMock

# Function that depends on external network API:
def get_current_weather(city):
    import urllib.request
    # In reality, this makes an HTTP call to api.weather.com
    raise ConnectionError("No internet in unit test environment!")

def weather_advisory(city):
    temp = get_current_weather(city)
    if temp > 35:
        return "Heat advisory!"
    elif temp < 5:
        return "Frost advisory!"
    return "Pleasant weather."

# Mocking get_current_weather to test advisory logic in isolation:
@patch("__main__.get_current_weather")
def test_weather_heat_advisory(mock_weather):
    mock_weather.return_value = 40  # Simulate 40 degrees without internet!
    advisory = weather_advisory("Delhi")
    assert advisory == "Heat advisory!"
    mock_weather.assert_called_once_with("Delhi")

C. Common questions

L1 L2

L1 Fundamental

C.1. What is a unit test and how does it differ from integration testing? ▾ Answer

Unit Testing: Tests the smallest testable piece of code (a single function or method) in total isolation from external systems. All external dependencies (databases, network calls, filesystem) are mocked out.

Integration Testing: Tests how multiple components interact and communicate with each other (e.g. testing whether the application layer correctly writes and reads records from a real PostgreSQL database instance).

C.2. What are the roles of setUp() and tearDown() in unittest? ▾ Answer

setUp() executes immediately before each test method is invoked, allowing you to construct clean, pristine test fixtures. tearDown() executes immediately after each test method completes (even if the test failed or raised an exception), ensuring that temporary files, databases, or mocks are cleaned up.

C.3. Why has pytest largely superseded unittest in professional Python? ▾ Answer
  • No Boilerplate: Tests are plain Python functions; no class inheritance required.
  • Native Assertions: Uses standard assert expr. Pytest rewrites the AST to provide detailed failure explanations (e.g. showing dict diffs or set differences).
  • Powerful Fixture System: Reusable dependency-injected fixtures with explicit scoping (function, class, module, session).
  • Rich Ecosystem: Hundreds of plugins (pytest-cov for test coverage, pytest-xdist for parallel execution, pytest-asyncio).
C.4. How do you assert that a specific exception is raised in pytest vs unittest? ▾ Answer

In unittest:

with self.assertRaises(ValueError):
    divide(10, 0)

In pytest:

with pytest.raises(ValueError) as exc_info:
    divide(10, 0)
assert "Cannot divide by zero" in str(exc_info.value)

L2 Intermediate

C.5. How do pytest fixture scopes work? ▾ Answer

Fixture scopes determine how frequently a fixture is recreated:

  • function (default): Re-executed once per test function. Guaranteed isolation.
  • class: Re-executed once per test class.
  • module: Re-executed once per Python module (file).
  • package: Re-executed once per package.
  • session: Executed once for the entire test suite run (ideal for expensive resources like starting a Dockerized database container).
C.6. How does yield enable teardown in a pytest fixture? ▾ Answer

When a fixture contains yield, execution pauses and hands the yielded value to the test function. Once the test completes, pytest resumes execution immediately after the yield statement to execute cleanup code (equivalent to a finally block).

C.7. What is mocking and when should you use unittest.mock.patch? ▾ Answer

Mocking simulates the behavior of complex, slow, or external real objects. You should use patch when testing code that interacts with:

  • External HTTP REST APIs or third-party web services.
  • Filesystem operations (writing/deleting files).
  • Database connections or message brokers.
  • Time-dependent functions (e.g. freezing datetime.now()).
C.8. What is the difference between unit testing and Selenium browser testing? ▾ Answer

Unit tests execute pure Python code in memory, taking mere milliseconds per test. Selenium tests drive a real headless or GUI browser, executing Javascript, rendering CSS, and simulating real user interactions (clicks, keyboard strokes). Selenium tests are slower and prone to timing flakiness, but verify critical end-to-end user workflows.

P.3. Challenge

  1. Mini project — Build a complete Shopping Cart test suite testing item addition, total calculation, discounts, and tax with pytest. ▾ Solution 
    # Mini Project: Shopping Cart Unit Test Suite
class ShoppingCart:
    def __init__(self):
        self.items = {}

    def add_item(self, item_name, price, quantity=1):
        if price < 0 or quantity < 1:
            raise ValueError("Invalid price or quantity")
        if item_name in self.items:
            self.items[item_name]["quantity"] += quantity
        else:
            self.items[item_name] = {"price": price, "quantity": quantity}

    def total(self, discount_pct=0):
        subtotal = sum(i["price"] * i["quantity"] for i in self.items.values())
        return subtotal * (1 - discount_pct / 100)

# Pytest test suite:
import pytest

@pytest.fixture
def populated_cart():
    cart = ShoppingCart()
    cart.add_item("Book", 20.0, 2)   # 40.0
    cart.add_item("Pen", 5.0, 4)     # 20.0
    return cart

def test_cart_total(populated_cart):
    assert populated_cart.total() == 60.0

def test_cart_discount(populated_cart):
    assert populated_cart.total(discount_pct=10) == 54.0

def test_invalid_item():
    cart = ShoppingCart()
    with pytest.raises(ValueError):
        cart.add_item("Bad", -10.0)
