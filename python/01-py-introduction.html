1.1. Overview

  • Python is an interpreted, high-level, dynamically typed, garbage-collected, multi-paradigm programming language.
  • It provides a high level of abstraction from underlying hardware architectures, automating manual memory allocation and deallocation while exposing a uniform, portable interface across operating systems.

L2 Intermediate

2.2. Multi-Paradigm Technical Architecture

Rather than enforcing a single ideological paradigm (such as pure object-orientation in early Java or pure functional purity in Haskell), Python integrates four foundational programming architectures:

ParadigmLanguage RootsCore Python Features & Mechanisms
Functional Programming C / Lisp First-class functions, higher-order functions (map, filter, reduce), closures, anonymous lambda expressions, list/dict/set comprehensions, and immutable data structures (tuple, frozenset).
Object-Oriented Programming (OOP) C++ Classes, encapsulation, single & multiple inheritance, Method Resolution Order (C3 Linearization MRO), polymorphism via magic/dunder methods, and abstract base classes (abc.ABC).
Procedural & Scripting C / Perl / Shell Top-level execution flow without mandatory boilerplate wrapper classes, automated control flow (if-elif-else, while, for), regular expressions (re), and standard I/O streams.
Modular Architecture Modula-3 Hierarchical packages (__init__.py), module-level encapsulation, explicit namespace boundaries (import, from ... import), and lazy symbol exports. 
# Demonstrating multi-paradigm coexistence in a single Python script:

# 1. Procedural: linear script execution
data = [1, 2, 3, 4, 5, 6]

# 2. Functional: pure higher-order transformation with lambda and filter
evens_squared = list(map(lambda x: x ** 2, filter(lambda x: x % 2 == 0, data)))

# 3. Object-Oriented: encapsulated state and behaviors
class MathProcessor:
    def __init__(self, values):
        self.values = values

    def compute_sum(self):
        return sum(self.values)

processor = MathProcessor(evens_squared)
print("Computed sum:", processor.compute_sum())  # Output: 56

3. Core technical features

L1 L2

L1 Fundamental

FeatureTechnical Definition & Mechanism
Dynamically TypedTypes are bound to runtime heap objects, not to variable names. Type validation occurs during runtime evaluation rather than compile time.
Strongly TypedPython strictly enforces type boundaries. It never performs implicit type coercions across incompatible types (e.g. "5" + 5 raises TypeError instead of coercing to string or integer).
Interpreted & Bytecode-DrivenSource code (.py) is parsed into an Abstract Syntax Tree (AST), compiled into portable bytecode (.pyc), and executed by a stack-based virtual machine.

L2 Intermediate

3.1. Dynamic vs Static & Strong vs Weak Typing Matrix

A classic technical interview distinction: Dynamic Typing is frequently confused with Weak Typing. Python is Dynamically Typed AND Strongly Typed.

Typing DimensionStrong Typing (Python, Ruby, Rust)Weak Typing (JavaScript, C, PHP)
Static Typing (Compile-time) Rust / Java / C++: Variables have declared types; types cannot change; no implicit coercion between incompatible types. C / C++: Unchecked pointer casts (void*) and implicit conversions can bypass type safety.
Dynamic Typing (Runtime) Python: Variables are untyped references to typed objects. Incompatible operations (10 + "20") fail immediately with TypeError. JavaScript: "10" + 20 evaluates silently to "1020" (implicit coercion); "10" - 5 evaluates to 5. 
# Python's Strong Typing Proof:
x = 10       # x points to an int object in heap memory
y = "20"     # y points to a str object in heap memory

# In JavaScript: x + y results in "1020"
# In Python:
try:
    result = x + y
except TypeError as e:
    print("TypeError raised:", e)  # unsupported operand type(s) for +: 'int' and 'str'

# Dynamic Rebinding: variable name can reference an object of a different type:
x = "Now I am a string"  # Valid: variable x simply points to a new str object

4. Python flavors & runtime engines

L1 L2

L1 Fundamental

Python is a formal language specification (defined by PEPs and language reference documents). Different runtime implementations—known as flavors—execute Python code targeting distinct virtual machines and platforms.

ImplementationWritten InTarget RuntimeKey Technical Characteristics
CPython (Standard) C Native OS / CPU The standard reference implementation. Direct C-API support for NumPy/C-extensions; utilizes a Global Interpreter Lock (GIL) and reference-counted garbage collection.
PyPy RPython Native OS with JIT High-performance engine equipped with a Tracing Just-In-Time (JIT) compiler. Typically achieves 4×–7× speedups on CPU-heavy numerical loops.
Jython (JPython) Java Java Virtual Machine (JVM) Compiles Python source into Java bytecode (.class). Provides seamless two-way interoperability with Java libraries; no CPython GIL.
IronPython C# .NET CLR / DLR Integrates Python with the Microsoft .NET ecosystem; allows direct access to WPF, WCF, and native .NET assemblies.
Cython C / Python C/C++ Compiler A superset of Python supporting optional static type declarations. Compiles code directly into optimized C/C++ translation units for maximum performance.
MicroPython C Bare-metal MCU A lean, stripped-down runtime optimized to execute directly on microcontrollers (ESP32, STM32, Raspberry Pi Pico) with as little as 16 KB of RAM.
Anaconda Python C (CPython fork) Native OS CPython bundled with Intel Math Kernel Library (MKL) binaries, OpenBLAS optimizations, and the Conda package management ecosystem.

5. Python execution architecture & PVM

L1 L2

L1 Fundamental

Python code does not execute directly on CPU hardware. CPython uses a two-stage compilation and execution architecture:

Execution Pipeline:
Source Code (.py) $\longrightarrow$ Compiler (Lexer / Parser / AST) $\longrightarrow$ Bytecode (.pyc) $\longrightarrow$ Python Virtual Machine (PVM) $\longrightarrow$ Machine Code $\longrightarrow$ CPU Hardware
  • Step 1 (Bytecode Compilation): CPython first parses Python source code into an Abstract Syntax Tree (AST), then compiles it into an intermediate, platform-independent instruction set called Bytecode.
  • Step 2 (Bytecode Caching in __pycache__): When an imported module is compiled, CPython serializes the bytecode to disk inside a __pycache__ directory as a .pyc file (e.g., module.cpython-312.pyc). The .pyc header contains a magic number and source file timestamp/hash. If the source file has not changed, compilation is skipped, drastically speeding up application startup time.
  • Step 3 (PVM Execution): The Python Virtual Machine (PVM) is the runtime engine of CPython. It is an internal stack-based evaluation loop (implemented in C within ceval.c) that reads bytecode instructions sequentially, executes them, and dispatches corresponding C function calls to the operating system and CPU.

L2 Intermediate

5.1. Inspecting Bytecode Instructions with the dis Module

You can disassemble any Python function or code block into raw PVM opcodes using Python’s built-in dis (disassembler) module:

import dis

def calculate_total(price, tax_rate):
    total = price + (price * tax_rate)
    return total

# Disassemble the function into PVM bytecode opcodes:
dis.dis(calculate_total)

Bytecode Disassembly Output Breakdown:

# Output from dis.dis(calculate_total):
# Line  Byte Offset  Opcode Name       Operand (Argument Value)
# ---------------------------------------------------------------
#   2           0    LOAD_FAST         0 (price)
#               2    LOAD_FAST         0 (price)
#               4    LOAD_FAST         1 (tax_rate)
#               6    BINARY_OP         5 (*)
#               8    BINARY_OP         0 (+)
#              10    STORE_FAST        2 (total)
#
#   3          12    LOAD_FAST         2 (total)
#              14    RETURN_VALUE
  • LOAD_FAST: Pushes a local variable onto the PVM evaluation stack.
  • BINARY_OP (*): Pops the top two stack items, computes their product, and pushes the result back onto the stack.
  • BINARY_OP (+): Pops the top two items, computes their sum, and pushes the result.
  • STORE_FAST: Pops the top value from the stack and stores it in the local variable slot for total.
  • RETURN_VALUE: Pops the top value and returns it to the caller.

6. Limitations & GIL mechanics

L1 L2

L1 Fundamental

Understanding the architectural trade-offs of Python is essential for systems design and technical interviews:

LimitationRoot Architectural CauseIndustry Mitigation Strategy
Execution Speed Dynamic typing and bytecode interpretation overhead; instructions are evaluated dynamically rather than executing as raw CPU instructions. Offload compute-heavy inner loops to vectorized C/C++ libraries (NumPy, SciPy), write Cython extensions, or run via PyPy JIT.
Global Interpreter Lock (GIL) CPython's internal memory management is not thread-safe; a mutual-exclusion lock prevents multiple native threads from executing Python bytecode simultaneously. Use process-based parallelism (multiprocessing, ProcessPoolExecutor), asynchronous I/O (asyncio), or free-threaded builds (PEP 703 in Python 3.13+).
Memory Footprint Every Python object has metadata overhead (reference count, type pointer, dictionary descriptors). Even a simple integer in Python 64-bit occupies 28 bytes of heap memory. Use __slots__ in classes, primitive arrays (array module), or contiguous memory arrays (NumPy buffers).
Mobile & Browser Native CPython is built around native OS kernels and posix/win32 APIs; it lacks first-class built-in UI toolkits for mobile touch interfaces or native web browsers. WebAssembly runtimes (Pyodide, PyScript), cross-platform UI frameworks (Kivy, BeeWare).

L2 Intermediate

6.1. The GIL (Global Interpreter Lock) in Detail

The GIL Rule: In CPython, even if a machine has 64 CPU cores, only one thread can execute Python bytecode at any given millisecond within a single CPython process.
  • Why does the GIL exist? CPython relies heavily on reference counting for garbage collection. Without the GIL, every increment/decrement of an object's reference counter across multiple threads would require atomic synchronization or granular locks, resulting in severe performance penalties for single-threaded programs.
  • I/O-bound vs CPU-bound:
    • For I/O-bound tasks (network calls, disk reads, database queries), the GIL is released during the wait, allowing multithreading to deliver excellent concurrent throughput.
    • For CPU-bound tasks (image processing, data crunching, heavy math), multiple Python threads contend for the single GIL lock, running slower than a single thread due to context-switch thrashing!

7. Python release journey (2.x → 3.x)

L1 L2

L1 Fundamental

Python 3.0 (released December 2008) intentionally broke backward compatibility to eliminate historical architectural flaws in Python 2.x.

AreaPython 2.x (Legacy / EOL)Python 3.x (Modern Standard)
Text & Strings Default str was ASCII byte sequences; Unicode required explicit u"..." literals, causing constant UnicodeDecodeError crashes. Default str is always pure Unicode text; raw binary data uses dedicated bytes and bytearray types.
Division Operator 5 / 2 performed floor division, returning integer 2 (truncating remainders silently). 5 / 2 performs true division, always returning float 2.5. Floor division requires explicit 5 // 2.
Print Statement print "Hello" was a language statement without parentheses; difficult to redirect or customize. print("Hello") is a built-in function accepting keyword arguments (sep, end, file, flush).
Integer Types Two distinct integer types: 32-bit fixed int and arbitrary-precision long (with trailing L, e.g. 100L). Unified single int type with automatic arbitrary precision; integers never overflow.
Iteration Models Methods like range(), dict.keys(), map() allocated complete lists eagerly in memory. Return lazy, memory-efficient iterable view objects (range, dict_keys, generators).

L2 Intermediate

7.1. Notable Python 3 Minor Milestones

  • Python 3.5: Native coroutines via async and await syntax (PEP 492); type hints framework (PEP 484).
  • Python 3.6: Formatted string literals (f-strings: f"{var}"); preservation of insertion order in dictionaries.
  • Python 3.7: Data Classes (@dataclass); context variables (contextvars).
  • Python 3.8: Assignment Expressions (the Walrus Operator: :=); positional-only parameters (/).
  • Python 3.9: Dictionary merge and update operators (|, |=); native generic type hints (list[int]).
  • Python 3.10: Structural Pattern Matching (match ... case); explicit union syntax (int | str).
  • Python 3.11: Faster CPython optimizations (specializing adaptive interpreter, 10%–60% speedup); exception groups and except*.
  • Python 3.12: Per-interpreter GIL in C-API; inline type parameter syntax (type Point[T] = ...); isolated comprehensions.

8. Install, REPL, and execution modes

L1

L1 Fundamental

8.1. Interactive Shell (REPL)

The REPL (Read-Eval-Print Loop) is Python’s interactive interpreter. It continuously reads expressions, evaluates them in the active process state, prints the result, and loops.

$ python3
>>> data = [10, 20, 30]
>>> sum(data)
60
>>> exit()

8.2. Script Execution Modes

# hello.py
print("Execution Mode Demo")
  • 1. File Path Execution: Directly invokes the script path:
python3 hello.py
python3 path/to/script.py
  • 2. Module Execution Mode (-m flag): Searches sys.path for the module and executes its top-level namespace:
python3 -m hello
python3 -m http.server 8000   # Launches built-in web server module
  • 3. Inline Command String (-c flag): Runs short commands directly from the shell without saving a file:
python3 -c "import sys; print(sys.version)"

8.3. Virtual Environment Isolation (venv)

To prevent dependency pollution across different system applications, every Python project should operate inside a dedicated virtual environment.

# 1. Create a virtual environment directory named .venv:
python3 -m venv .venv

# 2. Activate the virtual environment:
source .venv/bin/activate          # macOS / Linux
# .venv\Scripts\activate          # Windows PowerShell / CMD

# 3. Verify active interpreter binary location:
which python                       # macOS / Linux (Windows: where python)
# Output will point to: /path/to/project/.venv/bin/python

# 4. Deactivate when work is complete:
deactivate

C. Common questions

L1 L2

L1 Fundamental

C.1. Is Python a compiled language or an interpreted language? ▾ Answer

Python is both compiled and interpreted.

  • Compilation stage: When a Python program runs, CPython first compiles the source code (.py) into platform-independent intermediate bytecode (.pyc files). This compilation step verifies syntax and transforms code into stack instructions.
  • Interpretation stage: The compiled bytecode is then executed line-by-line by the Python Virtual Machine (PVM), which translates bytecode opcodes into machine instructions on the fly.

Because the compilation stage occurs automatically behind the scenes without producing a standalone machine binary (unlike C/C++), Python is classified in industry as an interpreted, bytecode-driven language.

C.2. What is the difference between dynamic typing and weak typing? Is Python weakly typed? ▾ Answer

No. Python is dynamically typed, but STRONGLY typed.

  • Dynamic Typing: Types are associated with runtime values in memory, not variable identifiers. Variables can be freely reassigned to objects of different types during execution.
  • Strong Typing: Python strictly prevents operations between incompatible types. For example, in a weakly typed language like JavaScript, "5" + 5 silently coerces the integer into a string yielding "55". In Python, "5" + 5 immediately raises a fatal TypeError because implicit type coercion across string and integer is disallowed.
C.3. What are .pyc files and the __pycache__ directory? ▾ Answer

.pyc files are compiled bytecode caches generated by CPython. When a module is imported for the first time, CPython compiles its source to bytecode and saves it inside __pycache__ with a file header embedding a magic version number and timestamp/hash of the original .py file.

On subsequent runs, if the source file has not been modified, CPython loads the .pyc file directly, skipping the parsing and compilation phases to reduce application startup latency.

L2 Intermediate

C.4. What is the Python Virtual Machine (PVM), and how does it compare to the Java Virtual Machine (JVM)? ▾ Answer
  • The PVM is the runtime engine of CPython. It is a software-based stack machine implemented in C that steps through bytecode instructions and executes the corresponding C routines.
  • PVM vs JVM:
    • JVM: Employs sophisticated HotSpot JIT compilers to translate Java bytecode into highly optimized native machine code at runtime, achieving near-C execution speeds.
    • Standard PVM (CPython): Interprets bytecode sequentially without an integrated native JIT compiler (though PyPy provides a JIT implementation). PVM is simpler, starts up faster, and interfaces directly with C libraries.
C.5. What is the Global Interpreter Lock (GIL), and why does CPython use it? ▾ Answer

The GIL is a mutex (mutual exclusion lock) used by CPython to synchronize thread execution so that only one native OS thread executes Python bytecode at any instant within a process.

Reason for existence: CPython's memory management heavily relies on reference counting. Without the GIL, every single reference count modification across threads would require atomic locking, degrading single-threaded execution performance and complicating C-extension integration.

Solution for multi-core CPU scaling: Use the multiprocessing module to create separate processes with independent memory spaces and separate GIL instances, or use C-extensions that release the GIL during heavy computation.

C.6. How does PyPy achieve significant speedups over standard CPython? ▾ Answer

PyPy includes a Tracing Just-In-Time (JIT) compiler. While CPython interprets bytecode repeatedly inside every loop iteration, PyPy monitors running code, identifies frequently executed ("hot") loops, traces the exact types being processed, and compiles those bytecode paths directly into optimized native machine code.

On long-running, CPU-bound mathematical loops, PyPy can run 4× to 7× faster than CPython.
