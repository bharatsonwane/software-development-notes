1. Introduction

L1

L1 Fundamental

1.1. Overview: Errors vs Exceptions

In software development, software failures generally fall into two broad categories:

  • Syntax Errors (Compile-Time / Parsing Errors): Occur when code violates Python syntax rules (e.g., missing colons, invalid indentation, unclosed quotes). The Python parser detects these before execution starts; no code runs.
  • Exceptions (Runtime Errors): Syntactically valid code that encounters an anomalous, unexpected, or invalid condition during execution (e.g., dividing by zero, accessing an absent dictionary key, attempting to read a non-existent file, network disconnection).

Exception handling is the mechanism that prevents unhandled runtime exceptions from crashing the program, allowing applications to gracefully recover, log diagnostics, free critical operating system resources, and provide user-friendly error responses.

Guiding Principle: EAFP vs LBYL: Python strongly favors EAFP ("Easier to Ask for Forgiveness than Permission") over LBYL ("Look Before You Leap"). Instead of writing deeply nested if-else checks verifying every condition beforehand, wrap the operation in a try-except block and handle the failure cleanly.

2. Introduction and default exception handling

L1 L2

L1 Fundamental

2.1. Default Exception Handling (The Crash Lifecycle)

When an error occurs inside a function, Python creates an exception object containing the error type, diagnostic message, and the complete call stack trace (traceback). If the current function has no try-except block to catch the exception, the function immediately terminates and passes the exception up to its caller.

This process of unwinding the call stack continues until either:

  1. An active try-except block catches and handles the exception object.
  2. The exception reaches the top-level main thread without being caught. At that point, Python's default exception handler takes over: it prints the complete traceback to sys.stderr and forcefully terminates the interpreter process with a non-zero exit code.
# Unhandled Exception demonstration (crashes execution)
def calculate_unit_price(total_cost, quantity):
    print("[STEP 1] Starting unit price calculation...")
    # If quantity is 0, ZeroDivisionError is raised here:
    unit_price = total_cost / quantity
    print(f"[STEP 2] Unit price computed: {unit_price}")
    return unit_price

def process_order(order_id, cost, qty):
    print(f"Processing order #{order_id}")
    price = calculate_unit_price(cost, qty)
    print("Order completed successfully!")

# Calling with valid quantity:
process_order(101, 500, 5)

# Calling with 0 quantity:
# process_order(102, 500, 0)
# Traceback (most recent call last):
#   File "script.py", line 16, in <module>
#   File "script.py", line 10, in process_order
#   File "script.py", line 4, in calculate_unit_price
# ZeroDivisionError: division by zero

L2 Intermediate

2.2. Graceful Recovery with try-except

By wrapping risky code in a try block, any matching exception raised inside is caught by the except block. Normal program flow resumes right after the try-except construct rather than crashing the script.

def safe_divide(a, b):
    try:
        result = a / b
        print(f"Calculation success: {a} / {b} = {result}")
        return result
    except ZeroDivisionError as e:
        print(f"[RECOVERED] Cannot divide by zero: {e}")
        return None

print("Result 1:", safe_divide(20, 4))   # 5.0
print("Result 2:", safe_divide(20, 0))   # None (handled gracefully, program continues!)
print("Application continues running smoothly.")

L1 Fundamental

3.1. Python's Exception Class Hierarchy

All built-in exceptions in Python form a class inheritance tree. At the very root sits BaseException:

BaseException
 ├── BaseExceptionGroup
 ├── GeneratorExit
 ├── KeyboardInterrupt          (Ctrl+C from terminal)
 ├── SystemExit                 (sys.exit() calls)
 └── Exception                  (ROOT FOR ALL APPLICATION & USER EXCEPTIONS)
      ├── ArithmeticError
      │    ├── FloatingPointError
      │    ├── OverflowError
      │    └── ZeroDivisionError
      ├── AssertionError
      ├── AttributeError
      ├── BufferError
      ├── EOFError
      ├── ImportError
      │    └── ModuleNotFoundError
      ├── LookupError
      │    ├── IndexError
      │    └── KeyError
      ├── NameError
      │    └── UnboundLocalError
      ├── OSError
      │    ├── FileNotFoundError
      │    ├── PermissionError
      │    ├── ConnectionError
      │    └── TimeoutError
      ├── RuntimeError
      │    └── RecursionError
      ├── TypeError
      └── ValueError
           └── UnicodeError
The Golden Rule of Exception Handling: Never catch BaseException directly, and avoid bare except: blocks! Catching BaseException intercepts KeyboardInterrupt (preventing users from stopping your script with Ctrl+C) and SystemExit (preventing clean script termination via sys.exit()). Always catch Exception or, even better, specific exceptions!

L2 Intermediate

3.2. Specificity and Order of except Blocks

When multiple except blocks are provided, Python evaluates them in top-to-bottom order. The first matching block is executed. If a parent exception class is listed before a child exception class, the parent will catch the exception and the child block will never execute (dead code).

# Handling multiple specific exceptions
def parse_and_fetch(data_dict, key, divisor):
    try:
        val = data_dict[key]
        num = int(val)
        return 100 / num
    except KeyError as e:
        print(f"[ERROR] Missing required dictionary key: {e}")
    except ValueError as e:
        print(f"[ERROR] Value could not be parsed to integer: {e}")
    except ZeroDivisionError as e:
        print(f"[ERROR] Divisor evaluation resolved to zero: {e}")
    except Exception as e:
        # Fallback catch-all for any other unanticipated runtime error
        print(f"[UNEXPECTED ERROR] {type(e).__name__}: {e}")

data = {"score": "25", "zero": "0", "bad": "abc"}

print(parse_and_fetch(data, "score", 1))   # 4.0
print(parse_and_fetch(data, "missing", 1)) # Caught by KeyError
print(parse_and_fetch(data, "bad", 1))     # Caught by ValueError
print(parse_and_fetch(data, "zero", 1))    # Caught by ZeroDivisionError

# Grouping multiple exceptions in a single tuple:
def safe_cast(val):
    try:
        return int(val)
    except (TypeError, ValueError) as err:
        print(f"Conversion error: {err}")
        return 0

4. else and finally blocks

L1 L2

L1 Fundamental

4.1. The else Block

The else block in a try-except statement executes only if NO exception was raised in the try block. Placing code in the else block is much better practice than keeping it inside the try block because it prevents accidentally catching unintended exceptions from subsequent operations.

def read_user_age(user_input):
    try:
        age = int(user_input)
    except ValueError:
        print("Invalid input! Please enter digits only.")
    else:
        # Executes ONLY if int(user_input) succeeded without raising ValueError!
        print(f"Age successfully validated: {age}")
        category = "Adult" if age >= 18 else "Minor"
        print(f"Category: {category}")
        return age

read_user_age("28")    # try runs -> no error -> else runs!
read_user_age("twenty") # try runs -> ValueError -> except runs -> else skipped!

L2 Intermediate

4.2. The finally Block: Unconditional Cleanup

The finally block executes unconditionally under every circumstance: whether an exception occurred or not, whether it was caught or uncaught, and even if an early return, break, or continue statement was executed inside try, except, or else.

It is the designated place for releasing scarce system resources (e.g., closing file descriptors, releasing locks, terminating database connections, or tearing down network sockets).

def process_file_with_cleanup(filepath):
    f = None
    try:
        print(f"Opening file: {filepath}")
        f = open(filepath, "r")
        content = f.read()
        return len(content)
    except FileNotFoundError:
        print(f"[RECOVERY] File '{filepath}' not found!")
        return -1
    finally:
        # ALWAYS runs, even after 'return len(content)' or 'return -1'!
        print("Executing finally block...")
        if f is not None and not f.closed:
            f.close()
            print("File handle closed safely.")

# Testing missing file:
process_file_with_cleanup("non_existent_file.txt")
Gotcha: return in finally Overrides Everything: If a finally block explicitly executes a return statement, that return value will override any previous return or unhandled exception raised in try or except, effectively silencing errors! Avoid return in finally.

4.3. Comprehensive Control Flow Permutations

Scenario Execution Sequence Result / Exit State
1. No exception in try try → else → finally Normal completion; statements following the structure execute.
2. Exception in try matched by except try (up to failure) → except → finally Normal recovery; statements following the structure execute.
3. Exception in try NOT matched by any except try (up to failure) → finally Abnormal termination; unhandled exception propagates to caller.
4. Exception raised inside an except block try → except (up to failure) → finally Abnormal termination; new exception propagates out.
5. Early return inside try or else try → finally Caller receives return value after finally completes.
6. Early return inside finally try (or except) → finally Caller receives finally return; any previous return or unhandled exception is discarded!
7. os._exit(0) invoked Kernel terminates process immediately finally DOES NOT execute! (Contrast with sys.exit() which raises SystemExit, allowing cleanups).

5. Nested try-except-finally control flow

L1 L2

L1 Fundamental

5.1. Nested Try Blocks

You can nest a try-except-finally block inside another try, except, or finally block. If an exception is raised inside an inner try:

  1. The inner except blocks are inspected first.
  2. If an inner except handles it, the inner finally runs, and execution continues in the outer try.
  3. If no inner except matches, the inner finally runs, and the exception propagates up to the outer try's except blocks.
  4. Finally, the outer finally runs.
def complex_nested_flow(x, y, filename):
    try:
        print("1. Outer try starts")
        try:
            print("2. Inner try starts")
            division_result = x / y
            print(f"3. Division success: {division_result}")
        except ZeroDivisionError:
            print("4. Caught ZeroDivisionError in INNER except")
        finally:
            print("5. INNER finally always executes")

        print("6. Continuing in outer try...")
        # Now trigger an error that the outer try handles:
        with open(filename, "r") as f:
            data = f.read()

    except FileNotFoundError:
        print("7. Caught FileNotFoundError in OUTER except")
    finally:
        print("8. OUTER finally always executes")

print("--- Scenario A: Division by zero (handled by inner) ---")
complex_nested_flow(10, 0, "missing.txt")

6. Combinations of try/except/else/finally

L1 L2

L1 Fundamental

6.1. Valid Syntax Combinations

Combination Valid? Notes / Behavior
try ... except VALID Standard minimal handling. At least one except block.
try ... finally VALID Guarantees cleanup without catching the exception (exception re-propagates).
try ... except ... else VALID else runs only when try completes with zero exceptions.
try ... except ... finally VALID Handles error and guarantees cleanup.
try ... except ... else ... finally VALID Complete 4-clause statement. Strict order: try -> except -> else -> finally.
try alone INVALID SyntaxError: try must have at least one except or finally.
try ... else without except INVALID SyntaxError: else cannot exist without an except block.
try ... finally ... except INVALID SyntaxError: finally must always be the very last block.

7. Customized / user-defined exceptions

L1 L2

L1 Fundamental

7.1. Creating User-Defined Exceptions

In production systems, built-in exceptions like ValueError or KeyError are too generic to represent specific business domain errors. Python allows defining custom exceptions by subclassing Exception (never BaseException).

# Base domain exception:
class BankApplicationError(Exception):
    """Base exception for all banking domain errors."""
    pass

class InsufficientFundsError(BankApplicationError):
    """Raised when an account does not have enough balance for a withdrawal."""
    def __init__(self, account_id, balance, requested_amount):
        self.account_id = account_id
        self.balance = balance
        self.requested_amount = requested_amount
        message = (f"Account '{account_id}' has insufficient funds. "
                   f"Available: ${balance:.2f}, Requested: ${requested_amount:.2f}")
        super().__init__(message)

class AccountLockedError(BankApplicationError):
    """Raised when operating on a locked or frozen bank account."""
    pass

# Using custom exceptions in business logic:
def withdraw(account, amount):
    if account["is_locked"]:
        raise AccountLockedError(f"Account {account['id']} is locked due to security flags!")
    if amount > account["balance"]:
        raise InsufficientFundsError(account["id"], account["balance"], amount)
    
    account["balance"] -= amount
    return account["balance"]

my_account = {"id": "ACC-9982", "balance": 150.0, "is_locked": False}

try:
    withdraw(my_account, 500.0)
except InsufficientFundsError as err:
    print(f"[REJECTED] {err}")
    print(f"Shortfall: ${err.requested_amount - err.balance:.2f}")
except BankApplicationError as err:
    print(f"[GENERAL BANK ERROR] {err}")

L2 Intermediate

7.2. Exception Chaining with raise ... from

Introduced in PEP 3134, explicit exception chaining allows attaching the root cause exception to a new higher-level domain exception using raise NewException(...) from original_exc. This preserves the original traceback via the __cause__ attribute.

class DatabaseQueryError(Exception):
    """Raised when database query execution fails."""
    pass

def execute_user_query(sql):
    try:
        # Simulating low-level socket timeout
        raise ConnectionResetError("Remote server closed socket connection abruptly")
    except ConnectionResetError as socket_err:
        # Wrap low-level socket exception into high-level database error while preserving causality:
        raise DatabaseQueryError(f"Failed to execute query: '{sql}'") from socket_err

try:
    execute_user_query("SELECT * FROM users")
except DatabaseQueryError as query_err:
    print("[APPLICATION LEVEL]:", query_err)
    print("[ROOT CAUSE]:", repr(query_err.__cause__))

C. Common questions

L1 L2

L1 Fundamental

C.1. What is the difference between an Error and an Exception in Python? ▾ Answer

Syntax Errors (e.g. SyntaxError, IndentationError) occur at compile/parse time before the code starts executing. They cannot be handled using try-except blocks within the same module.

Exceptions occur at runtime during execution of syntactically valid code (e.g. ZeroDivisionError, FileNotFoundError). Exceptions disrupt normal control flow and can be intercepted, handled, and recovered from using try-except statements.

C.2. What is the difference between BaseException and Exception? ▾ Answer

BaseException is the absolute root class of all exceptions in Python. Its direct subclasses include system-exiting events: SystemExit, KeyboardInterrupt, GeneratorExit, and Exception.

Exception inherits from BaseException and is the intended base class for all non-system-exiting exceptions, including built-in runtime errors and user-defined custom exceptions.

Catching Exception allows catching all normal application errors while letting terminal signals like Ctrl+C (KeyboardInterrupt) and sys.exit() pass through unhindered.

C.3. Why is a bare except: or except BaseException: considered an anti-pattern? ▾ Answer

A bare except: catches every possible exception, including KeyboardInterrupt and SystemExit. This means:

  • The user cannot terminate an infinite loop or hanging script with Ctrl+C.
  • Calls to sys.exit() are silently intercepted and ignored.
  • Real programming bugs like NameError or TypeError are masked, making debugging painful.

Always catch specific exception types (e.g., except (ValueError, KeyError):) or at least except Exception:.

C.4. What is the purpose of the else clause in a try-except block? ▾ Answer

The else block executes only if the try block completes without raising any exceptions.

It helps keep the try block minimal (containing strictly the risky code) while isolating follow-up code that should only run upon success. This prevents accidentally catching and masking errors generated by the follow-up code.

L2 Intermediate

C.5. Under what circumstances will a finally block NOT execute? ▾ Answer

A finally block executes in nearly all scenarios, even during early returns or uncaught exceptions. However, it will NOT execute if:

  • The process is killed abruptly by the operating system kernel (e.g., SIGKILL / kill -9).
  • A direct OS-level exit is performed via os._exit(), which terminates the process without unwinding Python stack frames or executing cleanups.
  • The host machine loses power, crashes, or the Python C-runtime segfaults.
C.6. What happens if a finally block contains an explicit return statement? ▾ Answer

If a finally block executes a return statement, that return value silently discards and suppresses any exception that was currently being propagated from try or except, as well as overriding any previous return value from try or else.

def dangerous():
    try:
        raise ValueError("Critical error!")
    finally:
        return "Cleaned up!"  # Silences the ValueError completely!

This is extremely dangerous and considered a major anti-pattern.

C.7. How does exception chaining work with raise ... from ...? ▾ Answer

Python allows explicit exception chaining using raise NewException() from original_exc. This explicitly sets the __cause__ attribute on the new exception object.

In tracebacks, Python will clearly print: "The above exception was the direct cause of the following exception:". To explicitly suppress context chaining, use raise NewException() from None (which sets __suppress_context__ = True).

C.8. How should custom exceptions be designed in production software? ▾ Answer

Best practices for custom exceptions:

  • Create a base exception class for your library or domain (e.g. class ServiceError(Exception): pass).
  • Inherit specific errors from this base class (e.g. class ValidationError(ServiceError): pass).
  • Store relevant diagnostic state as instance attributes (e.g. self.status_code = 404, self.payload = payload).
  • Always call super().__init__(message) to ensure proper string formatting and representation.

    # Mini Project: Transactional Bank Transfer Engine
class BankingError(Exception):
    pass

class InsufficientBalanceError(BankingError):
    pass

class InvalidAccountError(BankingError):
    pass

def transfer_money(accounts, from_acc, to_acc, amount):
    if from_acc not in accounts:
        raise InvalidAccountError(f"Sender account '{from_acc}' not found!")
    if to_acc not in accounts:
        raise InvalidAccountError(f"Recipient account '{to_acc}' not found!")
    if accounts[from_acc] < amount:
        raise InsufficientBalanceError(f"Account '{from_acc}' has ${accounts[from_acc]}, needed ${amount}")

    # Transaction execution with rollback safety
    print(f"[TRANSACTION] Transferring ${amount} from {from_acc} to {to_acc}...")
    accounts[from_acc] -= amount
    try:
        # Simulate network or recipient failure
        if amount > 1000:
            raise ConnectionError("Payment gateway connection dropped")
        accounts[to_acc] += amount
    except Exception as exc:
        print("[ROLLBACK] An error occurred; rolling back sender funds!")
        accounts[from_acc] += amount  # Rollback
        raise BankingError("Transfer aborted and rolled back") from exc
    else:
        print("[SUCCESS] Transaction confirmed.")
    finally:
        print(f"[AUDIT] Sender balance: ${accounts[from_acc]}, Recipient: ${accounts[to_acc]}")

bank = {"Alice": 2000, "Bob": 500}
try:
    transfer_money(bank, "Alice", "Bob", 1500)
except BankingError as err:
    print("Caught:", err)
