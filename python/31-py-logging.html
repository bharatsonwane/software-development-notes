31. Logging

Severity levels, handlers, formatters, hierarchical loggers, exception tracking, and production log rotation.

1. Introduction

L1

L1 Fundamental

1.1. Why Logging Over print()?

In hobby scripts, developers frequently rely on print() to see what the code is doing. However, in production applications, microservices, and libraries, print() is completely inadequate because:

  • No Granular Levels: You cannot disable debug prints in production without manually deleting or commenting out code lines.
  • No Routing / Destinations: print() writes indiscriminately to standard output (sys.stdout). It cannot simultaneously write to rotating files, external syslog servers, or error alerts.
  • No Contextual Metadata: print() lacks timestamps, process IDs, thread names, module names, and line numbers unless manually constructed.
  • No Exception Tracebacks: Capturing stack traces and diagnostics with print() during an outage requires messy manual traceback formatting.

Python's built-in logging module provides a standardized, thread-safe, and highly configurable framework to track events, performance, and errors across applications.

2. Introduction, levels, and basic demo

L1 L2

L1 Fundamental

2.1. The 5 Standard Logging Levels

Events are categorized by severity. Each level corresponds to an integer value in the logging module:

Level Numeric Value When to Use
DEBUG 10 Detailed diagnostic information, typically of interest only when diagnosing problems.
INFO 20 Confirmation that things are working as expected (e.g. service startup, user login).
WARNING 30 An indication that something unexpected happened (e.g. disk low, retry), but software still functions. (DEFAULT LEVEL)
ERROR 40 Due to a more serious problem, the software has been unable to perform some function (e.g. database query failure).
CRITICAL 50 A serious error, indicating that the program itself may be unable to continue running (e.g. memory exhaustion, core dependency down).

L2 Intermediate

2.2. Basic Logging with basicConfig()

logging.basicConfig() configures the root logger with basic defaults (destination, format, and minimum severity threshold). Any log event with severity greater than or equal to the configured threshold will be emitted.

import logging

# Configure basic logging to console with INFO threshold:
logging.basicConfig(
    level=logging.INFO,
    format="%(levelname)s - %(message)s"
)

logging.debug("This is a DEBUG message (Will NOT be displayed because threshold is INFO)")
logging.info("Application worker started successfully.")
logging.warning("Cache hit ratio dropped below 70%.")
logging.error("Database query timed out after 5000ms.")
logging.critical("Payment gateway returned 503 Service Unavailable!")

3. Formatting messages; logging exceptions

L1 L2

L1 Fundamental

3.1. Standard LogRecord Attributes

When an event is logged, Python creates a LogRecord object containing rich contextual attributes that can be injected into the format string:

  • %(asctime)s: Human-readable timestamp when the LogRecord was created.
  • %(levelname)s: Text logging level for the message ('DEBUG', 'INFO', etc.).
  • %(name)s: Name of the logger used to log the call.
  • %(message)s: The logged message string itself.
  • %(filename)s: Filename portion of pathname where the logging call was made.
  • %(lineno)d: Source line number where the logging call was made.
  • %(threadName)s: Thread name (vital for multi-threaded debugging).
  • %(process)d: Process ID (PID).

L2 Intermediate

3.2. Logging Exceptions with Full Tracebacks

Inside an except block, calling logger.exception("message") automatically captures the active exception traceback and appends it to the log message (equivalent to logger.error("message", exc_info=True)).

import logging

logging.basicConfig(
    level=logging.ERROR,
    format="%(asctime)s [%(levelname)s] (%(filename)s:%(lineno)d): %(message)s"
)

def divide_numbers(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        # Automatically extracts exception and complete stack trace!
        logging.exception("Failed to compute division ratio:")
        return None

divide_numbers(10, 0)

4. Custom logger patterns

L1 L2

L1 Fundamental

4.1. The 4 Pillars of Python Logging Architecture

Component Class Responsibility
Logger logging.Logger The direct interface that application code invokes (e.g. logger.info()). Evaluates severity thresholds and passes LogRecords to Handlers.
Handler logging.Handler Sends LogRecords to target destinations (console, disk files, HTTP endpoints, email).
Formatter logging.Formatter Specifies the exact structure and layout of the final output string.
Filter logging.Filter Provides fine-grained control to allow or reject specific LogRecords based on custom criteria.

L2 Intermediate

4.2. Building a Custom Multi-Destination Logger

In production applications, you often want DEBUG messages to be saved to a file, while only WARNING and above appear on the console.

import logging
import sys

# 1. Create a custom logger:
logger = logging.getLogger("service_logger")
logger.setLevel(logging.DEBUG)  # Lowest threshold for the logger itself

# 2. Console Handler (WARNING and above to stderr):
console_handler = logging.StreamHandler(sys.stderr)
console_handler.setLevel(logging.WARNING)
console_format = logging.Formatter("[CONSOLE %(levelname)s] %(message)s")
console_handler.setFormatter(console_format)

# 3. File Handler (DEBUG and above to disk):
file_handler = logging.FileHandler("service_debug.log", mode="a")
file_handler.setLevel(logging.DEBUG)
file_format = logging.Formatter("%(asctime)s [%(levelname)s] %(name)s: %(message)s")
file_handler.setFormatter(file_format)

# 4. Attach handlers to logger:
logger.addHandler(console_handler)
logger.addHandler(file_handler)

# Testing:
logger.debug("Detailed debug info (written to file only)")
logger.warning("Warning message (written to BOTH file and console!)")

5. Per-module logs and inspect

L1 L2

L1 Fundamental

5.1. The Idiomatic Pattern: getLogger(__name__)

Always create loggers using logger = logging.getLogger(__name__) at the top of every module. Because __name__ reflects the module's hierarchical package path (e.g. auth.jwt.validator), Python automatically establishes a parent-child relationship between loggers.

# In auth/service.py:
import logging

logger = logging.getLogger(__name__)

def authenticate(username):
    logger.info("Authenticating user: %s", username)
    # Output name will be "auth.service"

L2 Intermediate

5.2. Logger Propagation and Preventing Duplicate Messages

By default, child loggers pass their LogRecords up to their parent loggers (all the way to root) via propagation (logger.propagate = True). If a child logger has its own handler attached AND propagates to a root logger that also has a handler, every message will be logged twice!

To avoid duplicate logs, either configure handlers exclusively on the root logger, or set logger.propagate = False on child loggers that manage their own handlers.

6. Generic logger and config file

L1 L2

L1 Fundamental

6.1. Production Log Rotation: RotatingFileHandler

If an application runs continuously, a single log file will grow indefinitely, eventually consuming all disk space. RotatingFileHandler automatically rotates log files when they reach a maximum size limit (maxBytes), maintaining a fixed number of backup archives (backupCount).

import logging
from logging.handlers import RotatingFileHandler

# Rotate when file hits 5 MB, keeping at most 3 backups:
rotating_handler = RotatingFileHandler(
    "app_service.log",
    maxBytes=5 * 1024 * 1024,  # 5 MB
    backupCount=3,
    encoding="utf-8"
)

formatter = logging.Formatter("%(asctime)s [%(levelname)s]: %(message)s")
rotating_handler.setFormatter(formatter)

app_logger = logging.getLogger("production_app")
app_logger.setLevel(logging.INFO)
app_logger.addHandler(rotating_handler)

L2 Intermediate

6.2. Dictionary-Based Configuration: dictConfig

In modern production Python (Django, FastAPI, Flask), logging is configured declaratively using logging.config.dictConfig() from a Python dictionary or YAML file.

import logging.config

LOGGING_CONFIG = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "standard": {
            "format": "%(asctime)s [%(levelname)s] %(name)s: %(message)s"
        },
        "json_style": {
            "format": '{"time": "%(asctime)s", "level": "%(levelname)s", "msg": "%(message)s"}'
        }
    },
    "handlers": {
        "console": {
            "class": "logging.StreamHandler",
            "level": "DEBUG",
            "formatter": "standard",
            "stream": "ext://sys.stdout"
        },
        "file": {
            "class": "logging.handlers.RotatingFileHandler",
            "level": "INFO",
            "formatter": "json_style",
            "filename": "server.log",
            "maxBytes": 10485760,  # 10 MB
            "backupCount": 5
        }
    },
    "root": {
        "level": "INFO",
        "handlers": ["console", "file"]
    }
}

logging.config.dictConfig(LOGGING_CONFIG)

prod_logger = logging.getLogger("api.orders")
prod_logger.info("Order service initialized successfully.")

C. Common questions

L1 L2

L1 Fundamental

C.1. Why should you use the logging module instead of print() in production? ▾ Answer

print() lacks severity categorization, outputs only to sys.stdout, lacks timestamps and thread context, cannot be turned off selectively without editing source code, and cannot rotate files when disk space fills up.

The logging module allows dynamically adjusting thresholds (e.g. INFO in production, DEBUG in staging) via configuration, sends outputs to multiple destinations simultaneously, captures stack traces automatically, and is thread-safe.

C.2. What are the standard logging levels, their numeric values, and the default level? ▾ Answer
  • DEBUG (10): Diagnostic details.
  • INFO (20): General operational milestones.
  • WARNING (30): Potential issues or unexpected states. (DEFAULT LEVEL)
  • ERROR (40): Serious failure in a specific function.
  • CRITICAL (50): Severe failure threatening the application process.
C.3. How do Loggers, Handlers, Formatters, and Filters collaborate? ▾ Answer

Application code calls a Logger (e.g. logger.info()). The Logger checks its minimum level; if satisfied, it packages the event into a LogRecord object. The Logger forwards this record to one or more Handlers. Each Handler determines if it accepts the record level, passes it through optional Filters, uses a Formatter to render the record into a formatted string, and writes it to the target destination (console, file, socket).

C.4. Why is logger = logging.getLogger(__name__) standard best practice? ▾ Answer

In Python, __name__ evaluates to the fully qualified module name (e.g. ecommerce.payments.stripe). Using __name__ establishes an intuitive logger hierarchy matching the project folder/module structure. This allows setting granular logging levels for specific packages or modules without modifying individual files.

L2 Intermediate

C.5. What is the difference between logger.error() and logger.exception()? ▾ Answer

logger.error("msg") logs an ERROR level message without an exception traceback unless explicitly passed exc_info=True.

logger.exception("msg") logs an ERROR level message and automatically captures and appends the active exception's full stack traceback from sys.exc_info(). It should only be called within an except block.

C.6. Why do duplicate log lines occur and how do you resolve them? ▾ Answer

Duplicate log entries happen when:

  1. A child logger has a handler attached, and logger.propagate = True causes the record to also bubble up to a parent or root logger that has its own handler attached. (Fix: set logger.propagate = False or configure handlers exclusively on root).
  2. Handlers are added repeatedly inside a function or loop without checking if handlers already exist (Fix: check if not logger.handlers: logger.addHandler(...)).
C.7. How does RotatingFileHandler work and why is it essential? ▾ Answer

RotatingFileHandler writes log entries to an active file until its size reaches maxBytes. When full, the active file is closed and renamed (e.g. app.log $\to$ app.log.1, app.log.1 $\to$ app.log.2), and a fresh app.log is created. If the number of backup archives exceeds backupCount, the oldest file is deleted. This guarantees that logs never exhaust the server's disk space.

C.8. Why should you pass format arguments as parameters instead of f-strings to log methods? ▾ Answer

Writing logger.debug(f"User data: {heavy_computation()}") evaluates the f-string immediately even if the logger's level is set to INFO, wasting CPU cycles.

Writing logger.debug("User data: %s", user_id) allows the logger to check if DEBUG is enabled first; if disabled, the string formatting operation is skipped entirely, saving significant CPU resources.

    # Edge Case: Preventing duplicate log output

root = logging.getLogger()
root.setLevel(logging.INFO)
root_h = logging.StreamHandler()
root.addHandler(root_h)
