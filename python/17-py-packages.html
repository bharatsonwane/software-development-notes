1. Introduction

L1

L1 Fundamental

1.1. Overview

  • While a Module is a single file (.py), a Package is a hierarchical folder structure that organizes multiple related modules and sub-packages under a common namespace.
  • Packages use dot-notation for module paths (e.g. import urllib.request, from sklearn.metrics import accuracy_score).
  • Packages prevent naming collisions across large software architectures and allow distribution on the Python Package Index (PyPI) via pip.

2. What is a package and advantages

L1 L2

L1 Fundamental

2.1. Anatomy of a Python Package

A package is structured as a directory tree containing modules and an __init__.py file:

ecommerce/                     # Root Package
├── __init__.py                # Package initialization
├── database.py                # Sibling module
├── payments/                  # Sub-package
│   ├── __init__.py
│   ├── stripe.py
│   └── paypal.py
└── shipping/                  # Sub-package
    ├── __init__.py
    ├── fedex.py
    └── tracking.py

L2 Intermediate

2.2. Absolute vs Relative Imports

  • Absolute Imports: Specify the full path from the project root or sys.path. Highly readable and recommended by PEP 8: 
    from ecommerce.payments.stripe import process_payment
from ecommerce.database import get_db_connection
  • Relative Imports: Use leading dots (.) to navigate relative to the current module's location:
    • . (single dot): Current package/directory.
    • .. (two dots): Parent package directory.
    # Inside ecommerce/payments/stripe.py:
from .paypal import verify_account    # Same directory
from ..database import execute_query  # Parent directory
Rule on Relative Imports: Relative imports rely on the module's __name__ attribute. If you run a file containing relative imports directly as the top-level script (python3 stripe.py), Python raises ImportError: attempted relative import with no known parent package. Run it from the root using module syntax: python3 -m ecommerce.payments.stripe.

2.3. Regular Packages vs Namespace Packages (PEP 420)

  • Regular Packages (Classic): Any directory containing an __init__.py file.
  • Namespace Packages (Python 3.3+, PEP 420): Directories without an __init__.py file. Allows splitting portions of a single logical package across different directories, virtual environments, or independent repositories (e.g. company.auth and company.billing).

3. Importance of __init__.py

L1 L2

L1 Fundamental

3.1. What Happens When a Package is Imported?

  • When someone executes import ecommerce, Python implicitly executes the code inside ecommerce/__init__.py.
  • It can be an empty file (used merely as a package marker), but in professional libraries, it serves as the package's public API gatekeeper.

L2 Intermediate

3.2. Curating a Clean Public API via __init__.py

Without an export in __init__.py, consumers must navigate deep nested module paths. By importing classes into __init__.py, you provide a clean, convenient interface:

# ecommerce/__init__.py
"""Public API for the eCommerce engine."""

# Elevate internal symbols to package root:
from .payments.stripe import StripeGateway
from .shipping.tracking import ShipmentTracker

# Expose package metadata:
__version__ = "2.4.0"
__author__ = "Bharat Sonwane"

# Control wildcard import:
__all__ = ["StripeGateway", "ShipmentTracker"]

Now consumers can simply write:

# Clean consumer code:
import ecommerce

gateway = ecommerce.StripeGateway()
print(f"eCommerce version: {ecommerce.__version__}")

4. Installing packages with pip

L1 L2

L1 Fundamental

4.1. Pip and the Python Package Index (PyPI)

  • PyPI (Python Package Index): The official third-party repository hosting hundreds of thousands of open-source packages (requests, numpy, flask, fastapi).
  • pip: The standard package installer for Python.
TaskCommandPurpose
Install package pip install requests Downloads and installs package and all dependencies.
Specific version pip install requests==2.31.0 Pins exact package version.
Upgrade package pip install --upgrade requests Upgrades to latest release.
Uninstall pip uninstall requests Removes package from environment.
Export dependencies pip freeze > requirements.txt Generates lockfile of exact installed versions.
Install dependencies pip install -r requirements.txt Reproduces exact environment from requirements file.

L2 Intermediate

4.2. Virtual Environments (venv)

Best Practice: Never install third-party packages into your global operating system Python environment! Doing so causes version conflicts between different projects and can corrupt OS tools. Always isolate dependencies inside a virtual environment: 
# 1. Create virtual environment named '.venv':
python3 -m venv .venv

# 2. Activate virtual environment:
# On macOS / Linux:
source .venv/bin/activate
# On Windows (cmd):
# .venv\Scripts\activate.bat

# 3. Verify Python points to virtual environment:
which python3   # Points to project/.venv/bin/python3

# 4. Install dependencies safely:
pip install fastapi uvicorn

# 5. Deactivate when finished:
deactivate

C. Common questions

L1 L2

L1 Fundamental

C.1. What is the fundamental difference between a Module and a Package? ▾ Answer
  • Module: A single file containing Python code ending in .py (or compiled C extensions .so / .pyd).
  • Package: A directory containing an __init__.py file (or a PEP 420 namespace directory) that groups multiple modules and sub-packages under a dot-separated hierarchy.
C.2. Is __init__.py strictly mandatory in Python 3? ▾ Answer

No, but recommended: Since Python 3.3 (PEP 420), directories without an __init__.py are recognized as Implicit Namespace Packages.

However, for traditional single-distribution application code, keeping __init__.py is still best practice because it explicitly identifies the folder as a regular package, prevents IDE resolution ambiguities, and provides an initialization hook.

C.3. Why does running a file with relative imports directly cause an ImportError? ▾ Answer

When you execute a file directly via python3 file.py, Python sets its __name__ = "__main__" and treats it as the top-level script with no enclosing package hierarchy. Relative imports (from . import helper) require knowing the package parent. Because __package__ is empty, Python raises ImportError: attempted relative import with no known parent package.

Solution: Run the package from the parent directory using the module flag: python3 -m mypkg.file.

C.4. What does pip freeze do and how does it relate to requirements.txt? ▾ Answer

pip freeze inspects the currently active Python environment and outputs every installed third-party package and its exact version in standard requirements format (package==version).

Redirecting this into requirements.txt creates a reproducible snapshot lockfile that other developers or CI/CD pipelines can install with pip install -r requirements.txt.

L2 Intermediate

C.5. What is a Wheel (.whl) file in Python packaging? ▾ Answer

A Wheel (PEP 427) is a ZIP-format archive with a .whl extension containing pre-built, ready-to-install package files. Unlike Source Distributions (.tar.gz / sdist) which require compiling C/C++ extensions during installation, wheels install in seconds without needing build tools or compilers on the target machine.

C.6. What is pyproject.toml and how does it replace setup.py? ▾ Answer

Introduced in PEP 518 and PEP 621, pyproject.toml is the modern, declarative configuration standard for Python projects. It replaces legacy setup.py, setup.cfg, and tool-specific config files, unifying build requirements (Hatch, Flit, Poetry, Setuptools), project metadata, and linter settings in a single file.

C.7. What happens if two packages have the same name in different sys.path directories? ▾ Answer

Python imports the package from whichever directory appears earlier in sys.path (First Match Wins). Once found, it is loaded into sys.modules and search terminates. This is why having a local file named math.py or random.py in your project directory accidentally shadows the standard library!

C.8. How do you create an editable install with pip? ▾ Answer

Running pip install -e . installs the package in Editable Mode (Development Mode). Instead of copying files to site-packages, pip links directly to your active project folder. Any code edits you make take effect immediately without needing to re-run pip install.

    import os

def create_package_scaffold(root_dir: str):
    structure = [
        os.path.join(root_dir, "mypackage", "__init__.py"),
        os.path.join(root_dir, "mypackage", "core.py"),
        os.path.join(root_dir, "mypackage", "utils", "__init__.py"),

    for filepath in structure:
        os.makedirs(os.path.dirname(filepath), exist_ok=True)

            with open(filepath, "w") as f:
                f.write(f"# Auto-generated: {os.path.basename(filepath)}\n")

  2. Task 2: Dependency Conflict Checker — Compare two requirements lists and highlight version discrepancies. ▾ Solution 
    def check_dependency_conflicts(req1: dict, req2: dict):
    conflicts = {}
    for pkg, ver1 in req1.items():
        if pkg in req2 and req2[pkg] != ver1:
            conflicts[pkg] = {"env1": ver1, "env2": req2[pkg]}
    return conflicts

service_a = {"requests": "2.31.0", "pydantic": "2.5.0", "click": "8.1.0"}
service_b = {"requests": "2.28.0", "pydantic": "2.5.0", "click": "8.0.0"}

conflicts = check_dependency_conflicts(service_a, service_b)
print("Detected version conflicts:", conflicts)
# Detected version conflicts: {'requests': {'env1': '2.31.0', 'env2': '2.28.0'}, 'click': {'env1': '8.1.0', 'env2': '8.0.0'}}
  3. Task 3: SemVer (Semantic Version) Validator — Validate if a version string matches MAJOR.MINOR.PATCH syntax. ▾ Solution 
    def is_valid_semver(v_str: str) -> bool:
    parts = v_str.split(".")
    if len(parts) != 3:
        return False
    return all(part.isdigit() and (len(part) == 1 or part[0] != "0") for part in parts)

test_versions = ["1.0.0", "2.14.3", "01.2.3", "3.4", "v1.2.3"]
for v in test_versions:
    print(f"{v:10} -> Valid SemVer: {is_valid_semver(v)}")
