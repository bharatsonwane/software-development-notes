1. Introduction

L1

L1 Fundamental

1.1. Overview

  • Production TypeScript is less about syntax and more about team habits — consistent strictness, lint rules, and a sensible migration path from JavaScript.

1.2. Default rules and how to study this file

  • Default rule today: enable strict when you can; prefer precise types over any.
  • After reading sections 2–5, complete P. Practical Assignment in 12-practice.ts or refactor a small JS module into TS. Review C. Common questions.

2. Avoiding any

L1 L2 L3

L1 Fundamental

  • any disables the type checker for that value and propagates unsafety:
// Bad — errors hidden until runtime
function parse(data: any) {
  return data.items.map((i: any) => i.name);
}

// Better — validate at boundary
function parse(data: unknown) {
  if (!isValidPayload(data)) {
    throw new Error("Invalid payload");
  }
  return data.items.map((i) => i.name);
}

2.1. Alternatives to any

Temporary migration// @ts-expect-error with ticket + deadline

3. Prefer interface vs type in teams

L1 L2

L1 Fundamental

  • There is no universal winner — consistency matters.

3.1. Practical convention

// Object shapes / class contracts
interface User {
  id: string;
  name: string;
}

// Unions, tuples, utilities
type Result<T> =
  | { ok: true; value: T }
  | { ok: false; error: Error };

type UserId = string;

L2 Intermediate

3.2. When interface wins

  • Public API objects you may extend later
  • Declaration merging (augmenting Express, Jest globals)
  • Class implements contracts

3.3. When type wins

  • Unions and intersections
  • Mapped / conditional types
  • Aliasing primitives and computed types
  • Document the team rule in README or ESLint — avoid bikeshedding per PR.

5. Migration from JavaScript

L1 L2 L3

L1 Fundamental

5.1. Rename strategy

app.js  →  app.ts
utils.js → utils.ts (one file at a time)
  • Enable gradual adoption:
{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": false,
    "strict": true
  }
}
  • Turn on "checkJs": true for .js files with // @ts-check at the top.

L2 Intermediate

5.2. Migration order

  1. Add tsconfig.json + typescript dev dependency
  2. Rename leaf modules first (no dependents)
  3. Add types at boundaries (API responses, config, shared models)
  4. Replace any introduced during migration
  5. Enable stricter flags incrementally (strictNullChecks, noImplicitAny)

5.3. jsdoc bridge

  • Before renaming, add JSDoc to .js:
/**
 * @param {string} name
 * @returns {string}
 */
export function greet(name) {
  return `Hello, ${name}`;
}
  • checkJs uses JSDoc as types — smooth stepping stone to .ts.

5.4. Do not rewrite everything at once

  • Migrate by feature or by folder. Mixed .js and .ts is normal for months in large apps.

L3 Advanced

5.5. Typing existing JS libraries

npm install -D @types/lodash
  • If no types exist:
// types/shims.d.ts
declare module "legacy-lib";
  • Or write accurate .d.ts for the subset you use.

L3 Advanced

5.6. Essential Production Flags Beyond Strict

  • Even with "strict": true, TypeScript allows certain unsafe runtime behaviors by default. Enable these two flags for maximum type safety:
{
  "compilerOptions": {
    // 1. Array out-of-bounds index safety:
    "noUncheckedIndexedAccess": true,

    // 2. Strict optional property assignment:
    "exactOptionalPropertyTypes": true
  }
}
  • noUncheckedIndexedAccess: By default, const first = items[0] is typed as string even if items is empty, causing runtime crashes! With this flag enabled, items[0] is accurately typed as string | undefined, requiring an existence check.
  • exactOptionalPropertyTypes: Forbids passing { key: undefined } to an optional property typed { key?: string } unless undefined is an explicit union member, preventing subtle JSON serialization bugs.

C. Common questions

L1 L2 L3

L1 Fundamental

C.1. Is any ever acceptable? ▾ Answer

During migration or with truly dynamic plugins — isolate it, document why, and plan removal.

C.2. Should strict mode be non-negotiable? ▾ Answer

For new projects, yes. Legacy projects enable flags incrementally.

C.3. Should tests be .ts too? ▾ Answer

Yes when the app is TS — tests get the same type safety and refactoring support.

L2 Intermediate

C.4. eslint vs tsc — which catches what? ▾ Answer

tsc — type correctness. ESLint — patterns, async misuse, style, some type-aware rules. Use both.

C.5. How long does JS → TS migration take? ▾ Answer

Depends on size. Leaf-first + boundaries-first often gives value in weeks, full strict coverage in months.

C.6. What is the single best habit for maintainable TS? ▾ Answer

Treat external data as unknown until validated — never trust JSON.parse, form input, or query params as typed.

L3 Advanced

C.7. @ts-ignore vs @ts-expect-error? ▾ Answer

Prefer @ts-expect-error — fails if the error is fixed, so you remove the comment. @ts-ignore silently stays.

C.8. Monorepo: one tsconfig or many? ▾ Answer

Per package with project references (File 09) — shared strict base config extended per package.

L1 Fundamental

P.1. Warm-up

  1. Replace three anys. ▾ Solution 
    // Replacing 'any' with concrete types and unknown:
// BAD: function process(data: any) { return data.title; }
// GOOD:
interface PostPayload {
  title: string;
  views: number;
}

function processPost(data: PostPayload): string {
  return `${data.title} (${data.views} views)`;
}

console.log(processPost({ title: "TypeScript Best Practices", views: 1200 }));
  2. interface vs type team rule comment. ▾ Solution 
    /*
Team Rule: interface vs type:
1. Use 'interface' for defining public object shapes, component props, and OOP class contracts (enables extends & declaration merging).
2. Use 'type' for unions ("A" | "B"), primitives, tuples, and mapped/conditional type utilities.
3. Be consistent: never mix interface and type arbitrarily for simple data objects.
*/
  3. TS ESLint command list. ▾ Solution 
    /*
TypeScript ESLint Setup Commands:
1. Install parser & plugin:
   npm install -D @typescript-eslint/parser @typescript-eslint/eslint-plugin eslint

2. Run linting:
   npx eslint . --ext .ts,.tsx

3. Enable recommended rules:
   "@typescript-eslint/recommended",
   "@typescript-eslint/no-explicit-any": "error",
   "@typescript-eslint/no-unused-vars": "warn"
*/

P.2. Core tasks

  1. unknown + validate JSON. ▾ Solution 
    // Safe JSON Parsing using 'unknown' and a type guard:
interface UserConfig {
  theme: "light" | "dark";
  retries: number;
}

function isUserConfig(obj: unknown): obj is UserConfig {
  return (
    typeof obj === "object" &&
    obj !== null &&
    ("theme" in obj && (obj.theme === "light" || obj.theme === "dark")) &&
    ("retries" in obj && typeof obj.retries === "number")
  );
}

function parseConfig(rawJson: string): UserConfig {
  const parsed: unknown = JSON.parse(rawJson);
  if (!isUserConfig(parsed)) {
    throw new Error("Invalid configuration JSON structure");
  }
  return parsed;
}

console.log(parseConfig('{"theme":"dark","retries":3}'));
  2. satisfies if available. ▾ Solution 
    // Using the 'satisfies' operator (TypeScript 4.9+):
type ThemeColors = "primary" | "secondary" | "accent";

// 'satisfies' validates that palette conforms to Record<ThemeColors, string>,
// while preserving the exact string literal types for autocomplete and methods!
const palette = {
  primary: "#2563eb",
  secondary: "#64748b",
  accent: "#10b981"
} satisfies Record<ThemeColors, string>;

console.log(palette.primary.toUpperCase()); // Safe string method access!
  3. migrate one .js plan. ▾ Solution 
    /*
JavaScript to TypeScript Migration Strategy:
1. Add tsconfig.json with "allowJs": true and "checkJs": false.
2. Rename utility / leaf files first (.js -> .ts) — start with pure helper functions.
3. Fix compiler errors by adding parameter types and interfaces.
4. Gradually turn on "strictNullChecks" and "noImplicitAny".
5. Finally, migrate complex UI components and core application entry points.
*/
  4. allowJs strategy comment. ▾ Solution 
    /*
allowJs Tradeoffs:
- Setting "allowJs": true allows legacy .js files to coexist alongside .ts files in the same project.
- Pros: Enables gradual, incremental adoption without requiring a 100% full-codebase rewrite on day one.
- Cons: Increases compiler overhead and may allow untyped edge cases to leak into typed files unless checkJs is turned on.
*/

L2 Intermediate

P.3. Challenge

  1. 10-line TS style guide. ▾ Solution 
    /*
10-Line TypeScript Style Guide:
1. Enable strict: true in tsconfig.json — never turn off strictNullChecks.
2. Ban 'any' — use 'unknown' when data structure is uncertain.
3. Use Type Guards and Discriminated Unions to narrow unknown data safely.
4. Let TypeScript infer local variables — do not over-annotate obvious types.
5. Prefer string literal unions ("user" | "admin") over numeric enums.
6. Use 'type' for unions/primitives, 'interface' for public API objects.
7. Use type-only imports (import type { T }) to prevent bundler circularity.
8. Treat external API and JSON responses as unknown until validated.
9. Avoid non-null assertions (!) unless 100% verified via invariants.
10. Leverage 'satisfies' to validate shapes while preserving exact literal types.
*/
  2. Typed callback with errors. ▾ Solution 
    // Typed Node.js-style Error-First Callback:
type NodeCallback<T> = (err: Error | null, result?: T) => void;

function readConfigAsync(path: string, callback: NodeCallback<string>) {
  if (!path) {
    callback(new Error("Path cannot be empty"));
    return;
  }
  callback(null, "config_data_loaded");
}

readConfigAsync("app.json", (err, result) => {
  if (err) {
    console.error("Failed:", err.message);
  } else {
    console.log("Success:", result);
  }
});
