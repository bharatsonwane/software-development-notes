08. Scope and Hoisting

Where names are visible, and what happens before a line runs.

Scope Scope chain Hoisting TDZ

1. Introduction

L1

L1 Fundamental

1.1. What are scope and hoisting?

  • Scope is the region where a variable name is visible. Hoisting is how JavaScript registers declarations before it runs a scope. Both matter more after you know functions (File 05), because functions create scope and function declarations hoist differently from const/let/var (File 01).

1.2. Default rules and how to study this file

Default rule today: prefer block scope (const/let), declare before use, and do not rely on var hoisting.
  • Interactive visualizer: open 08-js-scope-hoisting-animation.html in a browser — TDZ, var hoisting, block vs function scope, scope chain, shadowing (Run / Step).
  • After reading sections 2–3, complete P. Practical Assignment in 08-practice.js before File 09. Review C. Common questions.

2. Scope

L1 L2

L1 Fundamental

  • Scope is the region where a variable name is visible and accessible. JavaScript uses lexical (static) scope — a function "sees" variables from the scopes where it was written, not where it is called.

2.1. Global scope

  • Variables declared outside any function or block live in the global scope. In browsers, global bindings become properties of window (with exceptions for const/let).
const appName = "MyApp";   // global (script/module top level)

function showName() {
  console.log(appName);    // can access global
}

2.2. Function scope

  • var and function declarations are scoped to the nearest function:
function demo() {
  var x = 1;
  if (true) {
    var x = 2;   // same x — still function-scoped
  }
  console.log(x);  // 2
}

2.3. Block scope

  • const and let are scoped to the nearest block ({ ... }) — including if, for, while, and standalone blocks:
if (true) {
  let blockScoped = 10;
  const alsoBlock = 20;
}
// blockScoped, alsoBlock — ReferenceError outside the block
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);  // 0, 1, 2 — new i each iteration
}

for (var j = 0; j < 3; j++) {
  setTimeout(() => console.log(j), 0);  // 3, 3, 3 — one shared j
}
  • setTimeout is File 07. This example is about scope of i/j, not how timers work.

L1 Fundamental

2.4. Variable shadowing

  • An inner scope can declare the same name as an outer scope, hiding the outer variable:
let value = "outer";

function test() {
  let value = "inner";   // shadows outer `value`
  console.log(value);    // "inner"
}

test();
console.log(value);      // "outer"
  • Illegal Shadowing Mechanics: While an inner block's let or const can cleanly shadow an outer let or var, you cannot declare a var inside an inner block with the same name as an outer let:
let outerVal = 10;
{
  let outerVal = 20;  // OK — new block declarative scope, shadows cleanly
}

let y = 100;
{
  // var y = 200;     // SyntaxError: Identifier 'y' has already been declared!
}
// Why? 'var' ignores block boundaries and hoists directly to the parent
// function/global scope, attempting to register 'y' in the same environment
// where 'let y' already exists!

L2 Intermediate

2.5. Scope chain

  • When code reads a variable, JS walks outward through nested scopes until it finds a binding. If none is found (in non-strict sloppy mode for assignments), it may create a global.
const outer = "global";

function outerFn() {
  const middle = "middle";

  function innerFn() {
    const inner = "inner";
    console.log(inner);   // "inner"  — own scope
    console.log(middle);  // "middle" — parent scope
    console.log(outer);   // "global" — outer scope
  }

  innerFn();
}

2.6. Strict mode and accidental globals

  • Without "use strict", assigning to an undeclared name creates a global property:
function oops() {
  mystery = 42;   // creates global `mystery` (avoid!)
}
  • In strict mode, that throws ReferenceError:
"use strict";
function safe() {
  mystery = 42;   // ReferenceError
}
Always declare with const/let/var — never rely on implicit globals.

3. Hoisting

L1 L2

L1 Fundamental

  • Hoisting is JS moving declarations to the top of their scope during the compile phase. It does not move assignments or initializations.
  • Think of it in two steps:
  1. Create bindings (names registered in scope).
  2. Run the code line by line (assign values).

3.1. var hoisting

  • var declarations are hoisted and initialized to undefined:
console.log(a);  // undefined — declared, not yet assigned
var a = 10;
console.log(a);  // 10
  • Conceptually similar to:
var a;             // hoisted declaration
console.log(a);    // undefined
a = 10;

3.2. Function declaration hoisting

  • Function declarations are fully hoisted — you can call them before the line they appear on:
greet();  // "hi" — works

function greet() {
  console.log("hi");
}

L1 Fundamental

3.3. Function expression hoisting

  • Function expressions follow variable hoisting rules (const/let → TDZ, var → undefined):
// sayHi();  // TypeError — sayHi is undefined (var hoisted, not the function)

var sayHi = function () {
  console.log("hi");
};
// greet();  // ReferenceError — TDZ

const greet = function () {
  console.log("hello");
};

L2 Intermediate

3.5. const and let hoisting

  • const and let are also hoisted, but stay in the TDZ until their declaration line:
// console.log(b);  // ReferenceError — TDZ
let b = 2;

3.6. Class declarations

  • class declarations are hoisted but not initialized until their line — same TDZ behavior as const/let:
// const c = new Person();  // ReferenceError

class Person {}

3.7. Hoisting order (same scope)

  • When names collide in one scope, function declarations take precedence over var:
console.log(typeof fn);  // "function"

var fn = "string";

function fn() {
  return "fn";
}
  • After all lines run, fn is the string "string" because the assignment wins at runtime — but the initial hoisted binding was the function. This pattern is confusing; avoid mixing var and function declarations with the same name.
  • Duplicate Function Declarations: If multiple function declarations share the same identifier in the same scope, the last declaration in code order wins during hoisting and overwrites previous ones.
sayHello(); // logs "Second hello!"

function sayHello() {
  console.log("First hello!");
}

function sayHello() {
  console.log("Second hello!"); // Overwrites previous declaration during compilation!
}
  • ES Module import Hoisting: Static import statements are hoisted to the absolute top of the module before any code evaluates. Regardless of where import appears in the file, dependencies are loaded and linked during the module initialization phase before synchronous code runs.

C. Common questions

L1 L2

L1 Fundamental

C.1. What is lexical scope? ▾ Answer

Scope is determined by where code is written in the source, not by the call stack at runtime. Inner functions can read outer variables; that outer lookup chain is the scope chain.

L1 Fundamental

C.2. Does hoisting move code physically to the top? ▾ Answer

No. It is a mental model. During compilation, JS registers declarations in scope first; then it executes the code top to bottom. Assignments and initializations stay on their original lines.

L2 Intermediate

C.3. Why does for (var i = 0; ...) break closures in loops? ▾ Answer

var is function-scoped, so there is one i shared by all iterations. let creates a new binding per iteration, which is what you want with async callbacks.

C.4. Are function declarations hoisted above var? ▾ Answer

In the same scope, the function declaration wins during the initial hoisting phase. If you later assign to the same name with const/let/var, that assignment overwrites it at runtime.

C.5. What is the Temporal Dead Zone? ▾ Answer

The period between entering a scope and executing the const/let declaration line. The binding exists but accessing it throws ReferenceError. File 01 introduces TDZ with const/let; this file shows how it fits the hoisting model.

  1. Create a global const city, a function that shadows it with a local city, and log both from inside and outside. ▾ Solution 
    const city = "Pune";

function showCity() {
  const city = "Mumbai"; // Shadows the outer 'city'
  console.log("Inner local city:", city); // Mumbai

showCity();
console.log("Outer global city:", city); // Pune
  2. Inside a block { }, declare let x and try to log x outside — note the error. ▾ Solution 
    {
  let x = 42;
  console.log("Inside block:", x); // 42
}

try {
  console.log(x); // ReferenceError: x is not defined outside the block
} catch (err) {
  console.log("Caught outside block:", err.message);
}
  3. Show var leaking out of a block vs let staying inside. ▾ Solution 
    {
  var leakedVar = "I leak out of blocks";
  let trappedLet = "I stay inside";
}

console.log("var access outside block:", leakedVar); // Works!
try {
  console.log(trappedLet);
} catch (err) {
  console.log("let access outside block:", err.message); // ReferenceError
}

P.2. Core tasks

  1. Scope chain — Nested functions outer → middle → inner where each level has a variable; innermost logs all three via the chain. ▾ Solution 
    const globalVar = "global";

function outer() {
  const outerVar = "outer";

  function middle() {
    const middleVar = "middle";

    function inner() {
      const innerVar = "inner";
      // Accessing all variables up the scope chain:
      console.log(`${innerVar} -> ${middleVar} -> ${outerVar} -> ${globalVar}`);
    }

    inner();
  }

  middle();
}

outer(); // "inner -> middle -> outer -> global"
  2. TDZ demo — In a block, log a let before its declaration (catch the error), then fix the order. ▾ Solution 
    {
  // TDZ (Temporal Dead Zone) window starts here for 'data'
  try {
    // Accessing before initialization throws ReferenceError
    // console.log(data);
    eval("console.log(data)");
  } catch (err) {
    console.log("TDZ Error:", err.message); // Cannot access 'data' before initialization
  }

  let data = "Initialized now!";
  console.log(data); // Works safely after declaration
}
  3. var vs let in loops — Create an array of 3 functions with for (var i = 0; i < 3; i++) that each log i; call them after the loop. Repeat with let. Explain the difference. ▾ Solution 
    // var: all functions share the same hoisted binding
const varFuncs = [];
for (var i = 0; i < 3; i++) {
  varFuncs.push(() => i);
}
console.log("var loop:", varFuncs.map(fn => fn())); // [3, 3, 3]

// let: creates a fresh binding per iteration
const letFuncs = [];
for (let j = 0; j < 3; j++) {
  letFuncs.push(() => j);
}
console.log("let loop:", letFuncs.map(fn => fn())); // [0, 1, 2]
  4. Hoisting quiz — Without looking, write what this prints, then run it: a function declaration call before its line; a const arrow assigned after a call attempt. ▾ Solution 
    // Hoisting demonstration:
console.log("1. Function call before declaration:", add(2, 3)); // 5 (fully hoisted)
console.log("2. var before assignment:", myVar);                // undefined (declaration hoisted, initialized to undefined)

function add(a, b) {
  return a + b;
}

var myVar = "Hello World";
console.log("3. var after assignment:", myVar);                 // "Hello World"

P.3. Challenge

  1. Accidental global — In a function (non-strict if needed), assign oops = 1 without declaring; log typeof oops outside. Then rewrite with "use strict" and show the ReferenceError. ▾ Solution 
    function createAccidentalGlobal() {
  // In non-strict mode, assigning without declaration attaches to global/window

  2. Shadow map — Draw (as comments) the scope chain for a short nested snippet you invent with 2 shadows of the same name. ▾ Solution 
    /*
Scope Chain Hierarchy:
[Global Scope]
  ├── window / globalThis
  └── a = 1
       └── [outer Scope]
             ├── a = 10 (shadows global a)
             └── b = 20
                  └── [inner Scope]
                        ├── b = 200 (shadows outer b)
                        └── c = 300
*/

const a = 1;
function outerScope() {
  const a = 10; // Shadows global a
  const b = 20;

  function innerScope() {
    const b = 200; // Shadows outer b
    const c = 300;
    console.log({ a, b, c }); // a: 10 (from outer), b: 200 (from inner), c: 300 (from inner)
  }

  innerScope();
}

outerScope();
