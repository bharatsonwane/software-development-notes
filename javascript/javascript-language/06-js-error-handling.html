1.1. What is error handling?

  • Error handling is how you detect failures, stop bad paths with throw, and recover with try/catch/finally.
  • Builds on control flow (File 04) and functions (File 05). Async errors are File 21. Custom class extends Error uses class syntax from File 19.

2. Error handling

L1 L2 L3

L1 Fundamental

2.1. try / catch / finally

try {
  const data = JSON.parse(maybeInvalidJson);
  process(data);
} catch (err) {
  console.error("Parse failed:", err.message);
} finally {
  console.log("Always runs — cleanup");
}
  • finally runs whether try succeeded or catch ran — useful for closing resources.

2.2. throw

function divide(a, b) {
  if (b === 0) throw new Error("Division by zero");
  return a / b;
}
  • Throw Error objects, not raw strings — preserves stack trace.

L1 Fundamental

2.3. Custom errors

class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

function saveUser(user) {
  if (!user.email) throw new ValidationError("Email required", "email");
}
  • Async errors use try/catch with await or .catch() on Promises (File 21). The class ... extends Error form is File 19.

L2 Intermediate

2.4. Error object and types

try {
  null.foo;
} catch (err) {
  err instanceof TypeError;      // true
  err instanceof ReferenceError;
  err.name;                      // "TypeError"
  err.message;
  err.stack;                     // stack trace string
}
  • Built-in types: Error, TypeError, ReferenceError, SyntaxError, RangeError, AggregateError (several errors in one — used by Promise.any, File 21).

2.5. Optional catch binding

try {
  JSON.parse(text);
} catch {
  return fallback;  // no unused err binding
}

2.6. Error.cause

  • Chain the original error when you wrap it — keeps the stack of the inner failure:
try {
  await saveUser(user);
} catch (err) {
  throw new Error("Could not save user", { cause: err });
}

// later
outer.cause;           // original error
outer.cause.message;
  • Error.isError(value) (ES2024+) — true for Error instances across realms; prefer over instanceof Error when values might cross iframes/workers.
Error.isError(new TypeError("x"));  // true
Error.isError({ message: "x" });     // false

2.7. AggregateError

try {
  await Promise.any([
    Promise.reject(new Error("a")),
    Promise.reject(new Error("b")),
  ]);
} catch (err) {
  err instanceof AggregateError;  // true — all rejected
  err.errors;                     // [Error a, Error b]
}

L3 Advanced

2.8. Errors the catch block never sees

  • Promise rejections with no .catch / no surrounding async try:
window.addEventListener("unhandledrejection", (e) => {
  console.error("Unhandled:", e.reason);
  e.preventDefault();  // optional — stops default console noise
});
  • Sync exceptions that escape all try/catch (browser):
window.addEventListener("error", (e) => {
  console.error(e.message, e.filename, e.lineno);
});
  • Node: process.on("unhandledRejection") / uncaughtException — log and usually exit; do not “swallow” and keep running.

C. Common questions

L1 L2 L3

L1 Fundamental

C.1. What is the difference between throw and return?

  • A: throw signals exceptional failure — jumps to nearest catch. return exits normally with a value.

L1 Fundamental

C.2. Should I throw strings or Error objects?

  • A: Error objects (or subclasses) — better debugging with .stack.

C.3. How do Promises handle errors vs try/catch?

  • A: async/await uses try/catch. Promises use .catch() or second argument to .then() (File 21).

L2 Intermediate

C.4. Does finally run if try returns?

  • A: Yes — finally runs before the return completes.

C.5. Why use Error.cause?

  • A: To wrap a low-level error in a user-facing one without losing the original stack. Read err.cause when logging.

L3 Advanced

C.6. Does try/catch catch unhandled Promise rejections?

  • A: No unless you await that Promise (or call .catch). Use unhandledrejection as a last-resort logger, not as normal control flow.

P. Practical Assignment

L1 L2
Write complete scripts. Prefer throw new Error(...) over throwing strings. Use console.log / console.error to verify paths.

L1 Fundamental

P.1. Warm-up

  1. Wrap JSON.parse('{ bad') in try/catch and log err.message.
  2. Write divide(a, b) that throws if b === 0, then call it safely with try/catch.
  3. Add a finally that always logs "done".

P.2. Core tasks

  1. safeParse(json) — Return the parsed value, or null if parsing fails. Never throw to the caller.
  2. assertPositive(n) — Throw new Error if n is not a number > 0. Call it from a small calculator function.
  3. Custom ValidationError — Create class ValidationError extends Error {} (or a function that returns an Error with name = "ValidationError"). Throw it for empty string input; catch and check err.name.
  4. finally return demo — In try, return 1; in finally log "cleanup". Confirm cleanup runs.

L2 Intermediate

P.3. Challenge

  1. Error.cause chain — Catch a low-level error from JSON.parse, rethrow new Error("Config load failed", { cause: err }), then log err.message and err.cause.message.
  2. AggregateError sketch — Collect two failures in an array and throw new AggregateError(errors, "batch failed"); catch and log err.errors.length.

P.4. Self-check

  • I know finally runs even when try returns or catch rethrows.
  • I throw Error objects, not bare strings.
  • I understand try/catch does not catch unhandled Promise rejections unless I await.
