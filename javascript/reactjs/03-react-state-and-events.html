03. State & Events

File 03 — useState, events, lifting state up, one-way data flow.

1. Introduction

L1

L1 Fundamental

1.1. Overview

  • State lets components remember and update data over time. Events let users interact with the UI. React combines them with one-way data flow: data moves down via props; changes move up via callback props.
  • File 01 introduced useState briefly. This chapter goes deeper on updating state correctly, handling events, and lifting state to a common parent.
  • Default rule today: treat state as immutable (copy, don't mutate); use functional updates when the next value depends on the previous; lift state to the lowest common ancestor of components that need it.

1.2. Default rules and how to study this file

  • Default rule today: prefer function components and hooks; keep components small; colocate state with the UI that needs it.
  • After reading sections 2–6, complete P. Practical Assignment in 03-practice.jsx before File 04. Review C. Common questions.

2. useState in depth

L1 L2

L1 Fundamental

2.1. State and re-renders

  • When you call a state setter, React:
  1. Schedules a re-render of that component.
  2. Runs the component function again with the new state.
  3. Updates the DOM where output changed (reconciliation).
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  console.log("render", count);

  return (
    <button onClick={() => setCount(count + 1)}>
      Count: {count}
    </button>
  );
}
  • Each click logs a new render with an incremented count.

L1 Fundamental

2.2. Initial state and lazy initialization

const [count, setCount] = useState(0);
const [user, setUser] = useState({ name: "", age: 0 });
  • Expensive initial value — pass a function so it runs only once:
function ExpensiveInit() {
  const [data, setData] = useState(() => {
    return computeHeavyInitialValue();
  });
}
  • Without the function, computeHeavyInitialValue() would run on every render.

2.3. Object and array state (immutability)

  • Do not mutate state objects or arrays — replace with a new copy:
const [user, setUser] = useState({ name: "Bharat", age: 30 });

// Bad — mutates same object
// user.age = 31;
// setUser(user);

// Good — new object
setUser({ ...user, age: 31 });
  • Arrays:
const [items, setItems] = useState(["a", "b"]);

setItems([...items, "c"]);           // add
setItems(items.filter((x) => x !== "a"));  // remove
setItems(items.map((x) => x === "b" ? "B" : x));  // update one
  • Same idea as JavaScript immutability (File 12) — React compares by reference for change detection.

2.4. Multiple state variables

  • Split unrelated state — easier to reason about:
function Form() {
  const [name, setName] = useState("");
  const [email, setEmail] = useState("");
  const [agreed, setAgreed] = useState(false);
}
  • Combine into one object when fields always update together (File 06 — forms):
const [form, setForm] = useState({ name: "", email: "" });

setForm((prev) => ({ ...prev, name: "Bharat" }));

L2 Intermediate

2.5. Functional updates

  • When the next state depends on the previous state, use the updater form:
setCount((prev) => prev + 1);
setCount((prev) => prev + 1);  // safe when batched — both see correct prev
  • Avoid stale closures in async handlers:
// Risky if multiple updates batch
setCount(count + 1);

// Safer
setCount((prev) => prev + 1);

2.6. React 18 Automatic Batching & flushSync

  • What is Batching? When multiple state updates occur, React groups them into a single re-render pass instead of re-rendering the component after every single setter call.
  • Legacy Behavior (React 17 and earlier):
    • Updates inside React event handlers were batched.
    • Updates inside setTimeout, promises, or native event listeners were NOT batched (e.g. 2 updates caused 2 distinct renders).
  • Modern Automatic Batching (React 18+):

    React 18 batches all state updates by default, regardless of where they originate:

    // In React 18: Only ONE re-render happens across async boundaries
fetch('/api/user').then(() => {
  setCount(c => c + 1);
  setUser(newUserData);
  setIsLoading(false);
  // React 18 queues all 3 updates and performs 1 single render pass!
});
  • Opting Out with flushSync:

    If you need the DOM to update synchronously immediately (for instance, to measure a DOM node right after updating state), use flushSync from react-dom:

    import { flushSync } from 'react-dom';

function handleScrollToBottom() {
  flushSync(() => {
    setMessages(prev => [...prev, newMessage]);
  });
  // DOM is updated synchronously here:
  chatEndRef.current.scrollIntoView({ behavior: 'smooth' });
}

2.7. State as a Snapshot & Stale Closure Mechanics

  • Render Frame Snapshot: State in React is not a mutable variable you read in real-time. Within a single render execution, state is a fixed constant snapshot:
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count); // Still logs 0! Not 1.
    setCount(count + 1);
    // React queues: nextCount = 0 + 1. The result after re-render is 1, not 2!
  }
}
  • Why this occurs: The count variable inside handleClick was closed over when the component rendered with count = 0. Calling setCount schedules a future render with the new value; it does NOT mutate the local constant count in the currently executing stack frame.
  • Solution: Functional Updates: Passing an updater function (setCount(prev => prev + 1)) queues an operation on the pending state queue rather than evaluating a stale local variable.

3. Events in React

L1

L1 Fundamental

3.1. Synthetic Events & Root Container Delegation

  • SyntheticEvent: React wraps native browser DOM events in a cross-browser SyntheticEvent wrapper that normalizes event attributes across different browser engines.
  • No More Event Pooling (React 17+): In legacy React (≤16), synthetic events were reused across clicks and pooled for performance; event fields were nullified synchronously, requiring e.persist(). In React 17, 18, and 19, event pooling is completely removed. You can freely read e.target.value inside asynchronous functions, setTimeout, or promises without errors.
  • Root Container Delegation:
    • In legacy React (≤16), React attached all listeners to the document object.
    • In modern React (17+), React attaches event listeners directly to the root DOM container element where createRoot(container) was mounted (e.g. #root).
    • This prevents event conflicts in micro-frontend architectures where multiple React apps, or React and non-React widgets, coexist on the same page.
function Button() {
  function handleClick(event) {
    console.log(event.type);   // "click"
    console.log(event.target); // DOM element

    // Safe in React 17+ (No event pooling / nullification):
    setTimeout(() => {
      console.log("Async target:", event.target.tagName);
    }, 100);
  }

  return <button onClick={handleClick}>Click</button>;
}
  • Use camelCase event names: onClick, onChange, onSubmit, onKeyDown.

L1 Fundamental

3.2. Common handlers

  • Click:
<button onClick={() => console.log("clicked")}>Go</button>
  • Input change:
function SearchBox() {
  const [query, setQuery] = useState("");

  return (
    <input
      value={query}
      onChange={(e) => setQuery(e.target.value)}
      placeholder="Search..."
    />
  );
}
  • Form submit:
function LoginForm() {
  function handleSubmit(e) {
    e.preventDefault();  // don't full-page reload
    console.log("submit");
  }

  return (
    <form onSubmit={handleSubmit}>
      <button type="submit">Log in</button>
    </form>
  );
}
  • Full forms in File 06.

3.3. Passing arguments to handlers

function ItemList({ items }) {
  function handleDelete(id) {
    console.log("delete", id);
  }

  return items.map((item) => (
    <button key={item.id} onClick={() => handleDelete(item.id)}>
      Delete {item.name}
    </button>
  ));
}
  • Wrap in arrow function — onClick={handleDelete(item.id)} would call immediately on render.

3.4. preventDefault and stopPropagation

function Link({ href, onNavigate }) {
  function handleClick(e) {
    e.preventDefault();        // cancel default anchor navigation
    onNavigate(href);
  }

  return <a href={href} onClick={handleClick}>Go</a>;
}
function handleInnerClick(e) {
  e.stopPropagation();  // don't bubble to parent handlers
}

3.5. Native DOM vs Synthetic Event Bubbling

  • Propagation Order:
    1. When a user clicks an element, the browser triggers native capture down the DOM to the target element.
    2. Native bubbling travels back up through ancestors. If any ancestor has a native listener (addEventListener('click', ...)), it triggers during this native phase.
    3. When the event bubbles to the root container (#root), React's SyntheticEvent listener intercepts it and simulates synthetic bubbling up the virtual component tree.
  • Crucial Caveat with stopPropagation: React's e.stopPropagation() stops propagation through the React virtual tree. It does not stop native listeners attached directly to the element or its parent DOM nodes that fired prior to reaching the React root container.

4. One-way data flow

L1 L2

L1 Fundamental

4.1. Data down, events up

  • Parent owns state; child receives props and callbacks:
function Parent() {
  const [text, setText] = useState("");

  return (
    <Child
      value={text}
      onChange={setText}
    />
  );
}

function Child({ value, onChange }) {
  return (
    <input
      value={value}
      onChange={(e) => onChange(e.target.value)}
    />
  );
}
  • Down: value={text}
  • Up: onChange calls parent's setText
  • Child does not own the text state — parent does (controlled pattern, File 06).

L1 Fundamental

4.2. Controlled vs uncontrolled (preview)

4.3. Unidirectional flow benefits

  • Easier to trace bugs — state lives in one place.
  • Predictable UI — render is a function of state.
  • Siblings stay in sync when they share parent state.

5. Lifting state up

L1 L2

L1 Fundamental

  • When two or more components need the same state, move it to their closest common parent.

5.1. Problem: siblings need shared data

// Won't stay in sync — separate state each
function BrokenApp() {
  return (
    <>
      <TemperatureInput scale="c" />
      <TemperatureInput scale="f" />
    </>
  );
}
  • Each TemperatureInput would keep its own temperature.

L1 Fundamental

5.2. Solution: lift to parent

function App() {
  const [temperature, setTemperature] = useState("");
  const [scale, setScale] = useState("c");

  return (
    <>
      <TemperatureInput
        scale="c"
        temperature={scale === "c" ? temperature : toCelsius(temperature, scale)}
        onTemperatureChange={setTemperature}
      />
      <TemperatureInput
        scale="f"
        temperature={scale === "f" ? temperature : toFahrenheit(temperature, scale)}
        onTemperatureChange={setTemperature}
      />
      <BoilingVerdict celsius={parseFloat(temperature)} />
    </>
  );
}

function TemperatureInput({ scale, temperature, onTemperatureChange }) {
  return (
    <fieldset>
      <legend>Enter temperature in {scale.toUpperCase()}:</legend>
      <input
        value={temperature}
        onChange={(e) => onTemperatureChange(e.target.value)}
      />
    </fieldset>
  );
}

function BoilingVerdict({ celsius }) {
  if (celsius >= 100) return <p>Water boils.</p>;
  return <p>Water does not boil.</p>;
}
  • Parent holds single source of truth; children are controlled.

5.3. Lifting callback-only state

  • Child triggers action; parent updates list:
function TodoApp() {
  const [todos, setTodos] = useState([]);

  function addTodo(text) {
    setTodos((prev) => [...prev, { id: Date.now(), text, done: false }]);
  }

  function toggleTodo(id) {
    setTodos((prev) =>
      prev.map((t) => (t.id === id ? { ...t, done: !t.done } : t))
    );
  }

  return (
    <>
      <TodoInput onAdd={addTodo} />
      <TodoList todos={todos} onToggle={toggleTodo} />
    </>
  );
}
  • List rendering details in File 04.

L2 Intermediate

5.4. How far to lift

  • Lift to the lowest ancestor that:
  • Needs the state for its own render, or
  • Has both children that need read/write access.
  • Lift too high → prop drilling (File 02, File 08). Keep state local when only one component cares.

6. State design basics

L2

L2 Intermediate

6.1. Single source of truth

  • Avoid duplicating the same fact in two state variables:
// Bad — name and fullName can drift
const [first, setFirst] = useState("");
const [last, setLast] = useState("");
const [fullName, setFullName] = useState("");

// Good — derive during render
const fullName = `${first} ${last}`.trim();
  • Derived values — compute from state/props in render; don't store unless expensive (File 12 — useMemo).

6.2. Minimal state

  • Ask: "What is the minimum state needed?" Remove anything computable:
const [items, setItems] = useState([]);
const [filter, setFilter] = useState("");

const visibleItems = items.filter((item) =>
  item.name.toLowerCase().includes(filter.toLowerCase())
);
// visibleItems is derived — not separate useState

6.3. State structure

PreferAvoid
Flat, normalized lists (id keys)Deeply nested duplicate objects
Separate booleans for independent flagsOne big `status: "loading" \
Lift shared stateCopy same data into sibling state
  • Complex global state → File 08, File 11.

C. Common questions

L1 L2

L1 Fundamental

C.1. What is lifting state up? ▾ Answer

Moving shared state from child components to their common parent, then passing it down as props and updating via callbacks.

C.2. What is one-way data flow? ▾ Answer

Data flows down (props); events/callbacks flow up. Parents own state; children request changes through handlers.

C.3. What is a SyntheticEvent? ▾ Answer

React's cross-browser wrapper around native DOM events, used by onClick, onChange, etc.

L1 Fundamental

C.4. Why use e.preventDefault() on forms? ▾ Answer

To stop the browser's default full page reload on submit and handle submission in JavaScript instead.

C.5. What is the difference between controlled and uncontrolled components? ▾ Answer

Controlled — React state is the source of truth for input value. Uncontrolled — DOM holds value; read via ref (File 07).

C.6. Should every input have its own useState? ▾ Answer

Often yes for simple forms, or one object for many related fields. Lift to parent when siblings or submit handler need the data.

C.7. What should I read next? ▾ Answer

File 04 (lists, keys, conditional UI), File 06 (forms), File 05 (useEffect for side effects).

L2 Intermediate

C.8. Why doesn't updating a variable re-render the component? ▾ Answer

React only re-renders when state (via setter) or parent re-renders with new props. Plain let variables are not tracked.

C.9. Can I mutate state directly? ▾ Answer

No. Mutating objects/arrays in place may skip re-renders and breaks predictability. Always pass a new reference to the setter.

C.10. When should I use the functional form of setState? ▾ Answer

When the new state depends on the previous state, especially with batched updates or inside timeouts (setCount(prev => prev + 1)).

P.2. Core tasks

  1. functional update — setCount(c => c+1) in a double-click scenario. ▾ Solution 
    import { useState } from "react";

function DoubleCounter() {
  const [count, setCount] = useState(0);

  const handleDoubleIncrement = () => {
    // Functional update ensures access to latest state across queued updates
    setCount((prev) => prev + 1);
    setCount((prev) => prev + 1);
  };

  return (
    <div>
      <p>Current: {count}</p>
      <button onClick={handleDoubleIncrement}>Add 2 at once</button>
    </div>
  );
}

export default DoubleCounter;
  2. lift state — two siblings sharing selectedId via parent. ▾ Solution 
    import { useState } from "react";

function ItemList({ items, selectedId, onSelect }) {
  return (
    <ul>
      {items.map((item) => (
        <li
          key={item.id}
          style={{ fontWeight: item.id === selectedId ? "bold" : "normal" }}

          {item.name}
        </li>

    </ul>
  );
}

function ItemDetail({ item }) {
  return <div>Selected: {item ? item.name : "None"}</div>;
}

// Parent lifts and owns state:
function MasterDetailParent() {
  const [selectedId, setSelectedId] = useState(1);
  const items = [{ id: 1, name: "Keyboard" }, { id: 2, name: "Mouse" }];

  return (
    <div>
      <ItemList items={items} selectedId={selectedId} onSelect={setSelectedId} />
      <ItemDetail item={items.find((i) => i.id === selectedId)} />
    </div>
  );
}

export default MasterDetailParent;
  3. object state — update one field with spread. ▾ Solution 
    import { useState } from "react";

function UserProfile() {
  const [user, setUser] = useState({ name: "Bharat", role: "Dev", score: 10 });

  const updateScore = () => {
    // Immutable update: spread old state, override target property
    setUser((prev) => ({
      ...prev,
      score: prev.score + 5
    }));
  };

  return (
    <div>
      <p>{user.name} ({user.role}) - Score: {user.score}</p>
      <button onClick={updateScore}>Boost Score</button>
    </div>
  );
}

export default UserProfile;

P.3. Challenge

  1. Form-like local state for name+email; submit logs values; reset clears. ▾ Solution 
    import { useState } from "react";

function ContactForm() {
  const [formData, setFormData] = useState({ name: "", email: "" });

  const handleChange = (e) => {
    const { name, value } = e.target;
    setFormData((prev) => ({ ...prev, [name]: value }));
  };

  const handleSubmit = (e) => {
    e.preventDefault();
    console.log("Submitted Form Data:", formData);
  };

  const handleReset = () => {
    setFormData({ name: "", email: "" });
  };

  return (
    <form onSubmit={handleSubmit}>
      <input name="name" value={formData.name} onChange={handleChange} placeholder="Name" required />
      <input name="email" value={formData.email} onChange={handleChange} placeholder="Email" type="email" required />
      <button type="submit">Submit</button>
      <button type="button" onClick={handleReset}>Reset</button>
    </form>
  );
}

export default ContactForm;
  2. Identify one piece of state that should live higher — refactor. ▾ Solution 
    // State Colocation & Lifting Refactor:
// If two tabs in a Dashboard component need to know which tab is active,
// that state should be lifted to Dashboard rather than duplicated inside each Tab child.
function Dashboard() {
  const [activeTab, setActiveTab] = useState("overview");

  return (
    <div>
      <TabNav activeTab={activeTab} onTabChange={setActiveTab} />
      <TabContent activeTab={activeTab} />
    </div>
  );
}

function TabNav({ activeTab, onTabChange }) {
  return (
    <nav>
      <button onClick={() => onTabChange("overview")} className={activeTab === "overview" ? "active" : ""}>Overview</button>
      <button onClick={() => onTabChange("settings")} className={activeTab === "settings" ? "active" : ""}>Settings</button>
    </nav>
  );
}

function TabContent({ activeTab }) {
  return <div>Active panel: {activeTab}</div>;
}
