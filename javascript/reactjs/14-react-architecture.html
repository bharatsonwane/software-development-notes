1. Introduction

L1

L1 Fundamental

1.1. Overview

  • As apps grow, structure matters as much as syntax. This chapter covers feature folders, separation of concerns, compound components, error boundaries, and patterns that keep React codebases maintainable.
  • Builds on composition (File 02), Context (File 08), routing (File 09), and testing (File 13).
  • Default rule today: organize by feature, not file type; keep UI, hooks, and API colocated per feature; use error boundaries for unexpected failures; prefer composition over prop explosion.

1.2. Default rules and how to study this file

  • Default rule today: prefer function components and hooks; keep components small; colocate state with the UI that needs it.
  • After reading sections 2–9, complete P. Practical Assignment in 14-practice.jsx or build a small multi-page app from earlier chapters. Review C. Common questions.

4.3. Internal context for compound pattern

const TabsContext = createContext(null);

function Tabs({ defaultIndex = 0, children }) {
  const [activeIndex, setActiveIndex] = useState(defaultIndex);
  const value = useMemo(
    () => ({ activeIndex, setActiveIndex }),
    [activeIndex]
  );
  return (
    <TabsContext.Provider value={value}>
      <div className="tabs">{children}</div>
    </TabsContext.Provider>
  );
}

function Tab({ index, children }) {
  const { activeIndex, setActiveIndex } = useContext(TabsContext);
  return (
    <button
      role="tab"
      aria-selected={activeIndex === index}
      onClick={() => setActiveIndex(index)}
    >
      {children}
    </button>
  );
}

Tabs.Tab = Tab;
Tabs.List = TabList;
// attach subcomponents

5. Error boundaries

L2 L3

L2 Intermediate

5.1. What they catch

  • What Error Boundaries Catch:
    • JavaScript runtime exceptions thrown during component render phase.
    • Exceptions thrown in lifecycle methods (componentDidMount, useLayoutEffect, etc.).
    • Exceptions thrown in constructors of the component tree below them.
  • What Error Boundaries CANNOT Catch:
    1. Event Handlers: Clicking a button with an error (onClick={() => { throw new Error(); }}) does NOT trigger an Error Boundary because event handlers run outside the React render pass. (Use standard try / catch blocks inside event handlers).
    2. Asynchronous Code: Unhandled promise rejections inside setTimeout, requestAnimationFrame, or raw fetch calls.
    3. Server-Side Rendering (SSR): Errors during server rendering are handled at the server response level.
    4. Errors Inside the Boundary Itself: A boundary catches errors in its children, not within its own render method.
  • Why Error Boundaries Require Class Components: React has not released a hook alternative for componentDidCatch or static getDerivedStateFromError. You must use a class component or the production battle-tested npm package react-error-boundary.

5.2. Granular placement

<AppProviders>
  <ErrorBoundary fallback={<AppCrashScreen />}>
    <Header />
    <ErrorBoundary fallback={<SectionError />}>
      <ProductRoutes />
    </ErrorBoundary>
    <Footer />
  </ErrorBoundary>
</AppProviders>
  • Isolate failures — one broken widget should not white-screen the entire app.

L3 Advanced

5.4. Class component boundary (current API)

class ErrorBoundary extends React.Component {
  state = { hasError: false, error: null };

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, info) {
    console.error("Boundary caught:", error, info.componentStack);
    // report to Sentry, etc.
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback ?? (
        <div role="alert">
          <h2>Something went wrong.</h2>
          <button onClick={() => this.setState({ hasError: false, error: null })}>
            Try again
          </button>
        </div>
      );
    }
    return this.props.children;
  }
}
  • React may add use / error boundary hooks — check your React version; class boundary remains widely used.

6. Boundaries and layers

L2

L2 Intermediate

6.1. Unidirectional data flow (recap)

  • Props down, events up (File 03). Global client state via Context or store (Files 08, 11). Server state via query library (File 10).

6.2. Avoid circular imports

  • Features import from components/ and lib/, not from each other. Shared types in lib/types or feature-agnostic module.

6.3. Environment and config

// lib/config.js
export const API_BASE = import.meta.env.VITE_API_URL;
  • Never hardcode secrets in client bundle — env vars prefixed for exposure (Vite VITE_).

6.4. React Server Components (RSC) vs Client Components ("use client")

  • The Modern Architectural Boundary:

    In modern React architectures (Next.js App Router, React Router 7, Waku), components are divided into two execution environments:

    FeatureServer Component (Default)Client Component ("use client")
    ExecutionExecutes strictly on server (at build or request time)Prerendered on server + hydrates in browser
    Client Bundle Impact0 KB (zero JavaScript sent to client)Included in the downloaded browser bundle
    Direct Backend AccessYes (can run database queries, access filesystem)No (must fetch through HTTP API or Server Actions)
    State & HooksNo (useState, useEffect disallowed)Yes (full React hooks and interactivity allowed)
    Browser APIs & EventsNo (window, onClick disallowed)Yes (onClick, localStorage allowed)
  • The "use client" Boundary Rule:

    "use client" does NOT make a component run exclusively on the client; it defines the entry boundary where client hydration begins. Best architectural practice is to push "use client" as far down the component tree (to the leaves) as possible, keeping layouts and data containers as 0-bundle Server Components.

C. Common questions

L2 L3

L2 Intermediate

C.1. Feature folders vs pages folders? ▾ Answer

Feature-first scales better — everything for "products" lives together. pages/ can alias route entry components inside features.

C.2. Where do shared hooks go? ▾ Answer

hooks/ at root if truly generic; otherwise inside the feature that owns them.

C.3. What are compound components? ▾ Answer

A set of components (Tabs, Tabs.Tab) that share implicit state via internal Context for a flexible public API.

C.4. How many providers is too many? ▾ Answer

Combine in AppProviders. Split contexts by concern (File 08) — not one mega-provider.

C.5. Monorepo? ▾ Answer

Shared ui package + app packages per product — same feature principles at package level.

C.6. TypeScript? ▾ Answer

Same structure — add types.ts per feature for API shapes and props.

C.7. When to split a feature? ▾ Answer

When folder grows hard to navigate (~15+ files) or two unrelated domains share a folder — extract sub-features.

C.8. End of React track — what next? ▾ Answer

Build a small full-stack app applying Files 01–14. Deepen File 10 (TanStack Query), File 12 (perf), or explore Next.js for SSR/file routing.

L3 Advanced

C.9. Do error boundaries catch useEffect errors? ▾ Answer

Not async errors inside effects unless re-thrown during render. Handle fetch errors in UI state (File 10).

C.10. Can I use error boundary with function components? ▾ Answer

Boundaries are class components today (or library wrappers). Handlers use try/catch.

  2. Error boundary around a crashing child (class or react-error-boundary). ▾ Solution 
    import React from "react";

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false, error: null };
  }

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, errorInfo) {
    console.error("ErrorBoundary caught an error:", error, errorInfo);
  }

  render() {
    if (this.state.hasError) {
      return (
        <div className="error-fallback">
          <h3>Something went wrong in this section.</h3>
          <p>{this.state.error?.message}</p>
        </div>
      );
    }
    return this.props.children;
  }
}

export default ErrorBoundary;
  3. Compound component sketch (Tabs API). ▾ Solution 
    import { createContext, useContext, useState } from "react";

const TabsContext = createContext();

export function Tabs({ defaultTab, children }) {
  const [activeTab, setActiveTab] = useState(defaultTab);
  return (
    <TabsContext.Provider value={{ activeTab, setActiveTab }}>
      <div className="tabs-container">{children}</div>
    </TabsContext.Provider>
  );
}

export function Tab({ value, children }) {
  const { activeTab, setActiveTab } = useContext(TabsContext);
  return (
    <button onClick={() => setActiveTab(value)} className={activeTab === value ? "active" : ""}>
      {children}
    </button>
  );
}

export function TabPanel({ value, children }) {
  const { activeTab } = useContext(TabsContext);
  return activeTab === value ? <div className="tab-panel">{children}</div> : null;
}

P.3. Challenge

  1. Document scaling rules for your future self (10 bullets). ▾ Solution 
    /*
10 Rules for Scaling Large React Codebases:
1. Feature-First Folder Structure: Group by feature/domain, not by technical role.
2. Colocate State: Keep state as close to where it is used as possible.
3. Strict API Boundaries: Export only via feature index.js; avoid deep relative imports.
4. Decouple Data Fetching from UI: Use hooks (TanStack Query/RTK Query) instead of raw useEffect inside components.
5. Error Boundaries at Route and Feature levels: Never allow an unhandled error to crash the entire application.
6. Favor Composition over Inheritance and boolean prop explosions.
7. Profile Before Optimizing: Avoid premature useMemo/useCallback until metrics show a bottleneck.
8. Controlled Code Splitting: Lazy-load routes and heavy modals using React.lazy and Suspense.
9. Accessibility (a11y) from Day One: Use semantic HTML and aria roles.
10. Explicit Types and Tests: Test user interactions with React Testing Library, not implementation details.
*/
