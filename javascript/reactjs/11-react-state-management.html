1. Introduction

L1

L1 Fundamental

1.1. Overview

  • React apps juggle local UI state, shared client state, and server state (File 10). This chapter clarifies what goes where, when Context + useReducer (File 08) is enough, and when to adopt Zustand or Redux Toolkit for global client state.
  • Default rule today: keep state local until sharing hurts; use TanStack Query for server data; use Zustand for moderate global client state or Redux Toolkit when you need strict patterns, middleware, and large-team tooling.

1.2. Default rules and how to study this file

  • Default rule today: prefer function components and hooks; keep components small; colocate state with the UI that needs it.
  • After reading sections 2–8, complete P. Practical Assignment in 11-practice.jsx before File 12. Review C. Common questions.

2. State placement decision tree

L1 L2

L1 Fundamental

2.1. Where should this state live?

Is it from the API?
  → Yes → TanStack Query / RTK Query (File 10)

Do only one component and its children need it?
  → Yes → useState / useReducer locally (File 03)

Do siblings need it?
  → Lift to common parent (File 03)

Do many distant components need it?
  → Context (File 08) OR global store (this chapter)

Does it change very often across a huge tree?
  → Prefer Zustand/Redux with selectors, not one big Context

L2 Intermediate

2.2. Avoid duplicating server data in global store

// Avoid — user also lives in React Query cache
dispatch(setUser(fetchedUser));

// Prefer — single source for server copy
const { data: user } = useQuery({ queryKey: ["me"], queryFn: fetchMe });
  • Store UI preferences, draft wizard state, cart (if not server-owned) globally — not every GET response.

3. Context limits (recap)

L2

L2 Intermediate

  • File 08 — Context works for theme, auth snapshot, locale. Pain points at scale:
  • One Provider value change re-renders many consumers
  • No built-in middleware, devtools, or time-travel
  • Easy to create a god context that everything subscribes to
  • Graduate to a store when profiling shows Context churn or logic sprawls across files.

4. Zustand

L1 L3

L1 Fundamental

4.1. Minimal global store

npm install zustand
import { create } from "zustand";

const useCartStore = create((set) => ({
  items: [],
  addItem: (item) =>
    set((state) => ({ items: [...state.items, item] })),
  removeItem: (id) =>
    set((state) => ({
      items: state.items.filter((i) => i.id !== id),
    })),
  clear: () => set({ items: [] }),
}));

function CartBadge() {
  const count = useCartStore((s) => s.items.length);
  return <span>{count}</span>;
}

function AddButton({ product }) {
  const addItem = useCartStore((s) => s.addItem);
  return <button onClick={() => addItem(product)}>Add</button>;
}

4.2. When Zustand fits

  • Medium global state without boilerplate
  • Quick prototypes and production apps alike
  • Optional persist middleware (localStorage)
  • Works outside React — useCartStore.getState()

4.3. immer middleware (optional)

import { immer } from "zustand/middleware/immer";

const useStore = create(
  immer((set) => ({
    todos: [],
    toggle: (id) =>
      set((state) => {
        const todo = state.todos.find((t) => t.id === id);
        if (todo) todo.done = !todo.done;
      }),
  }))
);

L3 Advanced

4.4. Selectors prevent extra re-renders

  • Subscribe to slices of state:
const items = useCartStore((s) => s.items);        // re-render when items change
const addItem = useCartStore((s) => s.addItem);    // stable function reference
  • Only re-renders when selected value changes (shallow compare by default).

5. Redux Toolkit

L1 L2

L1 Fundamental

5.1. Core ideas

TermMeaning
StoreSingle app state tree
SliceOne feature's reducer + actions
DispatchSend action to update state
SelectorRead derived data from state
  • Redux enforces one direction: UI → dispatch(action) → reducer → new state → UI.

5.2. createSlice

import { configureStore, createSlice } from "@reduxjs/toolkit";

const cartSlice = createSlice({
  name: "cart",
  initialState: { items: [] },
  reducers: {
    addItem(state, action) {
      state.items.push(action.payload); // Immer inside RTK
    },
    removeItem(state, action) {
      state.items = state.items.filter((i) => i.id !== action.payload);
    },
  },
});

export const { addItem, removeItem } = cartSlice.actions;

const store = configureStore({
  reducer: { cart: cartSlice.reducer },
});

5.3. React bindings

import { Provider, useSelector, useDispatch } from "react-redux";

function App() {
  return (
    <Provider store={store}>
      <CartPage />
    </Provider>
  );
}

function CartPage() {
  const items = useSelector((state) => state.cart.items);
  const dispatch = useDispatch();
  return (
    <button onClick={() => dispatch(addItem({ id: 1, name: "Hat" }))}>
      Add ({items.length})
    </button>
  );
}

5.4. When Redux Toolkit fits

  • Large teams wanting strict conventions
  • Complex async middleware (logging, analytics)
  • Redux DevTools time-travel debugging
  • Existing Redux ecosystem investment

L2 Intermediate

5.5. RTK Query (server state)

  • Redux Toolkit includes RTK Query — define API slices with generated hooks (parallel to TanStack Query). Pick one primary server cache per app.

7. Patterns across libraries

L1 L2

L1 Fundamental

7.1. Colocate feature state

  • Keep cart logic in cartSlice or useCartStore — not scattered useState in ten files.

7.2. URL as state

  • Filters, pagination, selected tab — prefer URL search params (File 09) over global store when users should share/bookmark state.

L2 Intermediate

7.3. Derived state

  • Compute totals in selectors or useMemo, do not duplicate in store unless needed for perf:
const total = useCartStore((s) =>
  s.items.reduce((sum, i) => sum + i.price, 0)
);

C. Common questions

L1 L2 L3

L1 Fundamental

C.1. Do I need Redux for every React app? ▾ Answer

No. Most apps get by with local state, Context, TanStack Query, and optionally Zustand.

C.2. Can I use multiple Zustand stores? ▾ Answer

Yes — one store per feature domain is common (useCartStore, useUIStore).

C.3. How do I persist cart to localStorage? ▾ Answer

Zustand persist middleware, or save in effect (File 05) — handle SSR carefully.

C.4. What should I read next? ▾ Answer

File 12 (performance — selectors vs re-renders), File 10 (server cache), File 14 (feature folders).

L2 Intermediate

C.5. Zustand vs Context? ▾ Answer

Context for low-frequency shared values. Zustand when many components need selective subscriptions without prop drilling or giant re-renders.

C.6. Should API data live in Redux? ▾ Answer

Prefer TanStack Query or RTK Query. Duplicating server cache in manual Redux slices adds sync bugs.

C.7. What is a selector? ▾ Answer

Function that reads a slice of store state — enables fine-grained subscriptions.

C.8. When is Redux Toolkit worth the overhead? ▾ Answer

Large codebases, many async workflows, team already on Redux, need standardized patterns and DevTools.

C.9. Can Zustand and Redux coexist? ▾ Answer

Technically yes, but avoid — pick one global client state approach.

L3 Advanced

C.10. Is dispatch stable in Redux? ▾ Answer

Yes — like useReducer dispatch (File 08).

P. Practical Assignment

L1 L2
Pick the smallest tool: local state → context → Zustand/Redux as needed.

L1 Fundamental

P.1. Warm-up

  1. Decision comment: where would cart state live in a shop app? ▾ Solution 
    /*
Cart State Location Decision:
- Local state (useState) is insufficient because Header (cart badge count), ProductCard (add to cart), and CheckoutPage all require access.
- Prop drilling through 5 levels adds maintenance drag.
- Optimal choice: Global client store (Zustand or Redux Toolkit) or Context if updates are infrequent.
*/
  2. Tiny Zustand store with count + inc (or Redux Toolkit slice). ▾ Solution 
    import { create } from "zustand";

export const useCounterStore = create((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
  reset: () => set({ count: 0 })
}));
  3. Read store in two components. ▾ Solution 
    import { useCounterStore } from "./counterStore";

function CounterDisplay() {
  const count = useCounterStore((state) => state.count);
  return <h2>Current Count: {count}</h2>;
}

function CounterControls() {
  const { increment, decrement } = useCounterStore();
  return (
    <div>
      <button onClick={increment}>+1</button>
      <button onClick={decrement}>-1</button>
    </div>
  );
}

P.2. Core tasks

  1. Zustand — selector to avoid extra re-renders. ▾ Solution 
    import { useCartStore } from "./cartStore";

// Atomic selector pattern: component re-renders ONLY when itemsCount changes,
// ignoring totalAmount, isCheckoutLoading, and other store mutations.
function CartBadge() {
  const itemsCount = useCartStore((state) => state.items.length);
  return <span className="badge">{itemsCount}</span>;
}

export default CartBadge;
  2. RTK — slice with one async thunk or plain reducers. ▾ Solution 
    import { createSlice } from "@reduxjs/toolkit";

export const counterSlice = createSlice({
  name: "counter",
  initialState: { value: 0 },
  reducers: {
    increment: (state) => {
      // Immer allows direct "mutation" syntax
      state.value += 1;
    },
    addByAmount: (state, action) => {
      state.value += action.payload;
    }
  }
});

export const { increment, addByAmount } = counterSlice.actions;
export default counterSlice.reducer;
  3. compare — Same feature in Context vs store; note boilerplate. ▾ Solution 
    /*
Context vs Zustand Comparison:
- Context API:
  - Built-in to React, no extra bundle weight.
  - Requires Provider wrapping in component tree.
  - Value changes trigger re-render in ALL consumer components unless split into multiple contexts.
- Zustand:
  - Zero boilerplate; no Provider needed.
  - Built-in selector subscription prevents unnecessary re-renders.
  - Supports middleware (persist, devtools, immer).
*/
  4. normalize — Comment on storing entities by id. ▾ Solution 
    /*
Normalized State Structure (Entities by ID):
Instead of:
[{ id: 'u1', name: 'Alice', posts: [{ id: 'p1', title: '...' }] }]

Store Normalized:
{
  users: {
    byId: { 'u1': { id: 'u1', name: 'Alice', postIds: ['p1'] } },
    allIds: ['u1']
  },
  posts: {
    byId: { 'p1': { id: 'p1', title: '...' } },
    allIds: ['p1']
  }
}
Benefit: Updating a single post is an O(1) lookup without cloning deeply nested arrays.
*/

L2 Intermediate

P.3. Challenge

  1. Migrate a Context theme toggle to Zustand (or vice versa). ▾ Solution 
    import { create } from "zustand";
import { persist } from "zustand/middleware";

export const useThemeStore = create(
  persist(
    (set) => ({
      theme: "light",
      toggleTheme: () => set((s) => ({ theme: s.theme === "light" ? "dark" : "light" }))
    }),
    { name: "app-theme" } // Automatically syncs with localStorage!
  )
);
  2. List 3 signs you’ve outgrown Context-only state. ▾ Solution 
    /*
3 Signs You Have Outgrown Context-Only State:
1. High-frequency state updates (e.g. typing inputs, animations, mouse coordinates) cause noticeable UI lag across unaffected components.
2. "Provider Hell" — your index.jsx has 8+ nested <XProvider> wrappers.
3. Complex asynchronous workflows and caching require custom manual effect glue rather than built-in store middleware.
*/
