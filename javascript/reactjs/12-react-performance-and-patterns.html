1. Introduction

L1

L1 Fundamental

1.1. Overview

  • React is fast by default. Optimize when profiling shows a problem — not preemptively everywhere. This chapter covers React.memo, useMemo, useCallback, lazy loading, and Suspense for splitting work and skipping unnecessary renders.
  • Builds on rendering (File 04), hooks (File 07), routing (File 09), and data fetching (File 10).
  • Default rule today: measure first; fix wasted re-renders and large bundles before micro-optimizing; use memo + stable props for expensive pure children; lazy-load routes and heavy components.

1.2. Default rules and how to study this file

  • Default rule today: prefer function components and hooks; keep components small; colocate state with the UI that needs it.
  • After reading sections 2–11, complete P. Practical Assignment in 12-practice.jsx before File 13. Review C. Common questions.

2. When to optimize

L2

L2 Intermediate

2.1. React is already efficient

  • Reconciliation updates only changed DOM nodes. Most slowness comes from:
  • Huge lists without virtualization
  • Expensive calculations every render
  • Large JavaScript bundles slow initial load
  • Unnecessary re-renders of heavy subtrees

2.2. Profile before memoizing

  • Use React DevTools Profiler and browser Performance tab. Avoid sprinkling memo/useMemo on every component — they add memory and comparison cost.

3. Re-renders recap

L2

L2 Intermediate

3.1. What triggers re-render?

  • State change in this component
  • Context value change (if consumer)
  • Parent re-rendered (child re-renders too, unless optimized)
  • Props equal by reference for objects/functions — new reference every parent render → child thinks props changed.

3.2. Children render with parent

function Parent() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount((c) => c + 1)}>{count}</button>
      <ExpensiveList items={items} />  {/* re-renders on every count click */}
    </>
  );
}
  • Fix by lifting state down, memo, or splitting state into smaller subtrees.

3.3. Fiber Reconciler Lifecycle: Render Phase vs Commit Phase

  • Phase 1: Render Phase (Pure, Asynchronous, Interruptible):
    • React calls your component functions, calculates new Virtual DOM trees, and runs the reconciliation diffing algorithm.
    • In React 18 Concurrency, this phase can be paused, aborted, or restarted if higher-priority user input arrives (e.g. typing in an input).
    • Critical rule: Components MUST be pure functions without side effects during this phase, because React may render a component multiple times without committing it.
  • Phase 2: Commit Phase (Synchronous, Uninterruptible):
    • React applies calculated mutations to the actual browser DOM (inserting, updating, deleting nodes).
    • Runs useLayoutEffect synchronously before paint.
    • The browser performs layout and paints pixels to the screen.
    • React asynchronously fires useEffect callbacks.

4. React.memo

L2 L3

L2 Intermediate

4.1. Skip re-render if props unchanged

const ExpensiveList = memo(function ExpensiveList({ items }) {
  console.log("ExpensiveList render");
  return (
    <ul>
      {items.map((item) => (
        <li key={item.id}>{item.name}</li>
      ))}
    </ul>
  );
});
  • Shallow-compares props — if each prop is === previous, skip render.

4.2. When memo helps

  • Component is expensive to render
  • Same props often across parent re-renders
  • Props are stable or primitives
  • Memo does not help if props are new objects/functions every time — pair with useCallback / useMemo or restructure.

L3 Advanced

4.3. Custom comparison

const UserRow = memo(
  function UserRow({ user }) {
    return <div>{user.name}</div>;
  },
  (prev, next) => prev.user.id === next.user.id
);
  • Return true if props are equal (skip re-render).

5. useCallback

L2

L2 Intermediate

5.1. Stable function reference

function Parent() {
  const [count, setCount] = useState(0);
  const [text, setText] = useState("");

  const handleSave = useCallback(() => {
    save(text);
  }, [text]);

  return (
    <>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <MemoizedToolbar onSave={handleSave} />
      <button onClick={() => setCount((c) => c + 1)}>{count}</button>
    </>
  );
}
  • Without useCallback, handleSave is a new function each render → memoized child re-renders anyway.

5.2. Dependency array

  • Include everything handleSave closes over (text). Same rules as useEffect (File 05).

5.3. When not to use useCallback

  • Child is not memoized
  • Handler passed to native DOM (onClick) — usually fine without
  • Premature optimization on cheap trees

6. useMemo

L2

L2 Intermediate

6.1. Cache expensive computation

function ProductTable({ products, filter }) {
  const filtered = useMemo(() => {
    return products.filter((p) => p.name.includes(filter));
  }, [products, filter]);

  return <Table rows={filtered} />;
}
  • Recomputes only when products or filter change.

6.2. Stable object for Context or memo children

const value = useMemo(
  () => ({ theme, toggleTheme }),
  [theme, toggleTheme]
);

return (
  <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>
);
  • File 08 — avoid new context object every render.

6.3. useMemo vs useCallback

HookReturns

7. Code splitting and lazy

L2

L2 Intermediate

7.1. dynamic import()

  • Split heavy modules into separate chunks loaded on demand:
import { lazy, Suspense } from "react";

const AdminDashboard = lazy(() => import("./AdminDashboard"));
  • Webpack/Vite creates a separate file fetched when the component first renders.

7.2. Suspense fallback

function App() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <Routes>
        <Route path="/admin" element={<AdminDashboard />} />
      </Routes>
    </Suspense>
  );
}
  • While chunk loads, fallback shows (File 09 — route-level splitting).

7.3. What to lazy-load

  • Admin / settings routes (rare visits)
  • Rich editors, charts, maps
  • Not tiny components — overhead of async boundary

8.3. Concurrent Transitions: useTransition vs useDeferredValue

  • Urgent vs Transition Updates:
    • Urgent updates: Direct user interactions like typing in an input, selecting a radio button, or clicking a button. These require instant screen feedback (0–16ms) to avoid feeling sluggish.
    • Non-urgent transitions: Heavy filtering, rendering complex charts, or switching tabs. These can yield to urgent input without degrading UX.
  • useTransition (Wrapping State Setters):
import { useState, useTransition } from "react";

function SearchPage() {
  const [input, setInput] = useState("");
  const [query, setQuery] = useState("");
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    // 1. Urgent update: input field updates immediately
    setInput(e.target.value);

    // 2. Non-urgent transition: filtering 10,000 items yields to user typing
    startTransition(() => {
      setQuery(e.target.value);
    });
  }

  return (
    <>
      <input value={input} onChange={handleChange} />
      {isPending && <span>Filtering list...</span>}
      <HugeFilteredList query={query} />
    </>
  );
}
  • useDeferredValue (Deferring Props/Values):

    When you don't control the state setter (e.g. receiving a value via props), useDeferredValue defers re-rendering the child tree until urgent work completes:

    import { useDeferredValue } from "react";

function ProductSearch({ query }) {
  // Defers expensive list re-render while query is being typed
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  return (
    <div style={{ opacity: isStale ? 0.6 : 1 }}>
      <SlowList query={deferredQuery} />
    </div>
  );
}

9. List performance

L2 L3

L2 Intermediate

9.1. Keys and stable item components

  • Stable key={item.id} (File 04). memo on row component when parent state changes often.

L3 Advanced

9.2. DOM Virtualization (Windowing Mechanics)

  • Why 10,000 DOM Nodes Crash Performance:

    Mounting 10,000 DOM nodes creates megabytes of memory pressure, forces browser layout engines to recalculate geometry across thousands of elements, and causes severe scrolling stutter below 60fps.

  • How Virtualization Solves This:
    1. Calculates the visible viewport height (e.g. 600px) and item height (e.g. 40px).
    2. Calculates that only ~15 items fit on screen + adds a buffer window (overscan of ~5 items above and below).
    3. Creates a tall scrollable container with total height (totalItems * itemHeight = 400,000px).
    4. Renders only the 25 active DOM elements, positioning them with transform: translateY(offsetPx). As the user scrolls, old nodes are unmounted or recycled into new positions.
  • Recommended Modern Libraries: @tanstack/react-virtual (headless, works with any DOM layout) and react-window.

11. Putting it together

L2

L2 Intermediate

11.1. Optimized list row

const ProductRow = memo(function ProductRow({ product, onSelect }) {
  return (
    <tr onClick={() => onSelect(product.id)}>
      <td>{product.name}</td>
      <td>{product.price}</td>
    </tr>
  );
});

function ProductList({ products }) {
  const [filter, setFilter] = useState("");
  const [selectedId, setSelectedId] = useState(null);

  const visible = useMemo(
    () => products.filter((p) => p.name.includes(filter)),
    [products, filter]
  );

  const handleSelect = useCallback((id) => {
    setSelectedId(id);
  }, []);

  return (
    <>
      <input value={filter} onChange={(e) => setFilter(e.target.value)} />
      <table>
        <tbody>
          {visible.map((p) => (
            <ProductRow key={p.id} product={p} onSelect={handleSelect} />
          ))}
        </tbody>
      </table>
    </>
  );
}

C. Common questions

L2 L3

L2 Intermediate

C.1. Should I wrap every component in memo? ▾ Answer

No. Only when Profiler shows expensive wasted renders and props can be stable.

C.2. useMemo vs recalculating every render? ▾ Answer

useMemo when computation is measurably expensive or you need referential stability for deps/memo children.

C.3. useCallback vs defining function in render? ▾ Answer

Inline is fine unless a memoized child or effect dep needs stable identity.

C.4. What is code splitting? ▾ Answer

Loading parts of the app on demand via dynamic import() — smaller initial bundle.

C.5. What does Suspense do? ▾ Answer

Catches lazy components (and some async data patterns) while waiting — shows fallback UI.

C.6. What should I read next? ▾ Answer

File 13 (testing memoized components), File 14 (architecture boundaries), File 10 (query suspense).

L3 Advanced

C.7. Why does memo not work with inline objects? ▾ Answer

{ foo: 1 } is a new reference each render — shallow compare fails. Memoize the object or pass primitives.

C.8. How do I speed up a 10,000 item list? ▾ Answer

Virtualize — do not render all DOM nodes. Consider pagination.

C.9. Does Context hurt performance? ▾ Answer

Any consumer re-renders when value changes. Split contexts, memoize value, or use Zustand selectors (File 11).

C.10. React Compiler / automatic memoization? ▾ Answer

Emerging tooling may reduce manual memo — still understand concepts for debugging.

  3. useMemo for a filtered list derived from state. ▾ Solution 
    import { useState, useMemo } from "react";

function ProductSearch({ products }) {
  const [filter, setFilter] = useState("");

  // useMemo recomputes only when products array or filter string changes
  const filteredProducts = useMemo(() => {
    console.log("Filtering products list...");
    return products.filter((p) => p.name.toLowerCase().includes(filter.toLowerCase()));
  }, [products, filter]);

  return (
    <div>
      <input value={filter} onChange={(e) => setFilter(e.target.value)} placeholder="Search..." />
      <ul>
        {filteredProducts.map((p) => <li key={p.id}>{p.name}</li>)}
      </ul>
    </div>
  );
}

  4. useLayoutEffect — One legitimate DOM-measure case (or comment). ▾ Solution 
    import { useLayoutEffect, useRef, useState } from "react";

function TooltipMeasure() {
  const tooltipRef = useRef(null);
  const [height, setHeight] = useState(0);

  // useLayoutEffect fires synchronously after DOM mutations, BEFORE the browser paints.
  // Ideal for measuring DOM elements to prevent visual layout flicker.
  useLayoutEffect(() => {
    if (tooltipRef.current) {
      setHeight(tooltipRef.current.getBoundingClientRect().height);
    }
  }, []);

  return <div ref={tooltipRef} className="tooltip">Measured Height: {height}px</div>;
}
