2. Trunk-based development

L1

L1 Fundamental

Trunk-Based Development (TBD) is an engineering practice where all developers merge small, frequent updates into a single core branch (called main or the "trunk") multiple times per day.

  • Short-lived branches: Branches typically live for only a few hours up to a single day before being merged.
  • Continuous Integration: Strong automated unit tests and CI pipelines validate every single commit pushed to the trunk.
  • Feature Flags: Incomplete or experimental features are protected behind runtime toggle flags rather than isolated in long-running branches.

3. Git Flow overview

L1 L2

L1 Fundamental

Git Flow (published by Vincent Driessen in 2010) is a structured, strict branching model organized around distinct release milestones.

/*
Git Flow Branch Structure:

main        ────── C1 ─────────────────────────── C2 (v1.0.0) ─────────── (Production)
                    ▲                             ▲
hotfix              │                             └─── H1 ──┘ (Emergency fix)
                    │                                   │
release             │                     └── R1 ───────┤ (Stabilization)
                    │                          ▲        │
develop     ─────── D1 ─────── D2 ──────────── D3 ──────┴─ D4 ─────────── (Next release)
                     \       /                 \       /
feature               F1 ── F2                  F3 ── F4
*/
  • Two Perpetual Branches: main (stores official production releases) and develop (serves as an integration branch for features).
  • Supporting Branches: feature/* (branched from develop), release/* (prepares release metadata), and hotfix/* (branched directly from main to fix critical production defects).

4. Feature branch workflow

L1

L1 Fundamental

The Feature Branch Workflow (often called GitHub Flow) is a lightweight, modern approach well-suited for web applications and SaaS products practicing continuous deployment.

  1. main is always deployable and protected against direct pushes.
  2. Create descriptive branches off main (e.g. feature/stripe-webhooks, fix/nav-overflow).
  3. Commit locally and push regularly to the remote server.
  4. Open a Pull Request for discussion, peer review, and automated CI test runs.
  5. Merge into main and deploy immediately to production.

5. Choosing a workflow for a team

L2

L2 Intermediate

Select a branching workflow based on your team's release mechanism:

  • Choose GitHub Flow / Feature Branches: When building web services, SaaS products, or microservices with continuous delivery and frequent deployments.
  • Choose Trunk-Based Development: For mature engineering teams with comprehensive automated test suites and high CI/CD discipline looking to eliminate merge friction.
  • Choose Git Flow: For scheduled, versioned release software (e.g. mobile app stores, desktop installers, embedded firmware) that must maintain multiple legacy versions concurrently.

C. Common questions

L1 L2

L1 Fundamental

C.1. What are the key architectural differences between Trunk-Based Development and Git Flow? ▾ Answer

Trunk-Based Development has a single persistent branch (main) where all developers merge short-lived branches (< 24-48 hours) frequently using feature toggles and continuous integration. Git Flow utilizes two perpetual branches (main and develop) alongside dedicated release, feature, and hotfix branches, designed for structured, periodic milestone releases.

C.2. In Git Flow, what is the role of a Hotfix branch? ▾ Answer

A hotfix branch is branched directly from main to address a critical bug discovered in production. Once resolved, it is merged immediately into both main (tagged with a patch version like v1.0.1) and develop, ensuring the fix is present in production and not lost in upcoming releases.

L2 Intermediate

C.3. How does Trunk-Based Development eliminate "merge hell"? ▾ Answer

"Merge hell" happens when a feature branch lives for weeks or months, diverging substantially from main and requiring hundreds of painful conflict resolutions. By merging multiple times a day in small increments, conflicts are tiny, detected immediately by CI, and resolved within minutes while the code is fresh in memory.

C.4. What is a Feature Flag (or Feature Toggle) and why is it necessary for Trunk-Based Development? ▾ Answer

A feature flag is a configuration check in code (e.g. if (features.NEW_BILLING_ENABLED)) that controls feature visibility at runtime. It decouples code deployment from feature release, allowing incomplete features to safely reside on main and deploy to production while remaining hidden from end users until fully finished and tested.

P.1. Warm-up

  1. Write 5 bullets: trunk-based vs Git Flow. ▾ Solution 
    /*
Trunk-Based Development vs Git Flow:
1. Trunk-Based: Developers merge small, frequent commits directly into 'main' (or short-lived <1 day branches).
2. Git Flow: Utilizes long-lived branches (main, develop, release, feature, hotfix) with scheduled release cycles.
3. Trunk-Based relies heavily on Automated CI/CD and Feature Flags.
4. Git Flow has higher isolation but significant merge overhead and conflict frequency.
5. Modern SaaS teams overwhelmingly prefer Trunk-Based for velocity.
*/
  2. Name the long-lived branches each uses. ▾ Solution 
    /*
Long-lived Branches:
- Git Flow: 'main' (production code) and 'develop' (integration branch).
- Trunk-Based: Single long-lived branch: 'main' (or 'trunk').
*/
  3. Describe where hotfixes land in each model. ▾ Solution 
    /*
Hotfix Handling:
- Git Flow: Branched from 'main' (hotfix/*), merged into BOTH 'main' and 'develop'.
- Trunk-Based: Fixed directly on 'main' and cherry-picked/deployed immediately via automated pipeline.
*/

P.2. Core tasks

  1. feature branch — End-to-end: branch → commits → PR → delete. ▾ Solution 
    # End-to-End Feature Branch Workflow:
git switch -c feature/auth-jwt
# ... work and commits ...
git add . && git commit -m "feat(auth): add jwt middleware"
git push -u origin feature/auth-jwt
# Open PR on GitHub -> Review & CI approval -> Squash and merge
git switch main
git pull
git branch -d feature/auth-jwt
  2. release branch sketch — When Git Flow creates release/*. ▾ Solution 
    /*
Release Branch in Git Flow:
- When develop reaches milestone maturity, branch 'release/v1.2.0' is cut.
- Only bug fixes and metadata polish occur on release/*; no new features.
- Once ready, tagged on 'main' and back-merged into 'develop'.
*/
  3. trunk — Short-lived branches + frequent integrate. ▾ Solution 
    /*
Trunk-Based Best Practices:
- Keep feature branches alive for less than 24-48 hours.
- Use Feature Toggles (launch darkly, unflagged flags) to hide incomplete features in production.
- Continuous Integration builds every commit automatically.
*/
  4. team rules — Draft 6 rules for your future team. ▾ Solution 
    /*
6 Team Git Rules:
1. Every commit must follow Conventional Commits (feat:, fix:, chore:).
2. Never push directly to main — all changes require Pull Requests.
3. Pull requests require at least one approving code review and passing CI.
4. Keep PRs small (< 300 lines) for thorough, high-quality review.
5. Always use --force-with-lease instead of --force.
6. Delete feature branches immediately after merging.
*/

When Git Flow is Overkill:

- Git Flow is suitable primarily for multi-version distributed software (e.g. mobile apps, embedded firmware, desktop OS).
*/
