2. Remotes: add, -v, fetch

L1

L1 Fundamental

A remote in Git is a bookmark URL pointing to a shared repository hosted on the internet or a local network (e.g. GitHub, GitLab, Bitbucket).

# List configured remotes and their fetch/push URLs
git remote -v

# Link a local repository to a remote server (conventionally named origin)
git remote add origin https://github.com/username/project.git

# Download all new branches and commits from remote without altering working tree
git fetch origin

# Prune stale remote tracking branches deleted on the server
git fetch --prune
  • git fetch is completely safe: it updates your remote tracking references (origin/main) inside .git without changing your working directory or active branch.

3. push, pull, and pull --rebase

L1 L2

L1 Fundamental

Synchronizing local commits with a remote repository:

# Push local commits and configure upstream tracking
git push -u origin feature/billing

# Subsequent pushes on a tracking branch
git push

# Standard pull: Fetches and creates a merge commit if branches diverged
git pull origin main

# Clean pull: Fetches and replays your local unpushed commits on top of remote
git pull --rebase origin main

# Safe force-push after local rebasing (never use raw --force!)
git push --force-with-lease

4. Pull requests / merge requests (overview)

L1

L1 Fundamental

A Pull Request (PR) (called a Merge Request in GitLab) is not a Git command, but a hosting platform feature that facilitates code review and automated CI/CD checks before code enters the main branch.

  1. Push feature branch to remote: git push -u origin feature/name.
  2. Open PR on GitHub pointing feature/name → main.
  3. Team conducts line-by-line review; automated tests pass.
  4. PR is merged into main and the feature branch is deleted.

5. Forking and contributing workflows

L2

L2 Intermediate

When contributing to open-source projects where you lack write access, use the Forking Workflow:

# 1. Fork target repo on GitHub (creates copy under your personal account)
# 2. Clone your personal fork
git clone https://github.com/my-user/open-source-app.git
cd open-source-app

# 3. Add original upstream repository as a second remote
git remote add upstream https://github.com/original-author/open-source-app.git

# 4. Sync your local main with upstream before starting work
git switch main
git pull upstream main

# 5. Create feature branch, commit, push to your fork (origin), and open PR

C. Common questions

L1 L2

L1 Fundamental

C.1. What is the difference between git fetch and git pull? ▾ Answer

git fetch downloads new commits, files, and branches from the remote server into your local repository database without modifying your current working files or branch. git pull is a composite command: it runs git fetch and immediately attempts to merge the downloaded commits into your active checked-out branch (git fetch + git merge).

C.2. What does the -u flag do during git push -u origin <branch>? ▾ Answer

The -u (or --set-upstream) flag configures the tracking link between your local branch and the remote branch on origin. Once set, Git remembers the target branch, allowing you to run simply git push or git pull in the future without specifying the remote name or branch name.

L2 Intermediate

C.3. Why do many development teams enforce git pull --rebase? ▾ Answer

A standard git pull creates an unnecessary merge commit ("Merge branch 'main' of ...") every time someone else pushes changes while you are working locally. git pull --rebase fetches the new remote commits and replays your local unpushed commits on top of them, keeping the repository history clean, readable, and completely linear.

C.4. Why is git push --force-with-lease much safer than git push --force? ▾ Answer

git push --force blindly overwrites the remote branch regardless of whether anyone else has pushed commits to it in the meantime, destroying their work. --force-with-lease checks whether the remote branch has received commits from someone else since your last fetch; if so, it refuses to push, protecting team members from accidental data loss.

P. Practical Assignment

L1 L2
Use GitHub/GitLab or a second local bare repo as “remote”.

L1 Fundamental

P.1. Warm-up

  1. Add a remote; git remote -v. ▾ Solution 
    # Add remote repository
git remote add origin git@github.com:username/repository.git

# Verify configured remotes
git remote -v
# origin  git@github.com:username/repository.git (fetch)
# origin  git@github.com:username/repository.git (push)
  2. Push a branch; set upstream. ▾ Solution 
    # Push local main branch and track remote origin/main
git push -u origin main
  3. Fetch and see new remote-tracking branches. ▾ Solution 
    # Fetch remote branches without merging into working directory
git fetch origin

# Inspect remote tracking branches
git branch -r

P.2. Core tasks

  1. pull — Pull with merge vs rebase; note the difference. ▾ Solution 
    # git pull = git fetch + git merge
git pull origin main

# git pull --rebase = git fetch + git rebase
# Keeps local commit history clean and linear
git pull --rebase origin main
  2. PR sketch — Open or describe a PR with base/compare. ▾ Solution 
    /*
Pull Request (PR) Anatomy:
- Base: The target branch you want to merge into (e.g. main or develop).
- Compare: The feature branch containing your new commits (e.g. feature/checkout).
- Reviewers inspect diff, leave comments, CI tests pass -> PR is merged.
*/
  3. fork model — Comment your fork → upstream sync steps. ▾ Solution 
    # Fork & Upstream Sync Workflow:
# 1. Add original project repository as 'upstream' remote
git remote add upstream https://github.com/original-owner/repo.git

# 2. Fetch upstream changes and sync into local main
git fetch upstream
git switch main
git merge upstream/main
git push origin main
  4. delete remote branch — After merge, delete remote feature branch. ▾ Solution 
    # Delete remote branch after merging PR
git push origin --delete feature/checkout

L2 Intermediate

P.3. Challenge

  1. Simulate two clones collaborating on one bare remote. ▾ Solution 
    # Simulating two clones collaborating:
# Clone 1:
git clone /path/to/bare-repo.git clone1
cd clone1 && echo "v1" > f.txt && git add . && git commit -m "feat: 1" && git push

# Clone 2:
git clone /path/to/bare-repo.git clone2
cd clone2 && git pull && echo "v2" >> f.txt && git commit -am "feat: 2" && git push
  2. Recover from rejected non-fast-forward push safely (pull --rebase then push). ▾ Solution 
    # Recovering from rejected non-fast-forward push:
# When push is rejected because remote contains new commits:
git pull --rebase origin main
# Fix any conflicts if necessary, then push cleanly:
git push origin main
