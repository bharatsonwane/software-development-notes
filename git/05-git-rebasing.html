2. Rebase vs merge (when to use which)

L1

L1 Fundamental

Both git merge and git rebase integrate changes from one branch into another, but with different philosophical approaches to history:

/*
Before:
          C3 ─── C4 (feature)
         /
C1 ─── C2 ─── C5 (main)

Option A: git merge (Preserves exact branching history & creates merge commit M)
C1 ─── C2 ─── C5 ─────── M (main)
         \             /
          C3 ─── C4 ──┘

Option B: git rebase (Replays C3 and C4 on top of main, creating linear history)
C1 ─── C2 ─── C5 ─── C3' ─── C4' (feature)
*/
  • Merge: Non-destructive. It preserves the exact chronological record and true historical context of when branches existed.
  • Rebase: Rewrites project history to create a clean, linear progression of commits without noisy merge bubbles.

3. git rebase onto main

L1

L1 Fundamental

To update your feature branch with the latest changes from main using rebase:

# Step 1: Switch to your feature branch
git switch feature/cart

# Step 2: Rebase your commits on top of the latest main
git rebase main

# If conflicts occur during replay:
# 1. Resolve conflict markers in affected files
# 2. Stage the resolved files:
git add .
# 3. Continue the replay (do NOT run git commit):
git rebase --continue

# To abandon the rebase and return to original state:
git rebase --abort

4. Interactive rebase (edit, squash, drop)

L2

L2 Intermediate

Interactive rebase (git rebase -i) allows you to clean up, reorder, combine, or edit local commits before submitting them for review.

# Start interactive rebase for the last 3 commits
git rebase -i HEAD~3

# In the interactive editor todo list:
pick 1a2b3c4 feat: add checkout button
squash 5d6e7f8 fix typo in checkout button
reword 9g0h1i2 docs: update payment docs
  • pick (p): Keep the commit as is.
  • reword (r): Keep the commit changes, but edit the commit message.
  • squash (s): Meld this commit into the previous one and concatenate commit messages.
  • fixup (f): Meld into previous commit, discarding this commit's log message.
  • drop (d): Remove the commit entirely.

5. Risks: rewriting shared history

L2

L2 Intermediate

The Golden Rule of Rebasing: Never rebase commits that exist outside your local repository and that others may have based work on.

Why: Rebasing creates brand-new commit hashes (C3', C4') for every replayed commit. If teammates have pulled the old commits, their Git will see two divergent histories and will attempt to merge them back, creating duplicate commits and chaotic merge conflicts.

Remote synchronization and the safer git push --force-with-lease command are covered in File 06 (Remote & Collaboration).

C. Common questions

L1 L2

L1 Fundamental

C.1. What is the fundamental difference between git merge and git rebase? ▾ Answer

git merge brings branches together by creating a new merge commit (preserving historical branching structure and commit dates). git rebase rewrites history by moving the entire feature branch so that it begins from the tip of the target branch, creating a clean and perfectly linear commit log.

C.2. Why must you run git rebase --continue instead of git commit after fixing rebase conflicts? ▾ Answer

During a rebase, Git is replaying a sequence of existing commits one by one. Running git commit would create an unintended new commit outside the rebase sequence. Staging the resolution with git add and running git rebase --continue signals Git to apply the resolved changes to the currently replayed commit and proceed to the next commit in the todo list.

L2 Intermediate

C.3. What is the Golden Rule of Rebasing and why is it critical? ▾ Answer

The Golden Rule is: never rebase public or shared branches. Because rebasing gives replayed commits brand-new SHA-1 hashes while discarding the old ones, any teammate who pulled the original commits will have their repository out of sync. When they push or pull, Git will attempt to reconcile the conflicting histories, causing severe duplication and merge conflicts.

C.4. What is the difference between squash and fixup during interactive rebase? ▾ Answer

Both commands combine the marked commit into the previous commit in the rebase list. squash prompts you to view and edit both commit messages together. fixup discards the marked commit's message completely, keeping only the parent commit's message (ideal for small fixups or typo fixes).

P. Practical Assignment

L1 L2
Only rebase commits you have not shared (or coordinate carefully).

L1 Fundamental

P.1. Warm-up

  1. Rebase a feature branch onto updated main (local). ▾ Solution 
    # Rebase feature branch onto updated main
git switch feature/login
git fetch origin
git rebase origin/main
# Re-applies feature commits one by one on top of origin/main
  2. Compare merge vs rebase histories visually. ▾ Solution 
    # Merge vs Rebase history visualization:
# Merge creates a non-linear diamond history with a merge commit.
# Rebase rewrites commit history linearly as if work began today.
git log --graph --oneline --decorate -n 10
  3. Run rebase -i and squash two commits. ▾ Solution 
    # Interactive rebase: squash last 2 commits into one
git rebase -i HEAD~2

# In the editor, change the second line from 'pick' to 'squash' (or 's'):
# pick 1a2b3c feat: initial login button
# squash 4d5e6f fix: adjust button padding

P.2. Core tasks

  1. onto — Rebase onto a different base. ▾ Solution 
    # Rebase --onto: move commits from one branch base to another
# git rebase --onto <new-base> <old-base> <branch>
git rebase --onto main feature/legacy-base feature/my-feature
  2. conflict during rebase — Resolve and --continue. ▾ Solution 
    # Resolving conflict during rebase:
# 1. Fix conflicting files
# 2. Stage resolved files
git add auth.js

# 3. Continue rebase (DO NOT use git commit)
git rebase --continue
  3. abort — Abort a rebase once. ▾ Solution 
    # Abort rebase mid-way and restore original branch state:
git rebase --abort
  4. golden rule — Write when not to rebase. ▾ Solution 
    /*
The Golden Rule of Rebasing:
NEVER rebase commits that exist outside your local repository and that other people might have based work on.
Rebasing changes commit SHAs; rebasing shared branches causes merge chaos for teammates.
Only rebase local, unpushed feature branches.
*/

L2 Intermediate

P.3. Challenge

  1. Interactive rebase: reword + drop one commit in a 4-commit branch. ▾ Solution 
    # Interactive rebase reword and drop:
git rebase -i HEAD~4

# In editor:
# r 1111111 feat: reword this commit message
# pick 2222222 feat: keep this commit
# d 3333333 test: drop this unwanted commit
# pick 4444444 feat: final commit
  2. Explain force-push need after rebase of a published branch — and safer alternatives. ▾ Solution 
    /*
Force-pushing after Rebase:
- Because rebase recalculates commit hashes, git push will be rejected with (non-fast-forward).
- DANGEROUS: git push --force (overwrites remote even if teammates pushed new commits).
- SAFE ALTERNATIVE: git push --force-with-lease
  Ensures no one else pushed new work to the remote branch before overwriting.
*/
