2. Client-side hooks overview

L1 L2

L1 Fundamental

Git hooks are executable scripts located in the .git/hooks/ directory that Git automatically runs before or after specific operations like commit, rebase, or push.

  • Local-only: The .git/hooks/ directory is not tracked by Git and is not cloned with the repository for security reasons.
  • Executable bit: Scripts must have execute permissions (chmod +x .git/hooks/<hook>) to trigger.
  • Sharing hooks across teams: Teams either configure git config core.hooksPath .githooks to point Git to a version-controlled folder or use hook management tools like Husky (Node.js) or pre-commit (Python).
# Inspect default hook sample templates
ls -la .git/hooks/
# Output includes: pre-commit.sample, commit-msg.sample, pre-push.sample

# Point git to a version-controlled hooks directory:
git config core.hooksPath .githooks

3. pre-commit and commit-msg

L1 L2

L1 Fundamental

The two most widely used client-side commit hooks are pre-commit and commit-msg:

  • pre-commit: Runs first upon invoking git commit, before the commit editor is opened. If the script exits with non-zero, Git aborts the commit. Perfect for linting staged files, syntax checks, and secret scanners.
  • commit-msg: Runs after the developer inputs the commit message. Git passes the path of a temporary file containing the message as argument $1. If the script exits non-zero, the commit is aborted. Used to enforce message formats (e.g. Conventional Commits).
# Bypassing hooks in an emergency (skips pre-commit and commit-msg):
git commit --no-verify -m "fix: emergency hotfix"

# Testing pre-commit hooks manually on staged files:
git diff --cached --name-only

4. Commit message conventions

L1 L2

L1 Fundamental

Standardized commit messages make changelogs automated, git histories readable, and code reviews effortless. The industry standard is Conventional Commits:

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
  • Types: feat (new feature), fix (bug fix), docs (documentation), refactor (code change without feature or bug fix), test (adding or refactoring tests), chore (build tasks, dependency updates).
  • Imperative tone: Use "add", "fix", "change" rather than "added" or "adds".
  • Subject line: Keep under 50–72 characters, lowercase, no period at end.

5. What not to commit (secrets, build artifacts)

L1 L2

L1 Fundamental

Repositories must strictly exclude build outputs, package managers' installations, OS metadata, and confidential credentials.

  • Never commit secrets: API keys, passwords, database URLs, SSH private keys, AWS credentials, .env files.
  • Never commit generated files: node_modules/, dist/, build/, __pycache__/, .DS_Store.
# If a file is already tracked by Git, adding it to .gitignore does NOT untrack it!
# You must remove it from the index (preserving it on disk):
git rm --cached .env

# Verify ignoring status:
git check-ignore -v .env

C. Common questions

L1 L2

L1 Fundamental

C.1. Why are client-side Git hooks not tracked in version control by default? ▾ Answer

Git explicitly excludes .git/hooks/ from cloning to prevent remote arbitrary code execution vulnerabilities. If hooks were tracked automatically, cloning a malicious repository could instantly execute harmful scripts on the developer's computer. Instead, teams use core.hooksPath or tools like Husky/pre-commit which require explicit user installation.

C.2. What are the key rules of the Conventional Commits specification? ▾ Answer

Conventional Commits require a structured prefix: <type>(<scope>): <description>. Common types are feat, fix, docs, refactor, and chore. The description must be in the imperative mood ("add feature" not "added feature"), under 50 characters, followed optionally by a blank line and detailed body paragraph, and footers for breaking changes (BREAKING CHANGE:).

L2 Intermediate

C.3. How do pre-commit and commit-msg hooks differ in execution point and purpose? ▾ Answer

pre-commit executes immediately when git commit is run, before any message prompt. It inspects staged code for linting, unit test pass rates, formatting, or committed secrets. In contrast, commit-msg executes after the commit message has been authored; it receives the file path containing the drafted message as $1 and validates adherence to ticketing or semantic formatting standards.

C.4. If an API key or password is committed and pushed to a remote repository, why is adding it to .gitignore not enough? ▾ Answer

.gitignore only stops untracked files from being staged in the future; it does not touch tracked files or erase history. Even if the file is deleted in a new commit, the sensitive key remains visible in every commit snapshot in Git's historical tree. The key must be immediately revoked/rotated at the provider, and the commit history must be purged using tools like git-filter-repo or BFG Repo-Cleaner before force-pushing.

ls -la .git/hooks

  2. Enable a sample pre-commit that rejects WIP in the message. ▾ Solution 
    # Create simple pre-commit hook that blocks "WIP" in staged files:
cat << 'EOF' > .git/hooks/pre-commit
#!/bin/sh
if git diff --cached | grep -q "TODO: NOCOMMIT"; then
  echo "ERROR: Attempting to commit code containing 'TODO: NOCOMMIT'!"
  exit 1
fi
EOF

chmod +x .git/hooks/pre-commit

P.2. Core tasks

  1. commit-msg — Enforce subject length or prefix. ▾ Solution 
    # Enforce commit message format in .git/hooks/commit-msg:
cat << 'EOF' > .git/hooks/commit-msg
#!/bin/sh
msg=$(head -n 1 "$1")
regex="^(feat|fix|docs|style|refactor|perf|test|chore)(\(.+\))?: .+"

if ! echo "$msg" | grep -Eq "$regex"; then
  echo "ERROR: Invalid commit message format. Expected conventional commit."
  exit 1
fi
EOF

chmod +x .git/hooks/commit-msg
  2. secrets — Checklist of files that must never be committed. ▾ Solution 
    /*
Files That Must NEVER Be Committed Checklist:
- .env, .env.local, .env.production (secret environment keys)

- credentials.json, service-account.json (cloud provider credentials)
- database backups (*.sql, *.dump)
