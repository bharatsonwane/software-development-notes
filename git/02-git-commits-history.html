2. git status, add, and the staging area

L1

L1 Fundamental

git status is your compass in Git. It reports the state of your working directory relative to the staging area and the latest commit.

# Inspect current status
git status

# Short status output (-s)
git status -s
# ?? = untracked,  M = modified unstaged, M  = modified staged

# Stage a specific file
git add filename.txt

# Stage all tracked and untracked changes in current directory
git add .

# Interactive staging: review and stage individual code hunks
git add -p
  • Untracked: New files created in your working directory that Git has never seen.
  • Modified (Unstaged): Tracked files with local modifications not yet added to the staging index.
  • Staged: Snapshots queued in the index ready to be sealed into the next commit.

3. Writing good commits

L1

L1 Fundamental

A Git commit is an immutable snapshot of your staged files accompanied by author metadata, a timestamp, a pointer to its parent commit(s), and a log message.

# Create a commit with an inline message
git commit -m "feat: add user authentication endpoint"

# Open configured default editor for multi-line commit messages
git commit

# Amend the most recent unpushed commit (fix typo or add missed staged file)
git add missed-file.txt
git commit --amend -m "feat: add user authentication endpoint with validation"
  • Conventional Commits: Follow <type>(<scope>): <description> (e.g. feat, fix, docs, chore, refactor).
  • Imperative Mood: Write "add feature" instead of "added feature" or "adds feature".
  • Atomic Commits: Each commit should address exactly one logical task or fix.

4. git log, show, and diff

L1 L2

L1 Fundamental

Inspecting commit history and code differences is essential for auditing project evolution.

# View commit history (one line per commit)
git log --oneline -n 10

# View visual branch and merge history graph
git log --graph --oneline --all --decorate

# Inspect changes in working directory vs staging index
git diff

# Inspect changes in staging index vs last commit (HEAD)
git diff --staged

# View metadata and full patch of a specific commit
git show HEAD
git show a1b2c3d

5. gitignore and untracked files

L1 L2

L1 Fundamental

The .gitignore file tells Git which files and folders to ignore so they are never accidentally staged or committed.

# Comments start with hash
# Ignore environment secrets
.env
.env.local

# Ignore dependencies and build artifacts
node_modules/
dist/
build/
*.log

# Untrack a file that was accidentally committed earlier (keeps it on disk)
git rm --cached sensitive-config.json
  • Rule: .gitignore only applies to untracked files. If a file is already committed, it must be untracked using git rm --cached before Git will ignore it.

C. Common questions

L1 L2

L1 Fundamental

C.1. What is the difference between git diff and git diff --staged? ▾ Answer

git diff compares modified files in your working directory against the staging area (shows what you have changed but NOT yet staged). git diff --staged (or --cached) compares the staging area against the latest commit (HEAD), showing exactly what will be included if you run git commit right now.

C.2. When is it safe to use git commit --amend? ▾ Answer

git commit --amend creates a brand-new commit with a new SHA-1 hash to replace the previous commit. It is completely safe to use on local, unpushed commits. Never amend commits that have already been pushed to a shared remote, as doing so rewrites public history and causes conflicts for teammates.

L2 Intermediate

C.3. Why is interactive staging (git add -p) recommended? ▾ Answer

git add -p splits file modifications into discrete "hunks" and prompts you to stage or skip each one. This allows you to review your changes before committing, exclude accidental debugging logs or unrelated edits, and craft clean, atomic commits even when multiple changes exist in the same file.

C.4. Why does adding a file to .gitignore have no effect if the file was already committed? ▾ Answer

.gitignore only instructs Git not to track new, untracked files. Files that are already tracked in Git's index continue to be tracked regardless of .gitignore rules. To make Git ignore them, you must remove them from the staging index using git rm --cached <file> and commit the removal.

P. Practical Assignment

L1 L2
Practice commit hygiene. Prefer small, focused commits.

L1 Fundamental

P.1. Warm-up

  1. Stage part of changes with git add -p (or add specific files). ▾ Solution 
    # Interactive patch staging: select specific hunks to stage
git add -p app.js

# Prompts per hunk:
# y - stage this hunk
# n - do not stage this hunk
# s - split into smaller hunks
# q - quit
  2. Write a commit with a clear subject line. ▾ Solution 
    # Conventional Commit format: <type>(<scope>): <subject>
git commit -m "feat(auth): implement JWT token refresh mechanism"

# Rules: Imperative mood, no trailing period, concise under 50 chars.
  3. View git log --oneline and git show. ▾ Solution 
    # Compact one-line history
git log --oneline -n 5

# Inspect specific commit diff and metadata
git show HEAD

P.2. Core tasks

  1. diff — Unstaged vs staged vs last commit diffs. ▾ Solution 
    # 1. Diff unstaged changes in working tree vs staging area
git diff

# 2. Diff staged changes vs last commit (HEAD)
git diff --staged

# 3. Diff working tree vs last commit
git diff HEAD
  2. amend — Fix the last commit message (unpushed only). ▾ Solution 
    # Amend the most recent unpushed commit (update message or include forgotten staged file)
git add forgotten-file.js
git commit --amend -m "feat: updated message with all changes included"

# WARNING: Only amend commits that have not yet been pushed to a shared remote!
  3. gitignore — Ignore .env and a dist/ folder; prove they stay untracked. ▾ Solution 
    # Create .gitignore file
cat << 'EOF' > .gitignore
# Environment secrets
.env
.env.local

# Build artifacts and dependencies
dist/
build/
node_modules/
*.log
EOF

git add .gitignore
git commit -m "chore: add .gitignore for secrets and build artifacts"
  4. log graph — git log --graph --oneline --all. ▾ Solution 
    # Visual ASCII branch and merge history graph
git log --graph --oneline --all --decorate

L2 Intermediate

P.3. Challenge

  1. Rewrite 3 bad commit messages into good ones (as comments). ▾ Solution 
    /*
Refactoring Poor Commit Messages:
1. BAD: "fix bug"
   GOOD: "fix(login): handle empty password submission error"

2. BAD: "changes"
   GOOD: "refactor(api): extract user serialization into helper function"

3. BAD: "update styles and fix layout and add button"
   GOOD: Split into atomic commits:
         - "feat(ui): add primary call-to-action button"
         - "style(layout): align dashboard sidebar grid columns"
*/
  2. Recover an “almost lost” change: commit, reset soft, recommit differently. ▾ Solution 
    # Preview: Recovering changes using Soft Reset (Mastered in File 08: Stash, Cherry-pick & Reset):
# (Note: In this tier, git commit --amend is your primary tool for updating the most recent commit)
# 1. Commit created prematurely
git commit -m "wip: incomplete work"

# 2. Undo commit while keeping changes staged in the index (Preview of File 08)
git reset --soft HEAD~1

# 3. Adjust files and recommit cleanly
git add extra-changes.js
git commit -m "feat: complete clean implementation"
