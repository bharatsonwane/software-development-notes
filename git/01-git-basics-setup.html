2. What Git is and why version control

L1

L1 Fundamental

Git is a modern Distributed Version Control System (DVCS) created by Linus Torvalds in 2005 to manage the Linux kernel development. It tracks changes across files over time, enabling developers to recall specific versions, audit changes, and collaborate efficiently.

  • Centralized VCS (e.g. SVN, CVS): A single central server holds all revision history. If the server is offline or corrupt, developers cannot commit, view logs, or branch.
  • Distributed VCS (Git): Every clone is a complete mirror of the repository, including the entire commit history and object database. All everyday operations (commit, log, diff) happen locally and instantaneously without a network connection.
  • Content-Addressed Storage: Every file and commit is identified by an immutable cryptographic hash (SHA-1 / SHA-256), ensuring complete data integrity.

3. Install Git and first-time config

L1

L1 Fundamental

After installing Git, verify the installation and configure your author identity. Git records this information into every commit you create.

# Verify installation
git --version

# Set global commit author identity
git config --global user.name "Your Name"
git config --global user.email "your.email@example.com"

# Set default initial branch name
git config --global init.defaultBranch main

# Inspect configuration and source files
git config --list --show-origin
  • System level (--system): Applied system-wide (/etc/gitconfig).
  • Global level (--global): Applied to your operating system user (~/.gitconfig).
  • Local level (--local): Specific to the active repository (.git/config); overrides global settings.

4. git init vs git clone

L1

L1 Fundamental

There are two ways to obtain a Git repository on your machine:

# Approach A: Initialize a fresh repository in the current directory
mkdir my-project && cd my-project
git init

# Approach B: Clone an existing repository from a remote URL
git clone https://github.com/user/repo.git

# Shallow clone: Download only the latest revision (saves bandwidth and disk)
git clone --depth 1 https://github.com/user/repo.git
  • git init creates a hidden .git/ directory holding the repository database, configuration, and default references.
  • git clone initializes the directory, downloads the full object history, creates remote tracking branches, and checks out the default branch into your working tree.

5. Working tree, staging area, repository

L2

L2 Intermediate

Git manages files across three distinct areas (the "Three Trees" architecture):

/*
Git Three-Tree Lifecycle:

Working Tree             Staging Area (Index)          Repository (.git)
[ Files on disk ]        [ .git/index cache ]          [ Object database ]
       │                         │                             │
       │────── git add ─────────>│                             │
       │                         │────── git commit ──────────>│
       │<───── git checkout ───────────────────────────────────│
*/
  1. Working Tree: The actual files on your filesystem that you view and edit.
  2. Staging Area (Index): A binary index file (.git/index) that acts as a preparation area. It records precisely which changes will be included in the next commit.
  3. Repository (History): The permanent object store inside .git/objects holding immutable commit snapshots.

C. Common questions

L1 L2

L1 Fundamental

C.1. What is the core architectural difference between a Centralized VCS and a Distributed VCS like Git? ▾ Answer

In a Centralized VCS (e.g., SVN), there is only one central server that maintains the revision history. If that server is down or unreachable, developers cannot commit or review logs. In Git (DVCS), every clone contains the complete repository history and object store locally. Committing, branching, diffing, and inspecting history are 100% offline operations.

C.2. What happens when you run git init in a directory? ▾ Answer

git init creates a hidden .git subfolder containing the Git internal database: the object store (objects/), references (refs/), configuration (config), hooks (hooks/), and the current branch pointer (HEAD). Existing files in the directory remain untouched until staged with git add.

L2 Intermediate

C.3. Why does Git have a Staging Area (Index) instead of committing directly from the working tree? ▾ Answer

The staging area decouples what you are editing on disk from what you are recording as a historical snapshot. This allows developers to craft atomic, focused commits — staging only specific files or specific hunks (git add -p) while keeping other work-in-progress edits unstaged.

C.4. How does Git determine configuration precedence when the same setting exists in multiple places? ▾ Answer

Git searches configuration in three hierarchical scopes, where the most specific scope wins: Local (.git/config) overrides Global (~/.gitconfig), which in turn overrides System (/etc/gitconfig). You can inspect the source of all active configurations using git config --list --show-origin.

Use a throwaway folder. Run the commands in your terminal to verify each state transition directly.

L1 Fundamental

P.1. Warm-up

  1. Install or confirm git --version. ▾ Solution 
    # Confirm Git installation
git --version
# Output: git version 2.39.0 (or newer)
  2. Set user.name and user.email (global or local). ▾ Solution 
    # Configure global user identity
git config --global user.name "Bharat Sonwane"
git config --global user.email "bharat@example.com"

# Verify configured identity
git config user.name
git config user.email
  3. git init a demo repo and make one empty commit or add a README. ▾ Solution 
    # Initialize a new git repository
mkdir demo-repo && cd demo-repo
git init

# Create and commit initial README
echo "# Demo Project" > README.md
git add README.md
git commit -m "chore: initial commit with README"

P.2. Core tasks

  1. clone vs init — Clone a public repo; note .git presence. Init another empty project. ▾ Solution 
    # 1. Clone an existing repository (creates folder with pre-existing .git history)
git clone https://github.com/example/sample-repo.git

# 2. Initialize from scratch (creates an empty .git directory in current folder)
mkdir my-new-app && cd my-new-app
git init
ls -la .git # Contains hooks, objects, refs, and HEAD
  2. three areas — Edit a file; show status before add, after add, after commit. ▾ Solution 
    # Three Areas Lifecycle:
# 1. Edit file in Working Tree
echo "console.log('v1');" > app.js
git status # Shows app.js as Untracked in Working Tree

# 2. Move to Staging Area (Index)
git add app.js
git status # Shows app.js as "Changes to be committed" in Staging

# 3. Commit to Repository (.git database)
git commit -m "feat: add app entrypoint"
git status # Working tree clean
  3. config list — git config --list --show-origin and identify where name/email come from. ▾ Solution 
    # List all active configurations and the files they originate from
git config --list --show-origin

# Output indicates whether settings come from:
# - file:/etc/gitconfig (system)
# - file:~/.gitconfig (global user)
# - file:.git/config (local repository)
  4. clone depth — Try a shallow clone and comment when you’d use it. ▾ Solution 
    # Shallow clone (fetches only the latest commit without entire historical log)
git clone --depth 1 https://github.com/torvalds/linux.git

# Benefit: Drastically reduces download size and time; ideal for CI/CD runners and deployment builds.

  2. Break something safely: unset user.email locally and see the commit error; fix it. ▾ Solution 
    # Unsetting email locally to simulate commit failure
git config --local --unset user.email
git commit --allow-empty -m "test"
# Error: *** Please tell me who you are. Run git config user.email "..."

# Fix: Set local identity
git config --local user.email "bharat@example.com"
git commit --allow-empty -m "fix: commit succeeds after configuring identity"
